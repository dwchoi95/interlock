\section{Introduction}
\label{sec:intro}

에이전트가 외부 도구를 받아오는 표준은 MCP(Model Context Protocol)다~\cite{gaire2026systematization}. 사용자는 설정 파일에 서버를 적고, 서버마다 그것을 실행할 명령, 서버가 받을 자격증명, 그리고 (일부 서버는) 어떤 도구를 광고할지 정하는 플래그를 함께 적는다. 그러면 호스트가 서버를 띄우고 도구 목록을 받아, 각 도구의 이름과 설명, 스키마를 모델에게 보여준다. 이렇게 한 세션에 모인 도구 전부를 그 배포의 \emph{tool surface}, 곧 모델이 부를 수 있는 도구의 집합이라 부른다. 이 방식은 이미 굳어졌다. 실제 애플리케이션 1,723개 중 85.2\%가 서버 목록을 파일로 두는 반면, 도구 호출을 멈추고 사용자 승인을 받는 차단형 게이트를 두는 것은 37.2\%뿐이다~\cite{majeed2026empirical}. 서버 한 줄을 적으면, 대개 그 서버의 도구는 모델이 부르기만 하면 실행된다.
% An LLM agent obtains external tools mainly through the Model Context Protocol (MCP)~\cite{gaire2026systematization}. A user lists servers in a configuration file, giving for each the command that starts it, the credentials it receives and, for some servers, flags that decide which of its tools are advertised. The host then starts each server, retrieves its tool list, and shows the model each tool's name, description and schema. We call the tools assembled for one session the deployment's \emph{tool surface}, the set of tools the model may call. This arrangement is settled: of 1,723 real applications, 85.2\% keep their server list in a file, while only 37.2\% put a blocking approval gate in front of a tool call~\cite{majeed2026empirical}. Listing one server therefore usually means its tools run on the model's call alone.

이 층위를 보호하는 연구는 세 갈래다. \emph{개별 검사}는 도구 하나 또는 서버 하나를 놓고 위험한지를 판정해, 광고된 설명의 숨은 지시와 이름 가로채기, 서버 구현 안의 결함, 실행 중의 이상 동작을 찾아낸다~\cite{jain2026detecting, ye2026trustdesc, wang2026mcptox, sun2026viper, tan2026sandscope}. \emph{조합 검사}는 도구의 능력 라벨을 받아, 신뢰할 수 없는 콘텐츠와 비공개 데이터, 그리고 공격자가 읽을 수 있는 목적지가 한 세션에 함께 모이는 조합을 위험으로 지목한다~\cite{willison2025lethal, beurerkellner2025toxicflow, schneider2026securing}. \emph{권한 제한}은 사용자의 작업에서 도구 권한 정책을 만들어 호출마다 집행한다~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}.
% Much research protects this layer, and it falls into three strands. \emph{Per-artifact vetting} judges one tool or one server dangerous or not, finding hidden instructions and shadowed names in advertised descriptions, defects inside a server implementation, and anomalous behaviour at run time~\cite{jain2026detecting, ye2026trustdesc, wang2026mcptox, sun2026viper, tan2026sandscope}. \emph{Set-level analysis} takes the tools' capability labels and names as dangerous the combination in which untrusted content, private data and a destination the attacker can read meet in one session~\cite{willison2025lethal, beurerkellner2025toxicflow, schneider2026securing}. \emph{Privilege narrowing} derives a tool-privilege policy from the user's task and enforces it at every call~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}.

실제 배포에서는 그 전제가 성립하지 않는다. 그림~\ref{fig:example}은 우리가 다루는 상황으로 MCP를 이용하여 자기 저장소의 열린 이슈를 정리하는 과정을 보여준다. 먼저 \stepnum{1}에서 개발자가 코딩 에이전트에 GitHub MCP 서버 하나를 붙인다. \stepnum{2}에서 호스트가 그 서버에 도구 목록을 요청하는데, 설정에 적힌 것은 서버 한 줄이지만 돌아오는 도구는 우리가 계측한 버전 기준 26개이고 모두 모델이 부를 수 있다. 이 가운데 셋이 모이면 유출 경로가 된다. \stepnum{3}의 \texttt{list\_issues}는 누구나 쓸 수 있는 공개 이슈를 컨텍스트로 들여오고, \stepnum{4}의 \texttt{get\_file\_contents}는 같은 토큰으로 비공개 저장소를 읽으며, \stepnum{5}의 \texttt{add\_issue\_comment}는 그 내용을 공격자가 읽을 수 있는 공개 이슈에 쓴다. 공격자가 공개 이슈에 지시문을 심어 두면, 에이전트는 그 이슈를 읽다가 지시를 따른다. 이런 경로는 손대지 않은 GitHub MCP 서버 하나만 연결한 상태에서 실제로 시연되었다~\cite{milanta2025github}. 그런데 \emph{개별 검사}는 \stepnum{3}과 \stepnum{4}, \stepnum{5}를 하나씩 보기 때문에 여기서 아무것도 지목하지 않는다~\cite{jain2026detecting, sun2026viper, tan2026sandscope}. \emph{조합 검사}는 셋이 함께 쓰일 때를 보므로 이 경로를 정확히 지목할 수 있다~\cite{beurerkellner2025toxicflow, schneider2026securing}. 그러나 거기서 멈춘다. 이 배포가 위험하다고 판정할 뿐 무엇을 꺼야 하는지는 말하지 않으므로, 사용자에게 남는 선택은 경고를 무시하거나 서버를 통째로 지우는 것뿐이다. 대책이 될 수 있는 것은 \emph{권한 제한}뿐이다. 작업에서 정책을 만들어 \stepnum{4}를 끄는 데까지 간다~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}. 다만 그러려면 \stepnum{4}가 비공개 데이터에 닿는다는 것을 먼저 알아야 하는데, 그 정보는 제공자가 쓴 이름과 설명에 없고 기계가 읽을 형태로 어디에도 선언되어 있지 않다. 이 예시가 드러내는 것은 일반적인 한계다. 권한 제한은 도구가 무엇에 닿는지를 제공자가 쓴 글에서 읽고, 그 글이 실제 구현과 맞는지는 아무도 확인하지 않는다. 그래서 글이 어긋나면 정책도 어긋나는데, 어긋났다는 사실이 드러나지 않는다. 비공개 데이터에 닿는 도구를 닿지 않는다고 믿고 열어 둔 채로 최소 권한을 집행했다고 보고하게 되며, 틀린 정책과 맞는 정책이 구별되지 않는다. 더구나 그 글은 우리 위협 모델에서 공격자가 쓸 수 있는 것이어서, 설명을 고치면 정책이 따라 바뀐다. 게다가 안다고 해도 끝이 아니다. 이 경로는 세 도구 가운데 어느 하나만 꺼도 끊어지므로, 무엇을 끌지는 \stepnum{6}의 선언된 작업이 정한다. 그 작업이 열린 이슈를 정리해 요약을 코멘트로 남기는 것이라면 \stepnum{3}과 \stepnum{5}는 작업이 쓰는 도구여서 끌 수 없고, \stepnum{4}만 끌 수 있다. 무엇을 끌지는 위험의 성질이 아니라 배포가 선언한 작업이 정하는 것이다. 그래서 도구를 하나씩 끄는 수단이 있고 정책을 만들 줄 아는 연구가 있어도, \stepnum{7}과 같은 정밀한 변경을 계산해 주는 것은 없다.
% In a real deployment that presupposition does not hold. Figure~\ref{fig:example} shows the situation we address: triaging the open issues of one's own repository through MCP. In \stepnum{1} a developer connects one GitHub MCP server to a coding agent. In \stepnum{2} the host asks that server for its tool list; the configuration names a single server, but 26 tools come back in the version we measured, every one callable by the model. Three of them form a leak. \texttt{list\_issues} in \stepnum{3} brings a publicly writable issue into the context, \texttt{get\_file\_contents} in \stepnum{4} reads a private repository with the same token, and \texttt{add\_issue\_comment} in \stepnum{5} writes the result back to the public issue where the attacker can read it. If the attacker has planted instructions in a public issue, the agent follows them while reading it. A path of this shape has been demonstrated with a single unmodified GitHub MCP server~\cite{milanta2025github}. \emph{Per-artifact vetting} looks at \stepnum{3}, \stepnum{4} and \stepnum{5} one at a time and so flags nothing here~\cite{jain2026detecting, sun2026viper, tan2026sandscope}, because none of the three is malicious or defective --- the authors who reported the demonstration say as much, that it is ``not a flaw in the server code''. \emph{Set-level analysis} looks at the three used together and can name this path exactly~\cite{beurerkellner2025toxicflow, schneider2026securing}, but it stops there: it judges the deployment dangerous without saying what to switch off, leaving the user to dismiss the warning or delete the server whole. The only strand that can act is \emph{privilege narrowing}, which derives a policy from the task and goes as far as denying \stepnum{4}~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}. To do that, though, it must first know that \stepnum{4} reaches private data, and that is not in the names and descriptions the provider wrote, nor declared anywhere else a machine can read. What the example exposes is a general limitation: privilege narrowing reads what a tool reaches off prose the provider wrote, and nothing checks that prose against the implementation. When the two diverge the policy diverges with them, and the divergence does not show. A tool that reaches private data is left open in the belief that it does not, while the system reports that least privilege is being enforced, so a wrong policy is indistinguishable from a right one. That prose is also, under our threat model, attacker-writable: edit the description and the policy follows. Even knowing what a tool reaches is not enough: switching off any one of the three tools breaks it, so which one to switch off is decided by the declared task in \stepnum{6}. If that task is to triage the open issues and comment a summary, then \stepnum{3} and \stepnum{5} are tools the task uses and cannot go, leaving \stepnum{4} as the only edge that may. What to switch off is decided by the deployment's declared task rather than by the nature of the danger. So although the means to switch off one tool at a time exists and research knows how to produce a policy for it, nothing computes a precise change like~\stepnum{7}.

이 논문에서 우리는 \textsc{Interlock}을 제시한다. 도구가 무엇에 닿는지를 제공자가 쓴 글이 아니라 서버의 소스 코드에서 회수하되 모든 주장을 기계적으로 재검사하고, 그렇게 얻은 효과 요약이 실제로 쓸 수 있는 정보임을 설정 변경을 계산해 보이는 접근이다. \emph{Summarize}는 신뢰도 순으로 정렬한 증거에서 도구마다 어떤 효과에 닿는지를 판정하고, 판정마다 그것을 뒷받침하는 코드 위치를 남긴다. 이 요약은 그 자체로 앞 문단의 빈자리를 채우는 산출물이며, 런타임 최소 권한 시스템이 사람 손으로 채우던 라벨을 대신할 수 있다. 우리는 이어서 그 요약이 설정 수준에서 실행 가능함을 보인다. \emph{Decide}는 설정이 지정한 값 수준 조건을 적용한 뒤 요약 위에서 흐름 정책을 평가해 금지된 흐름마다 그림의 \stepnum{3}--\stepnum{5}처럼 그것을 만드는 도구를 짚는다. \emph{Repair}는 호스트와 서버가 이미 가진 수단 --- 도구 거부 항목, 서버 모드와 toolset 플래그, 인자 축소, 마지막 수단인 서버 제거 --- 위에서 선언된 작업을 지키는 최소 비용 patch를 만들고, 그 결과가 \stepnum{7}의 설정 diff다. 집행에 호스트를 고칠 필요는 없다.
% In this paper we present \textsc{Interlock}, an approach that recovers what a tool reaches from the server's source code rather than from prose the provider wrote, re-checks every claim mechanically, and then shows that the resulting effect summaries are usable information by computing a configuration change from them. \emph{Summarize} judges, from evidence ranked by trust, which effects each tool can reach, and records for every judgement the code location that supports it. These summaries are themselves the artifact the previous paragraph finds missing, and they can stand in for the labels that run-time least-privilege systems fill in by hand. We then show that they are actionable at the level of a configuration. \emph{Decide} applies the value-level conditions the configuration sets, evaluates a flow policy over the summaries and points to the tools that make each forbidden flow, as \stepnum{3}--\stepnum{5} do in the figure. \emph{Repair} builds a minimum-cost patch over the controls hosts and servers already have --- per-tool deny entries, server mode and toolset flags, argument narrowing, and server removal as a last resort --- subject to preserving the declared tasks, and \stepnum{7} is the configuration diff it emits. Enforcement needs no change to the host.

핵심 난점은 그 정보가 선언되어 있지 않다는 것이다. 효과를 코드에서 읽어내야 하는데, 두 길 모두 쉽지 않다. 공개 패키지를 전부 정적 분석으로 따라가면 규모가 맞지 않고, 언어 모델에 읽히면 그 판정을 무엇으로 믿느냐가 남는다. 우리는 \emph{신뢰도 순위 요약과 결정적 재검사}를 묶어 이를 푼다. 모델이 서버의 소스를 읽고 도구별 효과를 판정하되 주장마다 \texttt{file:line} 증거를 달게 하고, 결정적 검사기가 가져온 소스에서 그 줄을 다시 읽어 확인되지 않는 주장을 걸러낸다. 확인되지 않은 주장은 버리지 않고 ``미확인''으로 표시해 라벨을 지키며, 모델이 판정하지 않은 도구에는 가장 보수적인 값을 준다. 문서만 근거로 한 ``무해'' 판정은 무해로 세지 않는다. 문서는 효과가 없다는 것을 증명하지 못하기 때문이다. 그래서 출력은 그럴듯한 요약이 아니라, 독자가 코드 한 줄까지 되짚을 수 있는 감사 가능한 기록이 된다.
% The central difficulty is that this information is not declared, so effects must be read out of code, and neither route is easy: following every published package by static analysis does not scale, and handing the code to a language model leaves open what makes its judgement trustworthy. We solve this by pairing \emph{trust-ranked summarisation with deterministic re-checking}. The model reads the server's source and judges each tool's effects, but must cite \texttt{file:line} evidence for every claim, and a deterministic checker re-reads the cited span in the fetched source and drops what it cannot confirm. An unconfirmed claim is kept and marked undetermined rather than discarded; a tool the model does not judge takes the most conservative value; and a clearance based only on documentation does not count, because documentation cannot show that an effect is absent. The output is thus an auditable record a reader can trace to a line of code, not a plausible summary.

\noindent\textbf{Contributions.} We summarize our contributions as follows:
\begin{itemize}
    \item \textbf{Observation:} 우리는 에이전트 최소 권한 기법들이 공통으로 전제하는 것, 곧 도구마다 무엇에 닿는지가 이미 알려져 있다는 전제를 정리하고, 그 전제를 세 시스템이 스스로 가정이나 한계로 적고 있음을 보인다. 또한 그 전제를 실제 서버에 대해 채우려는 유일한 선행 도구가 사람들이 실제로 선언하는 서버 대부분을 차지하는 생태계에서 작동하지 않음을 보인다.
    % \item \textbf{Observation:} We identify the presupposition that agent least-privilege methods share --- that what each tool reaches is already known --- and show that three such systems record it as an assumption or a limitation of their own, and that the one prior tool that tries to supply it for real servers does not work on the ecosystem that most declared servers belong to.
    \item \textbf{New technique:} 우리는 공격자가 쓸 수 있는 산문을 결코 신뢰하지 않고 서버의 소스 코드에서 도구별 효과를 회수하는 절차를 제시한다. 모델의 모든 판정에 \texttt{file:line} 증거를 요구하고 결정적 검사기로 그 구간을 다시 읽어 확인되지 않은 주장을 표시하며, 미판정 도구에는 보수적인 값을 주고 문서만으로는 무해를 인정하지 않는다. 그 위에서 설정에 대한 최소 권한 tool surface 합성을 정식화하고, witness 유도 수선과 제공자가 surface를 바꿀 때의 재판정을 제시한다.
    % \item \textbf{New technique:} We present a procedure that recovers per-tool effects from a server's source code while never trusting attacker-writable prose: every model judgement must cite \texttt{file:line} evidence, a deterministic checker re-reads the cited span and marks what it cannot confirm, unjudged tools take a conservative value, and documentation alone never clears a tool. On top of it we formulate least-privilege tool-surface synthesis for a configuration, with witness-guided repair and re-decision when a provider changes its surface.
    \item \textbf{Evaluation:} 우리는 이 절차를 구현해 공개 설정에서 가장 자주 선언되는 서버 34개와 그 도구 433개에 적용하고, 모델 판정 가운데 결정적 재검사를 통과하는 비율(전체 72.5\%, 구현 코드가 배포되는 경우 90.7\%)을 보고한다. 또한 공개된 패키지를 읽는 것만으로는 효과를 확정할 수 없는 세 가지 구조적 한계를 식별한다. 도구와 코드에서 도출한 효과 요약을 공개한다.
    % \item \textbf{Evaluation:} We implement the procedure, apply it to the 34 most frequently declared servers in public configurations and their 433 tools, and report how much of the model's judgement survives deterministic re-checking (72.5\% overall, 90.7\% where implementation code is distributed). We further identify the three structural limits where reading a published package cannot establish an effect. We release the tool and the code-derived effect summaries.
\end{itemize}



\section{Preliminaries}
\label{sec:prelim}

\subsection{Privilege Narrowing based Securing}

호스트 애플리케이션 --- IDE 어시스턴트, 데스크톱 에이전트, 코딩 에이전트 --- 은 설정 파일에 명시된 각 Model Context Protocol 서버를 실행하고 도구 목록을 요청한 뒤, 반환된 이름과 설명, JSON 스키마를 모델의 컨텍스트에 넣는다. 서버는 명령줄로 실행되는 로컬 프로세스일 수도, 컨테이너일 수도, 원격 엔드포인트일 수도 있으며, 스킬 번들이 서버를 추가로 기여하기도 한다. 한 세션에서 광고된 도구들의 합집합을 우리는 그 배포의 \emph{tool surface}라 부른다. 이 구조의 세 가지 성질이 이후 논의를 이끈다. surface는 개별 제공자가 아니라 사용자의 설정이 결정한다. surface 위의 모든 도구는 호출 가능하다. 도구 선택은 광고된 텍스트를 읽은 모델이 하기 때문이다. 그리고 surface는 고정되어 있지 않다. 호스트는 대개 버전을 고정하지 않은 패키지 지정으로 서버를 실행하므로, 도구 뒤의 코드는 사용자가 아무 행동을 하지 않아도 세션 사이에 바뀔 수 있다.
% A host application --- an IDE assistant, a desktop agent, a coding agent --- starts each Model Context Protocol server named in a configuration file, asks it for its tool list, and places the returned names, descriptions and JSON schemas into the model's context. A server may be a local process started by a command line, a container, or a remote endpoint; a skill bundle may contribute further servers. The union of the advertised tools, for the session, is what we call the deployment's \emph{tool surface}. Three properties of this arrangement drive the rest of the paper. The surface is decided by the user's configuration rather than by any single provider. Every tool on it is callable, because tool choice is made by the model from the advertised text. And the surface is not fixed: hosts commonly launch servers from an unpinned package specification, so the code behind a tool can change between sessions without any action by the user.

\label{sec:threatmodel}

우리는 에이전트가 자신이 읽은 콘텐츠 안의 지시를 따른다고 가정한다. 이는 lethal trifecta 프레이밍~\cite{willison2025lethal}과 toxic-flow 분석~\cite{beurerkellner2025toxicflow}이 전제하는 가정이며, 이 층위에 대해 공개된 공격들이 실제로 악용하는 가정이다~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. 공격자는 임의의 웹 호스트와 콘텐츠를 통제하고, 여러 사람이 쓸 수 있거나 제3자가 제공하는 출처의 콘텐츠 --- 공개 이슈와 댓글, 저장소 내용, 커뮤니티 문서와 레지스트리, 검색 결과 --- 도 통제한다. 공격자는 사용자의 로컬 파일이나 사용자 계정에 담긴 데이터를 통제하지 못하며, 설치된 서버를 수정하지도 못한다. 공격자는 자신이 통제하는 호스트와 공개된 모든 것을 읽을 수 있다. 이 가정 아래에서, 어떤 배포의 surface가 한 세션 안에서 비공개 데이터 출처, 공격자가 통제하는 콘텐츠 출처, 공격자가 읽을 수 있는 목적지에 모두 닿을 때 그 배포는 위험하다.
% We assume an agent that follows instructions found in the content it reads, which is the assumption under which the lethal-trifecta framing~\cite{willison2025lethal} and toxic-flow analysis~\cite{beurerkellner2025toxicflow} are stated, and which published attacks on this layer exploit~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. The attacker controls arbitrary web hosts and content, and content in multi-writer or third-party sources: public issues, comments and repository content, community documentation and registries, search results. The attacker does not control the user's local files or the data held in the user's own accounts, and does not modify the installed servers. The attacker can read hosts they control and anything published publicly. Under these assumptions a deployment is dangerous when its surface reaches, in the same session, a source of private data, a source of attacker-controlled content, and a destination the attacker can read.

\label{sec:prelim:baselines}

무엇을 꺼야 하는지에 관여하는 두 갈래, 곧 조합 검사와 권한 제한이 우리의 직접적인 비교 대상이다. 여기에 그 둘이 전제하는 라벨을 직접 뽑으려는 시도를 더해 방법론을 차례로 본다.

% The two strands that bear on what to switch off --- set-level analysis and privilege narrowing --- are what we compare against directly. We go through their methodology in turn, together with the one attempt to extract the labels they presuppose.

\noindent\textbf{Progent.} Progent는 권한을 도구 이름과 인자에 대한 기호 규칙의 집합으로 표현한다~\cite{shi2025progent}. 사용자의 질의가 주어지면 LLM이 작업 수행에 필요한 호출만 허용하고 불필요한 호출은 막는 초기 정책을 자동으로 생성하며, 실행 중 새 정보가 들어오면 정책을 갱신한다. 모든 도구 호출은 결정적 절차로 정책과 대조되고, 이 집행기는 LangChain이나 OpenAI Agents SDK 같은 에이전트 프레임워크 안에 통합된다. 정책 생성기가 입력으로 받는 것은 최초 질의와 사용 가능한 도구 집합이다.
% \noindent\textbf{Progent.} Progent represents privilege as a set of symbolic rules over tool names and arguments~\cite{shi2025progent}. Given the user's query, an LLM automatically generates an initial policy that admits the calls the task needs and blocks the unnecessary ones, and updates that policy during execution as new information arrives. Every tool call is checked against the policy by a deterministic procedure, and the enforcer is integrated into agent frameworks such as LangChain and the OpenAI Agents SDK. What the policy generator receives as input is the initial query and the set of available tools.

\noindent\textbf{CaMeL.} CaMeL은 신뢰된 질의에서 제어 흐름과 데이터 흐름을 먼저 뽑아낸다~\cite{debenedetti2025defeating}. 권한 있는 LLM이 질의를 제한된 프로그램으로 옮기고, 격리된 LLM이 신뢰할 수 없는 데이터를 해석하며, 전용 인터프리터가 값마다 능력(capability)을 추적해 도구가 호출되는 시점에 정책을 집행한다. 이로써 신뢰할 수 없는 데이터가 프로그램의 흐름에 영향을 주지 못한다. 정책은 임의의 로직을 담을 수 있도록 DSL 대신 Python 코드로 작성되며, 현재 구현에서는 CaMeL 엔진이 정의한다. 도구 또한 자기 기능에 따라 능력을 부여하는데, 어떤 주석을 어느 입도로 붙일지는 사용 사례마다 정해진다.
% \noindent\textbf{CaMeL.} CaMeL first extracts the control and data flow from the trusted query~\cite{debenedetti2025defeating}. A privileged LLM turns the query into a restricted program, a quarantined LLM interprets untrusted data, and a custom interpreter tracks a capability per value and enforces policies at the point a tool is called, so that untrusted data cannot affect the program's flow. Policies are written in Python rather than a DSL so that arbitrary logic can be expressed, and in the current implementation they are defined by the CaMeL engine. Tools also assign capabilities according to their functionality, and the choice of annotations and their granularity is made per use case.

\noindent\textbf{Fides.} Fides는 기밀성과 무결성 라벨을 실행 전반에 전파하는 플래너다~\cite{costa2025securing}. 라벨은 대화 이력의 메시지, 도구 인자, 도구 결과, 데이터저장소 변수에 붙고, 도구 결과 트리의 각 노드에 메타데이터 필드로 저장된다. 플래너는 이 라벨을 보고 다음 단계를 정하며, 필요하면 정보를 선택적으로 감춘다. 이 전파가 성립하려면 모든 도구가 자기 출력에 올바른 라벨을 붙여야 하는데, Fides는 신뢰할 수 없는 모든 도구에 신뢰된 wrapper를 둠으로써 이를 확보한다.
% \noindent\textbf{Fides.} Fides is a planner that propagates confidentiality and integrity labels through the execution~\cite{costa2025securing}. Labels are attached to the messages of the conversation history, to tool arguments, to tool results and to datastore variables, and are stored in a metadata field on each node of a tool-result tree. The planner reads these labels to decide the next step and can selectively hide information. For the propagation to hold, every tool must label its outputs correctly, which Fides secures by giving every untrusted tool a trusted wrapper.

\noindent\textbf{\texttt{mcp-sec-audit}.} 이 도구는 위 세 시스템이 전제하는 도구별 능력을 직접 뽑으려는 시도다~\cite{huang2026auditing}. TOML 규칙집에 능력군과 그 지표가 되는 키워드 및 정규식, 심각도 가중치를 적어 두고, 정적 파이프라인이 Python 소스와 MCP 도구 메타데이터 JSON을 훑어 \texttt{file\_read}, \texttt{file\_write}, \texttt{network\_outbound}, \texttt{command\_exec}, \texttt{env\_access} 같은 능력을 탐지한다. 선택적으로 Docker 샌드박스에서 도구를 실행하고 eBPF로 커널 이벤트를 수집하는 동적 파이프라인을 함께 돌린다. 산출물은 탐지된 능력의 신뢰도를 가중합한 위험 점수와, 그 능력에 대응하는 강화 권고다.
% \noindent\textbf{\texttt{mcp-sec-audit}.} This tool is an attempt to extract directly the per-tool capabilities that the three systems above presuppose~\cite{huang2026auditing}. A TOML rulebook records capability families together with the keywords and regular expressions that indicate them and their severity weights, and a static pipeline scans Python source and MCP tool metadata JSON for capabilities such as \texttt{file\_read}, \texttt{file\_write}, \texttt{network\_outbound}, \texttt{command\_exec} and \texttt{env\_access}. A dynamic pipeline optionally runs the tool in a Docker sandbox and collects kernel events with eBPF. The output is a risk score, a weighted sum of the confidences of the detected capabilities, together with hardening advice matched to those capabilities.

\noindent\textbf{조합 검사.} lethal trifecta 프레이밍은 비공개 데이터와 신뢰할 수 없는 콘텐츠, 그리고 외부 전송 --- 곧 공격자가 읽을 수 있는 목적지 --- 가 한 세션에 모이는 것을 위험으로 명명한다~\cite{willison2025lethal}. toxic-flow 분석은 도구 흐름, 곧 가능한 도구 사용 순서를 신뢰 수준과 민감도, 유출 지점 여부 같은 속성과 함께 모델링한다~\cite{beurerkellner2025toxicflow}. 조합 정책은 안전하지 않은 사슬이 시작되기 전에 조합을 차단하고, 누적된 노출로 다음 호출이 위반이 되면 세션을 취소한다~\cite{schneider2026securing}. 개별 검사와 달리 이들은 도구 하나가 아니라 조합을 판정하며, 그림~\ref{fig:example}의 유출 경로를 정확히 지목할 수 있다. 다만 이들은 도구의 능력 라벨을 \emph{입력으로 받는다}. 라벨을 어디서 얻는지는 두 문헌 모두 명시하지 않으며, 평가 규모는 도구 32개에 정책 16개다. 서버 하나가 도구 26개를 광고하는 환경에서는 그 출처가 문제가 되지만, 도구 32개 규모에서는 사람이 붙여도 되는 일이다.
% \noindent\textbf{Set-level analysis.} The lethal-trifecta framing names as dangerous the presence of private data, untrusted content and external communication in one session~\cite{willison2025lethal}. Toxic-flow analysis models tool flows --- the potential sequences of tool uses --- together with properties such as level of trust, sensitivity and whether a tool can act as an exfiltration sink~\cite{beurerkellner2025toxicflow}. Compositional policies block unsafe combinations before a chain starts and revoke the session once accumulated exposure would make the next call a violation~\cite{schneider2026securing}. Unlike per-artifact vetting, these judge a combination rather than an individual tool, and they can name the leak path of Figure~\ref{fig:example} exactly. They do, however, \emph{take} the tools' capability labels as input. Neither reports where those labels come from, and the evaluation scale is 32 tools with 16 policies. Where a single server advertises 26 tools the provenance of the labels matters; at 32 tools it is work a person can do by hand.

\subsection{Limitation}
\label{sec:prelim:limitation}

표~\ref{tab:baselines}가 비교 대상을 정리한다. 앞의 세 시스템은 도구 단위로 권한을 좁히지만, 각 도구가 무엇에 닿는지를 스스로 확정하지는 않는다. Progent의 정책 생성기가 보는 것은 제공자가 쓴 이름과 설명과 스키마이고, CaMeL의 능력 주석은 사용 사례마다 사람이 정하며, Fides는 신뢰된 wrapper를 통해 모든 도구가 올바로 라벨을 붙인다고 가정한다. 그런데 \S\ref{sec:threatmodel}의 위협 모델에서 그 이름과 설명은 공격자가 쓸 수 있는 글이고, 프로토콜 명세 자신도 신뢰된 서버에서 온 것이 아닌 한 도구 annotation을 믿지 말라고 클라이언트에 요구한다. 사람이 손으로 붙이는 주석은 서버 수와 버전 수에 비례해 늘어나는데, 공개 벤치마크는 서버 515개의 버전 9,273개에 걸쳐 초기 도구의 54.6\%가 수정되거나 폐기되었다고 보고한다~\cite{liu2026mcpevol}.
% Table~\ref{tab:baselines} summarises the systems we compare against. The first three narrow privilege at the granularity of a tool but do not themselves establish what each tool reaches: what Progent's policy generator sees are the names, descriptions and schemas the provider wrote; CaMeL's capability annotations are chosen by hand per use case; and Fides assumes, through trusted wrappers, that every tool labels its outputs correctly. Under the threat model of \S\ref{sec:threatmodel}, however, those names and descriptions are attacker-writable prose, and the protocol specification itself requires clients to treat tool annotations as untrusted unless they come from a trusted server. Hand-written annotations grow with the number of servers and versions, and a published benchmark reports that 54.6\% of initial tools were modified or deprecated across 9,273 versions of 515 servers~\cite{liu2026mcpevol}.

더구나 세 시스템의 평가는 실제 MCP 서버가 아니라 벤치마크 안에 정의된 가상 도구 모음 위에서 이루어진다. 그런 환경에서는 도구의 설명과 구현을 같은 저자가 같은 파일에 쓰므로, 도구가 무엇을 하는지 안다는 전제가 구조적으로 참이다. 다시 말해 전제가 깨지는 조건이 평가에 들어 있지 않다.
% Moreover, the three systems are evaluated on simulated tool suites defined inside a benchmark rather than on real MCP servers. In such a setting the description and the implementation of a tool are written by the same author in the same file, so the presupposition that one knows what a tool does holds by construction; the condition under which it breaks is simply absent from the evaluation.

그 전제를 실제 서버에 대해 채워 주려는 시도는 우리가 아는 한 \texttt{mcp-sec-audit} 하나뿐이며, 저자들이 세 가지 한계를 스스로 보고한다. 첫째, 정적 분석기가 Python과 JSON 메타데이터만 지원해 JavaScript 서버 7개 중 0개를 탐지한다. 그런데 사람들이 실제로 선언하는 서버는 대부분 npm이다(표~\ref{tab:corpus}에서 npm 항목 22,010개, PyPI 3,156개). 둘째, 패턴 기반 탐지는 위험한 키워드와 우연히 일치하는 정상 코드에 오탐하고 난독화되거나 간접적으로 호출되는 경우를 놓친다. 셋째, 산출물이 위험 점수와 일반적인 권고여서, 저자들의 표현대로 ``배포 가능한 설정을 생성하지 않는다''. 그리고 어느 경우에도 판정을 코드로 되짚는 장치는 없다.
% To our knowledge only \texttt{mcp-sec-audit} attempts to supply that presupposition for real servers, and its authors report three limitations of their own. First, the static analyser supports only Python and JSON metadata, so it detects 0 of 7 JavaScript servers, while the servers people actually declare are mostly npm (22,010 npm entries against 3,156 PyPI ones in Table~\ref{tab:corpus}). Second, pattern-based detection raises false positives on benign code that happens to match a risky keyword and misses obfuscated or indirect invocations. Third, its output is a risk score and generic advice, so in the authors' words it ``does not generate deployment-ready configurations''. In no case is there a mechanism that traces a judgement back to code.

그림~\ref{fig:example}의 설정에 이 한계들이 어떻게 드러나는지 보면 분명해진다. \emph{개별 검사}는 아무것도 지목하지 않는다. 세 도구 가운데 설명에 숨은 지시가 있거나 구현에 taint 결함이 있는 것이 없기 때문이다. \emph{조합 검사}는 유출 경로를 정확히 지목할 수 있지만 판정에서 멈춘다. 설정을 바꾸지도, 어느 도구를 꺼야 하는지 말하지도 않는다. 게다가 그 판정조차 \stepnum{3}이 신뢰할 수 없는 콘텐츠를 들여오고 \stepnum{4}가 비공개 데이터에 닿으며 \stepnum{5}가 공격자가 읽을 수 있는 곳에 쓴다는 것을 먼저 받아야 가능한데, 그 정보가 바로 아무도 만들지 않는 것이다. 행위까지 가는 것은 \emph{권한 제한}뿐인데, 세 시스템 모두 같은 자리에서 멈춘다. Progent가 이 작업에 필요한 호출만 허용하는 정책을 쓰려면 \stepnum{4}가 비공개 저장소를 읽는다는 것을 알아야 하는데, 그것을 도구 이름과 설명에서 읽어야 한다. Fides가 라벨을 전파하려면 이 서버의 26개 도구에 신뢰된 wrapper가 있어야 하고, CaMeL이라면 그 26개에 능력 주석을 사람이 붙여야 한다.
% How these limitations play out on the configuration of Figure~\ref{fig:example} makes them concrete. \emph{Per-artifact vetting} flags nothing, because none of the three tools carries a hidden instruction in its description or a taint defect in its implementation. \emph{Set-level analysis} can name the leak path exactly but stops at a verdict: it neither changes the configuration nor says which tool to switch off. And even that verdict requires being told first that \stepnum{3} brings in untrusted content, that \stepnum{4} reaches private data and that \stepnum{5} writes where the attacker can read --- precisely what nobody produces. Only \emph{privilege narrowing} goes as far as acting, and its three systems stop at the same place: for Progent to write a policy admitting only the calls this task needs, it must know that \stepnum{4} reads a private repository, and it has to read that off the tool's name and description; for Fides to propagate labels, this server's 26 tools need trusted wrappers; and for CaMeL, a person must annotate those 26 tools with capabilities.

그 정보가 주어졌다고 해도 문제가 남는다. 이 경로는 세 도구 가운데 어느 하나만 꺼도 끊어지므로, 경로를 지목하는 것만으로는 무엇을 꺼야 할지가 정해지지 않는다. \stepnum{6}의 선언된 작업이 열린 이슈를 정리해 요약을 코멘트로 남기는 것이라면, \stepnum{3}은 이슈를 읽는 도구이고 \stepnum{5}는 요약을 남기는 도구여서 둘 다 끌 수 없다. 저장소 파일을 읽는 \stepnum{4}만이 끌 수 있는 도구다. 무엇을 끌지는 위험의 성질이 아니라 배포가 선언한 작업이 정하며, 이것은 탐지 문제가 아니라 작업 보존 제약 아래의 선택 문제다. 위 어느 시스템도 이 제약을 명시적으로 다루지 않는다. 끝으로 Progent와 CaMeL, Fides는 판정을 실행 시점에 내리므로 판정이 옳더라도 사용자에게 남는 산출물이 없다. 같은 설정을 내일 다시 열면 같은 판정을 처음부터 다시 만들어야 하고, 제공자가 도구를 추가해도 어제의 판정이 무효가 되었다는 사실은 어디에도 기록되지 않는다.
% Even given that, a question remains. The path is broken by switching off any one of its three tools, so naming it does not by itself say what to switch off. If the declared task in \stepnum{6} is to triage the open issues and comment a summary, then \stepnum{3} is the tool that reads the issues and \stepnum{5} is the tool that leaves the summary, so neither can go; \stepnum{4}, which reads repository files, is the only one that may. Which tool to switch off is decided by the deployment's declared task rather than by the nature of the danger, and that is not a detection problem but a choice under a task-preservation constraint, which none of the systems above addresses explicitly. Finally, Progent, CaMeL and Fides decide at run time, so even a correct decision leaves the user with no artifact: opening the same configuration tomorrow means deriving the same decision from scratch, and when a provider adds a tool, nothing records that yesterday's decision has been invalidated.

이 논문의 목표는 실제 MCP 서버의 도구마다 무엇에 닿는지를, 제공자가 쓴 글이 아니라 배포된 코드에서, 독자가 되짚을 수 있는 형태로 회수하는 것이다. 이 산출물은 위 세 시스템이 사람 손으로 채우거나 가정으로 두던 자리를 대신할 수 있고, 설정 시점에 직접 쓰일 수도 있다.
% The goal of this paper is to recover, for each tool of a real MCP server, what that tool reaches --- from the code that is distributed rather than from prose the provider wrote, and in a form a reader can trace. Such an artifact can stand in for what the three systems above fill in by hand or leave as an assumption, and it can also be used directly at configuration time.

두 가지가 어렵다. 첫째, 공개된 패키지를 전부 정적 분석으로 따라가는 것은 규모가 맞지 않는다. 서버는 TypeScript와 Python, Go, Rust 등으로 작성되고, 번들이나 minify된 형태로, 또는 바이너리를 내려받는 실행기로 배포되며, 얇은 wrapper가 실제 구현을 의존성에 두기도 한다. \texttt{mcp-sec-audit}이 JavaScript에서 멈춘 지점이 바로 여기다. 둘째, 언어 모델에 코드를 읽히면 규모 문제는 사라지지만 그 판정을 무엇으로 믿을지가 남는다. 모델은 읽지 않은 것을 그럴듯하게 서술할 수 있고, 판정 대상이 바로 공격자가 쓸 수 있는 텍스트를 포함하고 있다. 따라서 목표는 판정을 얻는 것만이 아니라, 얻은 판정 가운데 코드로 뒷받침되는 부분과 그렇지 않은 부분을 기계적으로 가르는 것까지를 포함한다.
% Two things make this hard. First, following every published package by static analysis does not scale: servers are written in TypeScript, Python, Go and Rust, are shipped bundled, minified or as launchers that download a binary, and thin wrappers leave the real implementation in a dependency --- which is exactly where \texttt{mcp-sec-audit} stops on JavaScript. Second, handing the code to a language model removes the scale problem but leaves the question of what makes its judgement trustworthy: a model can describe plausibly what it has not read, and the object being judged contains the very text an attacker can write. The goal therefore includes not only obtaining judgements but mechanically separating the part of them that is backed by code from the part that is not.

\section{Our Approach}
\label{sec:approach}

\subsection{Overview}

\textsc{Interlock}은 설정, 흐름 정책, 배포가 선언한 작업을 입력으로 받아, 호스트와 서버가 이미 제공하는 제어 수단 위의 patch를 반환한다. 절차는 세 단계다. \emph{Summarize}는 신뢰도 순으로 정렬한 증거에서 도구별 효과 요약을 도출한다. \emph{Decide}는 설정이 유도한 surface에 대해 정책을 평가하고 각 금지 흐름을 증언하는 도구를 반환한다. \emph{Repair}는 최소 비용 patch --- 도구 단위 거부 항목, 서버 모드와 toolset 플래그, 인자 축소, 그리고 가장 비싼 선택지인 서버 제거 --- 를 탐색해 금지된 흐름을 제거하면서 선언된 작업이 계속 동작하도록 한다. 이 논문은 \emph{Summarize}를 구현·평가하며, \emph{Decide}와 \emph{Repair}는 여기서 명세하고 진행 중인 작업으로 남겨 두되, 두 단계에 관한 모든 진술은 그에 맞게 표시한다.
% \textsc{Interlock} takes a configuration, a flow policy and the deployment's declared tasks, and returns a patch over the controls that hosts and servers already expose. It proceeds in three stages. \emph{Summarize} derives a per-tool effect summary from evidence ranked by trust. \emph{Decide} evaluates the policy over the surface the configuration induces and returns the tools that witness each forbidden flow. \emph{Repair} searches for a minimum-cost patch --- per-tool deny entries, server mode and toolset flags, argument narrowing, and, as the most expensive option, server removal --- that removes the forbidden flows while keeping the declared tasks working. This paper implements and evaluates \emph{Summarize}; \emph{Decide} and \emph{Repair} are specified here and are the subject of ongoing work, and we mark every claim about them accordingly.

\subsection{Summarize: Trust-ranked Effect Summaries}

이 단계는 광고된 도구마다 하나의 질문에 답한다. 이 도구는 SECRET, UNTRUSTED, SINK, HOSTEXEC 가운데 무엇에 닿을 수 있으며 그 증거는 무엇인가. 증거는 공격자가 얼마나 통제할 수 있는지에 따라 순위가 매겨진다. 설정 자신의 인자와 서버의 소스 코드가 1순위, 선언된 스키마와 annotation이 2순위이며, 자유 서술 설명은 효과를 낮추는 데 결코 쓰이지 않는다. 올리는 데만 쓸 수 있는데, 설명은 판정 대상인 당사자가 작성하기 때문이다. HOSTEXEC은 나머지 셋을 함의한다. 호스트에서의 코드 실행은 호스트가 닿을 수 있는 모든 것에 닿기 때문이다.
% The stage answers one question per advertised tool: which of SECRET, UNTRUSTED, SINK and HOSTEXEC can this tool reach, and what is the evidence? Evidence is ranked by how much an attacker controls it. The configuration's own arguments and the server's source code rank first, declared schemas and annotations second, and free-text descriptions are never allowed to lower an effect --- they may only raise one, because a description is written by the party being judged. HOSTEXEC implies the other three, since host code execution reaches whatever the host can reach.

요약은 언어 모델이 생성하되 모든 주장에 \texttt{file:line} 증거를 인용해야 하며, 이후 결정적 검사기가 가져온 소스에서 인용된 구간을 다시 읽어 걸러낸다. 인용이 가져온 트리 안에서 해석되지 않거나, 그 구간에 도구 이름이나 근거 설명이 지목한 식별자가 없으면, 그 주장은 유지되되 미확인으로 표시된다. 미확인 주장이 효과를 낮춰서는 안 되므로 라벨은 살아남지만, 검증된 것으로는 세지 않는다. 모델이 아예 판정하지 않은 도구에는 가장 보수적인 값인 HOSTEXEC을 부여한다. 모델이 라벨 없이 무해하다고 판정한 도구는 그 증거가 코드에서 해석될 때만 무해로 센다. 문서는 효과의 \emph{부재}를 입증할 수 없기 때문이다. 이 구분이 이 단계의 출력을 그럴듯한 것이 아니라 감사 가능한 것으로 만들며, 5절은 그중 얼마가 검사기를 통과하는지 측정한다.
% Summaries are produced by a language model that must cite \texttt{file:line} evidence for every claim, and are then filtered by a deterministic checker that re-reads the cited span in the fetched source. A claim whose citation does not resolve inside the fetched tree, or whose span does not contain the tool name or an identifier the rationale names, is kept but marked undetermined; the label survives, because an unverified claim must not lower an effect, but it no longer counts as verified. A tool the model does not judge at all is assigned HOSTEXEC, the least restrictive reading. A tool the model clears with no labels counts as cleared only when its evidence resolves in code: documentation cannot establish the \emph{absence} of an effect. This split is what makes the stage's output auditable rather than merely plausible, and Section~\ref{sec:eval} measures how much of it survives the checker.

실무적으로 중요한 세부가 둘 있다. 모델에게는 모든 줄에 실제 줄 번호를 붙인 소스를 보여준다. 줄 번호가 없으면 인용된 줄이 파일 뒤로 갈수록 어긋나고, 올바른 판정이 검증에 실패하기 때문이다. 또한 패키지 자신의 코드가 도구 이름을 전혀 언급하지 않는 경우 --- 구현이 의존성에 있는 래퍼 패키지가 그렇다 --- 그 이름을 언급하는 직접 의존성을 스크립트 실행을 끈 채 가져와 함께 보여준다. 파이프라인의 어느 지점에서도 제공자 코드는 실행되지 않는다.
% Two details matter in practice. The model is shown source with every line prefixed by its true line number, because without them cited lines drift with depth and correct judgements fail verification. And when a package's own code never mentions a tool name --- the case for wrapper packages whose implementation lives in a dependency --- the direct dependencies that do mention it are fetched and shown, with scripts disabled; provider code is never executed at any point in the pipeline.

\subsection{Repair: Minimum-cost Patch Synthesis}

\emph{Decide}는 설정이 지정한 값 수준 조건 --- 읽기 전용 모드, toolset 선택, 경로 root, origin 허용 목록 --- 을 적용한 뒤 설정이 유도한 surface에 대해 배포자의 정책을 평가하고, 금지된 흐름마다 그것을 증언하는 도구를 반환할 것이다. \emph{Repair}는 선언된 작업의 보존을 조건으로 사용 가능한 제어 수단 위에서 최소 비용 patch를 탐색하고, 후보 patch마다 다시 판정해 결과가 가정이 아니라 검증된 것이 되게 하며, patch를 설정 diff로 내보낼 것이다. 우리는 두 단계를 서버 통째 제거, 서버 모드만 사용하는 방식, 이름 기반 휴리스틱 거부 목록, 동일 정책 하의 실행 시점 집행과 비교해, patch 전후의 benign utility, 공격 하 utility, 표적 공격 성공률을 측정할 계획이다.
% \emph{Decide} will evaluate the deployer's policy over the surface induced by a configuration, after applying the value-level conditions that configuration sets --- read-only modes, toolset selections, path roots, origin allow-lists --- and return, for each forbidden flow, the tools that witness it. \emph{Repair} will search for a minimum-cost patch over the available controls subject to preserving the declared tasks, re-deciding after each candidate patch so that the result is verified rather than assumed, and will emit the patch as a configuration diff. We plan to evaluate both against whole-server removal, server modes alone, a name-based heuristic deny list, and run-time enforcement under the same policy, measuring benign utility, utility under attack and targeted attack success rate before and after the patch.

AgentDojo는 프롬프트 주입에 대한 에이전트 방어를 평가하는 환경으로, 업무용 메일과 일정과 드라이브를 다루는 workspace, 메신저를 다루는 slack, 예약을 다루는 travel, 계좌를 다루는 banking의 네 suite에 도구 74개와 사용자 과제 97개, 주입 과제 35개를 담고 있다. 하나의 \emph{보안 케이스}는 사용자 과제와 주입 과제를 짝지은 것으로, 공격자의 지시는 에이전트가 읽게 될 콘텐츠에 심기고 성공 여부는 결정적 Python 함수가 판정한다. 언어 모델 심판을 쓰지 않는 이유를 저자들이 밝혀 두었고 우리도 이를 따르는데, 공격이 충분히 성공적이면 평가 모델까지 탈취할 수 있기 때문이다. 다만 우리는 보안 케이스 949개 전부가 아니라 \textbf{909개}를 사용한다. \subsubsection{Baselines}

본 연구는 MCP 에이전트의 권한을 제한하는 선행연구인 AgentDojo~\cite{debenedetti2024agentdojo}, Progent~\cite{shi2025progent}, CaMeL~\cite{debenedetti2025defeating}을 베이스라인으로 삼아 평가를 수행한다. Fides~\cite{costa2025securing} 역시 같은 갈래의 선행연구이나, 공개된 저장소가 튜토리얼 노트북 하나여서 보고된 결과를 재현할 수 없기 때문에 제외하였다. 조합 검사 계열의 연구도 제외하였는데, 위험 여부를 판정할 뿐 설정을 바꾸지 않으므로 공격이 막혔는지와 작업이 유지되었는지로 채점하는 자리에 놓일 수 없기 때문이다. 우리가 선행연구들에서 선정한 베이스라인은 다음과 같다.
% This study evaluates against the prior work that narrows an MCP agent's privilege: AgentDojo~\cite{debenedetti2024agentdojo}, Progent~\cite{shi2025progent} and CaMeL~\cite{debenedetti2025defeating}. Fides~\cite{costa2025securing} belongs to the same line but is excluded, because its public repository is a single tutorial notebook from which the reported results cannot be reproduced. Set-level analyses are excluded as well: they judge whether a deployment is dangerous without changing its configuration, and so cannot be scored on whether an attack was stopped and the task preserved. The baselines we take from this prior work are the following.

\begin{itemize}
    \item \textbf{No Defense}~\cite{debenedetti2024agentdojo}: 방어를 두지 않은 에이전트로, 나머지 셋이 무엇을 줄였는지 재는 기준점이다.
    % \item \textbf{No Defense}~\cite{debenedetti2024agentdojo}: an agent with no defence at all, the reference against which the other three are measured.
    \item \textbf{Tool Filter}~\cite{debenedetti2024agentdojo}: AgentDojo가 함께 제공하는 방어다. 질의를 받으면 모델에게 그 작업에 필요한 도구만 고르게 한 뒤 나머지를 제거하며, 집행은 첫 호출 이전에 한 번 이루어진다.
    % \item \textbf{Tool Filter}~\cite{debenedetti2024agentdojo}: the defence AgentDojo ships. Given the query it asks the model to select only the tools the task needs and removes the rest, enforcing once before the first call.
    \item \textbf{Progent}~\cite{shi2025progent}: 사용자의 작업에서 도구 이름과 인자에 대한 기호 규칙을 LLM으로 생성하고 호출마다 그 규칙과 대조하며, 실행 중 새 정보가 들어오면 정책을 갱신한다.
    % \item \textbf{Progent}~\cite{shi2025progent}: has an LLM generate symbolic rules over tool names and arguments from the user's task, checks every call against them, and updates the policy as new information arrives.
    \item \textbf{CaMeL}~\cite{debenedetti2025defeating}: 권한 있는 LLM이 신뢰된 질의를 제한된 프로그램으로 옮기고 격리된 LLM이 신뢰할 수 없는 데이터를 해석하며, 전용 인터프리터가 값마다 능력을 추적해 도구 호출 시점에 정책을 집행한다.
    % \item \textbf{CaMeL}~\cite{debenedetti2025defeating}: a privileged LLM turns the trusted query into a restricted program while a quarantined LLM interprets untrusted data, and a custom interpreter tracks a capability per value and enforces policies at the point a tool is called.
\end{itemize}

\subsubsection{Environments}

본 연구는 GPT-4o를 사용한다. 네 베이스라인이 공통으로 사용한 모델일 뿐 아니라, 그들이 사용한 모델 가운데 지금도 API로 이용할 수 있는 유일한 모델이기 때문이다. Progent가 함께 보고한 Claude Sonnet~4와 Gemini~2.5 Flash, GPT-4.1, CaMeL이 사용한 Claude~3.5 Sonnet과 Gemini~2.5 Pro는 모두 제공자가 서비스를 종료하여 재현할 수 없다. 이 때문에 모델 세대에 따라 방어가 어떻게 달라지는지 보려면 새 모델을 우리가 선정해야 하므로, 현재 이용 가능한 최신 모델인 GPT-5.6-sol과 Claude Opus~5를 추가하였다. Progent는 에이전트와 정책 생성기 양쪽에, CaMeL은 권한 있는 LLM과 격리된 LLM 양쪽에 같은 모델을 사용하므로 우리도 그와 같이 맞추었다. 온도와 실행 횟수는 베이스라인이 설정한 방식을 그대로 따랐다. AgentDojo와 Progent, CaMeL은 모두 온도를 0으로 두고 보안 케이스마다 한 번씩만 실행하며 반복 실행을 하지 않는데, 이들 논문이 보고하는 구간 역시 반복 사이의 편차가 아니라 케이스 수에 대한 신뢰구간이다. 실험은 macOS~26.6, Apple~M1 Ultra(20코어), 64\,GB 메모리 환경에서 수행하였고, 모든 모델 호출이 제공자의 API를 거치므로 GPU는 사용하지 않는다. 벤치마크와 각 베이스라인은 공개 저장소를 고정된 리비전으로 받아 사용하였으며, 체크아웃에 가한 수정은 두 가지뿐이다. AgentDojo에는 모델 식별자를 등록하는 세 줄을 더하였고, CaMeL에는 지원하지 않는 상수를 만났을 때 오류 메시지를 만들면서 존재하지 않는 속성을 참조해 실행 전체가 중단되는 버그를 한 줄 고쳤다. 과제와 채점기, 공격, 정책 로직에는 손대지 않았다.
% This study uses GPT-4o. It is the model the four baselines share, and it is also the only model any of them used that a provider still serves: the Claude Sonnet~4, Gemini~2.5 Flash and GPT-4.1 that Progent additionally reports, and the Claude~3.5 Sonnet and Gemini~2.5 Pro that CaMeL uses, have all been retired and cannot be reproduced. Seeing how a defence moves across model generations therefore requires choosing new models ourselves, so we add the current GPT-5.6-sol and Claude Opus~5. Progent uses one model for both the agent and the policy generator, and CaMeL one for both the privileged and the quarantined LLM, and we match that. Temperature and the number of runs follow what the baselines set: AgentDojo, Progent and CaMeL all use a temperature of 0 and run each security case once without repetition, and the intervals their papers report are likewise confidence intervals over cases rather than spread between repetitions. The experiments were run on macOS~26.6 with an Apple~M1 Ultra (20 cores) and 64\,GB of memory; all model calls go through the providers' APIs, so no GPU is used. The benchmark and each baseline were taken from their public repositories at pinned revisions, and we made only two changes to those checkouts: three lines registering model identifiers in AgentDojo, and a one-line fix in CaMeL where the handler for an unsupported constant referenced a non-existent attribute while formatting its error message, aborting the whole run. No task, checker, attack or policy logic was touched.

\subsection{RQ1: How Much of the Effect Judgement Survives Re-checking?}

여기서는 하나의 질문을 던진다. \textbf{RQ1.} 모델의 효과 판정 가운데 얼마가 제공자의 소스에 대한 결정적 재검사를 통과하며, 어떤 제공자에서 이 절차가 실패하는가? 우리는 광고된 surface를 복원할 수 있었던, 가장 자주 설정되는 npm 및 PyPI 서버 34개, 총 433개의 광고된 도구를 대상으로, 고정된 rubric과 JSON 스키마를 사용하는 Claude Opus~5, 패키지당 400\,KB의 소스 예산, 그리고 4절에서 설명한 검사기로 프로파일을 만든다. 광고된 각 도구는 정확히 하나의 범주에 들어간다. 모델이 라벨을 주장했고 인용이 코드에서 해석된 경우(\emph{verified}), 문서에서만 해석된 경우(\emph{verified\_doc}), 해석되지 않은 경우(\emph{demoted}), 모델이 무해로 판정했고 코드 증거가 있는 경우(\emph{cleared verified}) 또는 없는 경우(\emph{cleared unverified}), 그리고 모델이 판정하지 않은 경우(\emph{unjudged})다. 광고된 surface에 없는 이름을 판정한 경우는 별도로 센다. 기준과 정의는 실행 전에 사전 등록했으며, 계획서가 정한 dry-run에서 발견된 측정 도구 변경은 모두 실행 이후가 아니라 이전에 기록했다.

Three servers account for most of the loss, and each fails for a structural reason rather than a labelling error. One ships a launcher and downloads a compiled binary, so its implementation is not in the package at all and all 68 of its citations point at documentation. One generates its tool names at start-up from an interface description, so the names occur nowhere in its source and no source file could be selected. One implements its tools in a minified bundle, where 13 of 35 citations name the first line of the bundle while the cited identifiers sit elsewhere. Restricted to the 27 servers where implementation code was available to read, the verified-claim rate is \textbf{90.7\%} (243 of 268). The four further servers that fall outside the usable set are not failures of the procedure: every one of their tools was cleared, in three cases entirely on code evidence, and the registered usability rule treats a server with no asserted claims as not usable.

\section{Threats to Validity}
\label{sec:threats}

\emph{코퍼스.} GitHub 코드 검색은 질의당 결과 수에 상한을 두고 표집이 아니라 관련도 순위로 반환하므로, 이 코퍼스는 배포의 무작위 표본이 아니다. 커밋된 설정은 사람들이 실제로 실행하는 설정과 다를 수도 있다. \emph{판정 대상 집합.} 효과는 가장 자주 설정되는 서버 17개(측정)와 34개(평가)에 대해서만 도출했으므로, 유병률 수치는 인기 서버로 구성된 설정을 설명하며 롱테일을 설명하지 않는다. \emph{위협 모델.} 유병률 수치는 최악 가정의 에이전트 아래에서 광고된 surface가 갖는 성질이다. 특정 배포가 공격을 당했다거나 공격이 성공한다고 주장하지 않으며, 악용 가능성 확인은 향후 과제다. \emph{검사기.} 검사기는 한 방향으로 엄격하고 다른 방향으로 느슨하다. 강등 81건 중 약 9건은 인용 구간에 해당 식별자가 더 긴 표현 안에 실제로 존재하지만 토큰 일치가 이를 놓친 경우이고, 반대로 코드로 검증된 판정 308건 중 4건은 네 글자 이하의 토큰에 기대고 있다. \emph{발췌.} 큰 파일에 대해서는 이름이 등장하는 지점 주변 창만 보여주므로, 큰 파일에 존재하는 도구 이름 11개는 모델에게 한 번도 보이지 않았다. 따라서 의존성 추적의 이득은 하한이다. \emph{범위.} 우리의 결론은 설정 파일이 선언하는 MCP 서버에 대한 것이며, 에이전트 스킬로 일반화하지 않는다. 스킬은 광고된 도구 목록을 갖지 않으므로 여기서 쓴 측정 단위가 그대로 적용되지 않는다. \emph{단일 모델.} 모든 요약은 한 시점의 한 모델에서 나왔다. 모델이나 시간에 따라 이 비율이 얼마나 달라지는지는 측정하지 않았다.
% \emph{Corpus.} GitHub's code search caps results per query and ranks rather than samples them, so the corpus is not a random sample of deployments; committed configurations may also differ from those people run. \emph{Adjudicated set.} Effects are derived for the 17 (measurement) and 34 (evaluation) most frequently configured servers, so the prevalence figures describe configurations built from popular servers, not the long tail. \emph{Threat model.} The prevalence figure is a property of the advertised surface under a worst-case agent; it does not assert that a deployment has been attacked or that an attack would succeed, and confirming exploitability is future work. \emph{Checker.} The checker is strict in one direction and loose in another: about 9 of 81 demotions cite spans that do contain the relevant identifier inside a longer expression that the token match misses, while 4 of 308 code-verified judgements rest on a token of four characters or fewer. \emph{Excerpts.} For large files the prompt shows windows around name occurrences, and 11 tool names present in large files were never shown, so the benefit we report from following dependencies is a lower bound. \emph{Scope.} Our conclusions concern the MCP servers a configuration file declares and do not generalise to agent skills, which have no advertised tool list and therefore no counterpart to the unit of measurement used here. \emph{Single model.} All summaries come from one model at one date; we have not measured how much the rate varies across models or over time.

\section{Related Work}
\label{sec:related}

\emph{아티팩트 하나를 검사하는 연구.} 도구 오염 탐지기는 광고된 설명에서 숨겨진 지시, 이름 가로채기, 유출 엔드포인트를 읽어낸다~\cite{jain2026detecting}. 신뢰할 수 있는 설명을 재생성해 이 벡터를 제거할 수 있고~\cite{ye2026trustdesc}, 벤치마크는 실제 서버에서 그런 공격의 성공률을 정량화하며~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}, 정적 분석은 서버 내부의 taint 계열 결함을 찾고~\cite{sun2026viper}, 동작 감사는 실행 중 도구를 관찰하며~\cite{tan2026sandscope}, 이들은 아티팩트를 그 자신의 manifest나 코드에 비추어 판단한다. 우리의 입력은 여러 아티팩트를 조합한 설정이고, 출력은 그 설정에 대한 변경이다.
% \emph{Vetting one artifact.} Tool-poisoning detectors read advertised descriptions for hidden instructions, shadowed names and exfiltration endpoints~\cite{jain2026detecting}; trusted descriptions can be regenerated to remove the vector~\cite{ye2026trustdesc}; benchmarks quantify how often such attacks succeed on real servers~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}; static analysis finds taint-style bugs inside a server~\cite{sun2026viper}; behavioural audit watches tools as they run~\cite{tan2026sandscope}; These judge an artifact against its own manifest or code. Our input is a configuration that composes several artifacts, and our output is a change to that configuration.

\emph{집합을 판단하는 연구.} lethal trifecta 프레이밍은 위험한 조합을 명명하고~\cite{willison2025lethal}, toxic-flow 분석은 정책을 위반할 도구 순서를 구성해 점수화하며~\cite{beurerkellner2025toxicflow}, 조합 정책은 누적된 노출로 다음 호출이 위반이 되면 세션을 취소하고~\cite{schneider2026securing}, 레지스트리 규모 조사는 일부 서버가 세 능력을 동시에 가진다고 보고한다~\cite{zhao2026parasites}. 우리는 판단하는 성질을 공유하되 모집단과 출력에서 다르다. 레지스트리 아티팩트가 아니라 사람들이 작성한 설정을 대상으로 측정하고, 판정이나 세션 범위의 제한이 아니라 patch를 반환한다.
% \emph{Judging a set.} The lethal-trifecta framing names the dangerous combination~\cite{willison2025lethal}; toxic-flow analysis instantiates and scores tool sequences that would violate a policy~\cite{beurerkellner2025toxicflow}; compositional policies revoke a session once accumulated exposure would make the next call a violation~\cite{schneider2026securing}; and a registry-scale census reports that some servers hold all three capabilities at once~\cite{zhao2026parasites}. We share the property being judged and differ in population and output: we measure it over configurations people wrote rather than over registry artifacts, and we return a patch rather than a verdict or a session-scoped restriction.

\emph{인접 생태계: 에이전트 스킬.} 에이전트 스킬은 MCP와 다른 메커니즘이다. 스킬은 지시문 파일과 선택적 스크립트의 묶음이며, 도구 목록을 협상하는 프로토콜이 없고 광고된 schema도 없다. 그럼에도 공급망 관점의 위험은 닮아 있어서, 스킬에 대해서도 건전한 능력 상한이 추상 해석으로 계산되고~\cite{bhardwaj2026formal}, 페이로드를 여러 스킬에 분산해 아티팩트 단위 검사기를 회피하는 공격이 제시되었고~\cite{zeng2026colluskill}, 대규모 측정으로 취약점 유병률과 자격증명 유출, 공급망 오염이 보고되었다~\cite{liu2026agent, holzbauer2026context, chen2026your, qu2026supply, liu2026not}. 우리 결과는 이 생태계로 그대로 옮겨지지 않는다. 우리의 측정 단위는 설정 파일이 선언한 MCP 서버와 그 서버가 광고한 도구이며, 스킬에는 대응하는 광고된 surface가 없기 때문이다.
% \emph{A neighbouring ecosystem: agent skills.} Agent skills are a different mechanism from MCP: a skill is a bundle of instruction files and optional scripts, with no protocol that negotiates a tool list and no advertised schema. The supply-chain risks nevertheless rhyme, and for skills a sound capability bound is computed by abstract interpretation~\cite{bhardwaj2026formal}, payloads are dispersed across skills to evade per-artifact scanners~\cite{zeng2026colluskill}, and large-scale measurement reports vulnerability prevalence, credential leakage and supply-chain poisoning~\cite{liu2026agent, holzbauer2026context, chen2026your, qu2026supply, liu2026not}. Our results do not transfer to that ecosystem unchanged: our unit of measurement is the MCP servers a configuration file declares and the tools those servers advertise, and a skill has no corresponding advertised surface.

\emph{실행 시점에 에이전트를 제약하는 연구.} 신뢰된 질의에서 제어 흐름과 데이터 흐름을 추출해 신뢰할 수 없는 데이터가 프로그램 흐름에 영향을 주지 못하게 하거나~\cite{debenedetti2025defeating}, 기밀성과 무결성 라벨을 호출 단위로 추적·집행하거나~\cite{costa2025securing}, 호출 단위 권한 정책으로 최소 권한을 강제하거나~\cite{shi2025progent}, 도달 가능성 위에서 능력을 가두는 cut을 계산하거나~\cite{xiong2026reachability}, 가드레일로 에이전트 루프를 감쌀 수 있다~\cite{murugan2026}. 이들은 질의나 호출 단위로 판단하고, 호스트를 교체하거나 계측해야 하며, 설치된 surface는 그대로 둔다. \textsc{Interlock}은 이들과 상호보완적이다. 질의가 실행되기 전에 기성 호스트가 광고하는 것을 좁히며, 한 배포가 둘을 함께 쓸 수 있다.
% \emph{Constraining the agent at run time.} Control and data flow can be extracted from the trusted query so that untrusted data cannot affect program flow~\cite{debenedetti2025defeating}; confidentiality and integrity labels can be tracked and enforced per call~\cite{costa2025securing}; per-call privilege policies enforce least privilege~\cite{shi2025progent}; a capability-confining cut can be computed over reachability~\cite{xiong2026reachability}; and guardrails can wrap the agent loop~\cite{murugan2026}. These decide per query or per call, require the host to be replaced or instrumented, and leave the installed surface untouched. \textsc{Interlock} is complementary: it narrows what a stock host advertises before any query runs, and a deployment can do both.

\emph{기능 제약 아래 권한을 줄이는 연구.} 브라우저 확장의 과다 권한은 선언된 manifest 권한을 코드가 실제로 호출하는 API와 비교해 탐지되고~\cite{cheng2026percheck}, 프로그램 debloating은 테스트 스위트를 계속 통과시키면서 아티팩트를 줄인다~\cite{heo2018effective, sharif2018trimmer}. Android의 앱 간 권한 유출에 대한 조합 분석은 설치된 집합을 분석하고 앱이 설치·갱신·삭제될 때 이를 다시 검사한다~\cite{bagheri2015covert, li2015iccta}. 우리 상황은 무엇을 바꿀 수 있는가에서 다르다. 아티팩트는 제3자의 것이라 우리가 고쳐 쓸 수 없으므로 축소는 배포의 설정에서 일어나며, 보존해야 할 성질은 아티팩트가 아니라 배포에 속한다.
% \emph{Reducing privilege under a functional constraint.} Over-privilege in browser extensions is detected by comparing declared manifest permissions against the API calls the code makes~\cite{cheng2026percheck}, and program debloating reduces an artifact while a test suite must keep passing~\cite{heo2018effective, sharif2018trimmer}. Compositional analysis of inter-application permission leakage on Android analyses the installed set and re-checks it when applications are installed, updated or removed~\cite{bagheri2015covert, li2015iccta}. Our setting differs in what may be changed: the artifact belongs to a third party and is not ours to rewrite, so the reduction happens in the deployment's configuration, and the property to preserve belongs to the deployment rather than to the artifact.

\section{Conclusion}
\label{sec:conclusion}

에이전트 도구 보안 연구는 아티팩트 단위로 성숙해 왔고 집합 단위 질문도 명명되고 탐지되었지만, 사용자가 실제로 바꿀 수 있는 대상인 설정에는 고유한 분석이 없었다. 우리는 그 설정 모집단을 측정해, 분석 가능한 설정의 84.1\%가 한 세션 안에서 비공개 데이터와 공격자가 통제하는 콘텐츠, 공격자가 읽을 수 있는 목적지에 닿으며, 그 전부에서 단일 서버로 충분하고, 존재하는 축소 수단은 대체로 쓰이지 않으며 주요 원인 서버에는 아예 없음을 확인했다. 우리는 설정에 대한 최소 권한 tool surface를 계산하는 \textsc{Interlock}을 제시하고 그 첫 단계를 구현했다. 모든 주장이 인용된 소스에 대해 재검사되는 효과 요약으로, 전체의 72.5\%가, 패키지가 실제로 실행하는 코드를 함께 배포하는 경우에는 90.7\%가 검사를 통과한다. 실무적 함의는 두 가지다. 이 층위의 해법은 설정에 속하며, 사용자가 설치한 것의 대부분은 이미 내려받은 코드만으로 판정할 수 있다.
% Research on agent tool security has matured artifact by artifact, and the set-level question has been named and detected, yet the object a user can actually change --- the configuration --- has had no analysis of its own. We measured that configuration population and found that 84.1\% of the analysable configurations reach private data, attacker-controlled content and an attacker-readable destination in a single session, that a single server suffices in every such case, and that the narrowing controls which exist are largely unused and for the main offenders absent. We presented \textsc{Interlock}, which computes a least-privilege tool surface for a configuration, and implemented its first stage: effect summaries whose every claim is re-checked against the cited source, of which 72.5\% survive overall and 90.7\% survive where a package actually ships the code it runs. The practical reading is that the remedy for this layer belongs in the configuration, and that most of what a user installs can be judged from the code they already downloaded.
