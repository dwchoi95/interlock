\section{Introduction}
\label{sec:intro}

에이전트가 외부 도구를 받아오는 표준은 MCP(Model Context Protocol)다~\cite{gaire2026systematization}. 사용자는 설정 파일에 서버를 적고, 서버마다 그것을 실행할 명령, 서버가 받을 자격증명, 그리고 (일부 서버는) 어떤 도구를 광고할지 정하는 플래그를 함께 적는다. 그러면 호스트가 서버를 띄우고 도구 목록을 받아, 각 도구의 이름과 설명, 스키마를 모델에게 보여준다. 이렇게 한 세션에 모인 도구 전부를 그 배포의 \emph{tool surface}, 곧 모델이 부를 수 있는 도구의 집합이라 부른다. 이 방식은 이미 굳어졌다. 실제 애플리케이션 1,723개 중 85.2\%가 서버 목록을 파일로 두는 반면, 도구 호출을 멈추고 사용자 승인을 받는 차단형 게이트를 두는 것은 37.2\%뿐이다~\cite{majeed2026empirical}. 서버 한 줄을 적으면, 대개 그 서버의 도구는 모델이 부르기만 하면 실행된다.
% An LLM agent obtains external tools mainly through the Model Context Protocol (MCP)~\cite{gaire2026systematization}. A user lists servers in a configuration file, giving for each the command that starts it, the credentials it receives and, for some servers, flags that decide which of its tools are advertised. The host then starts each server, retrieves its tool list, and shows the model each tool's name, description and schema. We call the tools assembled for one session the deployment's \emph{tool surface}, the set of tools the model may call. This arrangement is settled: of 1,723 real applications, 85.2\% keep their server list in a file, while only 37.2\% put a blocking approval gate in front of a tool call~\cite{majeed2026empirical}. Listing one server therefore usually means its tools run on the model's call alone.

이 층위를 보호하는 연구는 세 갈래다. \emph{개별 검사}는 도구 하나 또는 서버 하나를 놓고 위험한지를 판정해, 광고된 설명의 숨은 지시와 이름 가로채기, 서버 구현 안의 결함, 실행 중의 이상 동작을 찾아낸다~\cite{jain2026detecting, ye2026trustdesc, wang2026mcptox, sun2026viper, tan2026sandscope}. \emph{조합 검사}는 도구의 능력 라벨을 받아, 신뢰할 수 없는 콘텐츠와 비공개 데이터, 그리고 공격자가 읽을 수 있는 목적지가 한 세션에 함께 모이는 조합을 위험으로 지목한다~\cite{willison2025lethal, beurerkellner2025toxicflow, schneider2026securing}. \emph{권한 제한}은 사용자의 작업에서 도구 권한 정책을 만들어 호출마다 집행한다~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}.
% Much research protects this layer, and it falls into three strands. \emph{Per-artifact vetting} judges one tool or one server dangerous or not, finding hidden instructions and shadowed names in advertised descriptions, defects inside a server implementation, and anomalous behaviour at run time~\cite{jain2026detecting, ye2026trustdesc, wang2026mcptox, sun2026viper, tan2026sandscope}. \emph{Set-level analysis} takes the tools' capability labels and names as dangerous the combination in which untrusted content, private data and a destination the attacker can read meet in one session~\cite{willison2025lethal, beurerkellner2025toxicflow, schneider2026securing}. \emph{Privilege narrowing} derives a tool-privilege policy from the user's task and enforces it at every call~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}.

실제 배포에서는 그 전제가 성립하지 않는다. 그림~\ref{fig:example}은 우리가 다루는 상황으로 MCP를 이용하여 자기 저장소의 열린 이슈를 정리하는 과정을 보여준다. 먼저 \stepnum{1}에서 개발자가 코딩 에이전트에 GitHub MCP 서버 하나를 붙인다. \stepnum{2}에서 호스트가 그 서버에 도구 목록을 요청하는데, 설정에 적힌 것은 서버 한 줄이지만 돌아오는 도구는 우리가 계측한 버전 기준 26개이고 모두 모델이 부를 수 있다. 이 가운데 셋이 모이면 유출 경로가 된다. \stepnum{3}의 \texttt{list\_issues}는 누구나 쓸 수 있는 공개 이슈를 컨텍스트로 들여오고, \stepnum{4}의 \texttt{get\_file\_contents}는 같은 토큰으로 비공개 저장소를 읽으며, \stepnum{5}의 \texttt{add\_issue\_comment}는 그 내용을 공격자가 읽을 수 있는 공개 이슈에 쓴다. 공격자가 공개 이슈에 지시문을 심어 두면, 에이전트는 그 이슈를 읽다가 지시를 따른다. 이런 경로는 손대지 않은 GitHub MCP 서버 하나만 연결한 상태에서 실제로 시연되었다~\cite{milanta2025github}. 그런데 \emph{개별 검사}는 \stepnum{3}과 \stepnum{4}, \stepnum{5}를 하나씩 보기 때문에 여기서 아무것도 지목하지 않는다~\cite{jain2026detecting, sun2026viper, tan2026sandscope}. \emph{조합 검사}는 셋이 함께 쓰일 때를 보므로 이 경로를 정확히 지목할 수 있다~\cite{beurerkellner2025toxicflow, schneider2026securing}. 그러나 거기서 멈춘다. 이 배포가 위험하다고 판정할 뿐 무엇을 꺼야 하는지는 말하지 않으므로, 사용자에게 남는 선택은 경고를 무시하거나 서버를 통째로 지우는 것뿐이다. 대책이 될 수 있는 것은 \emph{권한 제한}뿐이다. 작업에서 정책을 만들어 \stepnum{4}를 끄는 데까지 간다~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}. 다만 그러려면 \stepnum{4}가 비공개 데이터에 닿는다는 것을 먼저 알아야 하는데, 그 정보는 제공자가 쓴 이름과 설명에 없고 기계가 읽을 형태로 어디에도 선언되어 있지 않다. 이 예시가 드러내는 것은 일반적인 한계다. 권한 제한은 도구가 무엇에 닿는지를 제공자가 쓴 글에서 읽고, 그 글이 실제 구현과 맞는지는 아무도 확인하지 않는다. 그래서 글이 어긋나면 정책도 어긋나는데, 어긋났다는 사실이 드러나지 않는다. 비공개 데이터에 닿는 도구를 닿지 않는다고 믿고 열어 둔 채로 최소 권한을 집행했다고 보고하게 되며, 틀린 정책과 맞는 정책이 구별되지 않는다. 더구나 그 글은 우리 위협 모델에서 공격자가 쓸 수 있는 것이어서, 설명을 고치면 정책이 따라 바뀐다. 게다가 안다고 해도 끝이 아니다. 이 경로는 세 도구 가운데 어느 하나만 꺼도 끊어지므로, 무엇을 끌지는 \stepnum{6}의 선언된 작업이 정한다. 그 작업이 열린 이슈를 정리해 요약을 코멘트로 남기는 것이라면 \stepnum{3}과 \stepnum{5}는 작업이 쓰는 도구여서 끌 수 없고, \stepnum{4}만 끌 수 있다. 무엇을 끌지는 위험의 성질이 아니라 배포가 선언한 작업이 정하는 것이다. 그래서 도구를 하나씩 끄는 수단이 있고 정책을 만들 줄 아는 연구가 있어도, \stepnum{7}과 같은 정밀한 변경을 계산해 주는 것은 없다.
% In a real deployment that presupposition does not hold. Figure~\ref{fig:example} shows the situation we address: triaging the open issues of one's own repository through MCP. In \stepnum{1} a developer connects one GitHub MCP server to a coding agent. In \stepnum{2} the host asks that server for its tool list; the configuration names a single server, but 26 tools come back in the version we measured, every one callable by the model. Three of them form a leak. \texttt{list\_issues} in \stepnum{3} brings a publicly writable issue into the context, \texttt{get\_file\_contents} in \stepnum{4} reads a private repository with the same token, and \texttt{add\_issue\_comment} in \stepnum{5} writes the result back to the public issue where the attacker can read it. If the attacker has planted instructions in a public issue, the agent follows them while reading it. A path of this shape has been demonstrated with a single unmodified GitHub MCP server~\cite{milanta2025github}. \emph{Per-artifact vetting} looks at \stepnum{3}, \stepnum{4} and \stepnum{5} one at a time and so flags nothing here~\cite{jain2026detecting, sun2026viper, tan2026sandscope}, because none of the three is malicious or defective --- the authors who reported the demonstration say as much, that it is ``not a flaw in the server code''. \emph{Set-level analysis} looks at the three used together and can name this path exactly~\cite{beurerkellner2025toxicflow, schneider2026securing}, but it stops there: it judges the deployment dangerous without saying what to switch off, leaving the user to dismiss the warning or delete the server whole. The only strand that can act is \emph{privilege narrowing}, which derives a policy from the task and goes as far as denying \stepnum{4}~\cite{shi2025progent, debenedetti2025defeating, costa2025securing}. To do that, though, it must first know that \stepnum{4} reaches private data, and that is not in the names and descriptions the provider wrote, nor declared anywhere else a machine can read. What the example exposes is a general limitation: privilege narrowing reads what a tool reaches off prose the provider wrote, and nothing checks that prose against the implementation. When the two diverge the policy diverges with them, and the divergence does not show. A tool that reaches private data is left open in the belief that it does not, while the system reports that least privilege is being enforced, so a wrong policy is indistinguishable from a right one. That prose is also, under our threat model, attacker-writable: edit the description and the policy follows. Even knowing what a tool reaches is not enough: switching off any one of the three tools breaks it, so which one to switch off is decided by the declared task in \stepnum{6}. If that task is to triage the open issues and comment a summary, then \stepnum{3} and \stepnum{5} are tools the task uses and cannot go, leaving \stepnum{4} as the only edge that may. What to switch off is decided by the deployment's declared task rather than by the nature of the danger. So although the means to switch off one tool at a time exists and research knows how to produce a policy for it, nothing computes a precise change like~\stepnum{7}.

이 논문에서 우리는 \textsc{Interlock}을 제시한다. 도구가 무엇에 닿는지를 제공자가 쓴 글이 아니라 서버의 소스 코드에서 회수하되 모든 주장을 기계적으로 재검사하고, 그렇게 얻은 효과 라벨을 소비하는 두 집행 규칙으로 그 라벨이 실제로 쓸 수 있는 정보임을 보이는 접근이다. \emph{Summarize}는 신뢰도 순으로 정렬한 증거에서 도구마다 어떤 효과에 닿는지를 판정하고, 판정마다 그것을 뒷받침하는 코드 위치를 남긴다. 이 요약은 그 자체로 앞 문단의 빈자리를 채우는 산출물이며, 런타임 최소 권한 시스템이 사람 손으로 채우던 라벨을 대신할 수 있다. 우리는 이어서 그 라벨만을 입력으로 받는 두 규칙을 둔다. \emph{Narrow}는 에이전트의 첫 턴 이전에, 시스템 메시지와 사용자의 요청만 보는 LLM이 그 작업에 필요한 WRITE 도구를 지목하게 하여 허용 목록을 만든다. 목적지나 값 인자를 가진 WRITE만 게이트하고 READ 도구와 부수 효과뿐인 도구는 게이트하지 않으며, 이 LLM은 도구 출력을 결코 보지 않으므로 주입이 목록을 넓힐 수 없다. 허용 목록 밖의 WRITE는 surface에서 제거하지 않고 보이는 채로 두되 호출을 거부한다. 같은 라벨 위에서 설정 시점의 결정도 내릴 수 있다. 그림의 \stepnum{6}이 \stepnum{3}과 \stepnum{5}를 쓰는 작업이면 \stepnum{4}를 끄는 것이 그 결정이고, 호스트가 도구 단위 거부 항목을 제공하면 \stepnum{7}과 같은 설정 patch로 내보낼 수 있다. 이 논문이 평가하는 것은 호출 단위의 두 규칙이다. \emph{Guard}는 그 아래 층위를 맡는다. 목적지 인자를 가진 모든 호출에서 인자 값마다 그것이 어디서 왔을 수 있는지 --- 사용자의 요청, 앞선 결과의 구조화된 필드, 앞선 쓰기의 결과, 또는 공격자가 쓸 수 있는 텍스트 --- 를 추적해, 공격자 텍스트에서만 나올 수 있는 값이면 호출을 거부한다. 식별자는 동등 비교로, 산문은 포함 비교로 출처를 정하고, 공격자가 이름 지은 식별자에는 둘 다 적용한다. 거부문은 어느 인자나 값이 걸렸는지 말하지 않고, 도구 결과 안의 지시는 사용자의 것이 아니니 사용자의 작업을 계속하라고만 말한다. 어느 도구가 무엇을 쓰고 어느 필드가 주입 가능한지는 \emph{Summarize}의 라벨이 정하며, 두 규칙은 모델과 도구 사이의 호출 경로에서만 동작한다.
% In this paper we present \textsc{Interlock}, an approach that recovers what a tool reaches from the server's source code rather than from prose the provider wrote, re-checks every claim mechanically, and then shows that the resulting effect labels are usable information through two enforcement rules that consume them. \emph{Summarize} judges, from evidence ranked by trust, which effects each tool can reach, and records for every judgement the code location that supports it. These summaries are themselves the artifact the previous paragraph finds missing, and they can stand in for the labels that run-time least-privilege systems fill in by hand. We then add two rules whose only input is those labels. \emph{Narrow} builds an allow-list before the agent's first turn: an LLM that sees only the system message and the user's request names the WRITE tools the task needs. Only WRITEs with a destination or value argument are gated, READ tools and tools with incidental side effects never are, and since that LLM never sees a tool output an injection cannot widen the list. A WRITE outside the list is not removed from the surface; it stays visible and a call to it is refused. The same labels also support a configuration-time decision: when \stepnum{6} in the figure is a task that uses \stepnum{3} and \stepnum{5}, that decision is to switch off \stepnum{4}, and where a host exposes per-tool deny entries it can be emitted as a configuration patch like \stepnum{7}. What this paper evaluates is the two per-call rules. \emph{Guard} works one level below. At every call with a destination argument it traces each value to where it could have come from --- the user's request, a structured field of an earlier result, the result of an earlier write, or attacker-writable text --- and refuses the call if the value can only have come from attacker text. Identifiers are matched by equality and prose by containment, and an attacker-named identifier gets both. The refusal names no argument or value; it says only that instructions inside tool results are not from the user and that the agent should continue the user's task. Which tools write, and which fields are injectable, is decided by \emph{Summarize}'s labels, and both rules act only on the call path between the model and the tools.

핵심 난점은 그 정보가 선언되어 있지 않다는 것이다. 효과를 코드에서 읽어내야 하는데, 두 길 모두 쉽지 않다. 공개 패키지를 전부 정적 분석으로 따라가면 규모가 맞지 않고, 언어 모델에 읽히면 그 판정을 무엇으로 믿느냐가 남는다. 우리는 \emph{신뢰도 순위 요약과 결정적 재검사}를 묶어 이를 푼다. 모델이 서버의 소스를 읽고 도구별 효과를 판정하되 주장마다 \texttt{file:line} 증거를 달게 하고, 결정적 검사기가 가져온 소스에서 그 줄을 다시 읽어 확인되지 않는 주장을 걸러낸다. 확인되지 않은 주장은 버리지 않고 ``미확인''으로 표시해 라벨을 지키며, 모델이 판정하지 않은 도구에는 가장 보수적인 값을 준다. 문서만 근거로 한 ``무해'' 판정은 무해로 세지 않는다. 문서는 효과가 없다는 것을 증명하지 못하기 때문이다. 그래서 출력은 그럴듯한 요약이 아니라, 독자가 코드 한 줄까지 되짚을 수 있는 감사 가능한 기록이 된다.
% The central difficulty is that this information is not declared, so effects must be read out of code, and neither route is easy: following every published package by static analysis does not scale, and handing the code to a language model leaves open what makes its judgement trustworthy. We solve this by pairing \emph{trust-ranked summarisation with deterministic re-checking}. The model reads the server's source and judges each tool's effects, but must cite \texttt{file:line} evidence for every claim, and a deterministic checker re-reads the cited span in the fetched source and drops what it cannot confirm. An unconfirmed claim is kept and marked undetermined rather than discarded; a tool the model does not judge takes the most conservative value; and a clearance based only on documentation does not count, because documentation cannot show that an effect is absent. The output is thus an auditable record a reader can trace to a line of code, not a plausible summary.

집행 쪽의 난점은 도구 단위가 너무 굵다는 것이다. 라벨이 모두 맞고 작업이 쓰는 도구를 정확히 안다고 해도, 도구를 켜고 끄는 규칙은 작업이 쓰는 도구로 수행되는 공격을 가르지 못한다. 작업이 이메일을 보내는 것인데 주입이 공격자에게도 보내라고 하는 식이어서, 도구 수준 규칙은 각 작업의 도구를 완벽히 알아도 AgentDojo에서 targeted ASR 4.18\% 아래로 내려갈 수 없다(\S\ref{sec:prelim:goal}). \emph{Guard}가 도구가 아니라 인자 값의 출처를 보는 이유가 이것이다. 이메일 주소나 채널 이름 같은 목적지가 사용자의 요청이나 앞선 결과의 구조화된 필드에서 왔다면 통과하고, 도구 결과의 산문 안에서만 나왔다면 오염된 것으로 보아 거부한다. 거부의 형태도 결과를 가른다. 허용 목록 밖의 도구를 surface에서 제거하면 에이전트는 없는 도구를 부르지 않는 대신 작업에서 이탈하고, 같은 도구를 보이게 두고 호출을 거부하면 거부문을 읽고 작업으로 돌아온다. 부재는 침묵이고 거부는 신호여서, 이 변경 하나로 utility under attack이 54.9\%에서 61.3\%로 올랐다.
% The difficulty on the enforcement side is that a tool is too coarse a unit. Even with every label right and the task's tools known exactly, a rule that switches tools on and off cannot separate an attack that is carried out with the tools the task itself uses. The task sends an email and the injection says to send it to the attacker too, so a tool-level rule cannot go below a targeted ASR of 4.18\% on AgentDojo even with perfect knowledge of each task's tools (\S\ref{sec:prelim:goal}). This is why \emph{Guard} looks at the provenance of an argument value rather than at the tool. A destination such as an email address or a channel name passes if it came from the user's request or from a structured field of an earlier result, and is refused as tainted if it appears only inside the prose of a tool result. The form of the refusal decides the outcome as well. Remove a tool outside the allow-list from the surface and the agent never calls the missing tool, but drifts off the task; leave the same tool visible and refuse the call, and the agent reads the refusal and returns to the task. Absence is silence and refusal is a signal: this one change lifted utility under attack from 54.9\% to 61.3\%.

GPT-4o는 온도 0에서도 결정적이지 않으므로, 모든 수치는 반복 실행의 평균으로 보고한다.
% We evaluate \textsc{Interlock} in two places (\S\ref{sec:eval}). \emph{Summarize} is applied to the 34 servers most frequently declared in public configurations and their 433 tools, and 72.5\% of the model's judgements survive deterministic re-checking overall, 90.7\% where implementation code is distributed. 호스트 애플리케이션 --- IDE 어시스턴트, 데스크톱 에이전트, 코딩 에이전트 --- 은 설정 파일에 명시된 각 Model Context Protocol 서버를 실행하고 \texttt{tools/list}로 도구 목록을 요청한 뒤, 반환된 이름과 설명, JSON 스키마를 모델의 컨텍스트에 넣는다. 한 세션에서 이렇게 모인 도구 전체를 그 배포의 \emph{tool surface}라 부른다. 이 구조의 세 가지 성질이 이후 논의를 이끈다. surface는 개별 제공자가 아니라 사용자의 설정이 결정한다. surface 위의 모든 도구는 호출 가능하다. 도구 선택은 광고된 텍스트를 읽은 모델이 하기 때문이다. 그리고 surface는 고정되어 있지 않다. 호스트는 대개 버전을 고정하지 않은 패키지 지정으로 서버를 실행하므로, 도구 뒤의 코드는 사용자가 아무 행동을 하지 않아도 세션 사이에 바뀔 수 있다. 실제로 \S\ref{sec:prelim:limitation}에서 수집한 코퍼스를 보면 stdio 항목의 91.3\%가 버전을 명시하지 않는다(표~\ref{tab:corpus}).
% A host application --- an IDE assistant, a desktop agent, a coding agent --- starts each Model Context Protocol server named in a configuration file, asks it for its tool list over \texttt{tools/list}, and places the returned names, descriptions and JSON schemas into the model's context. The tools thus assembled for one session are what we call the deployment's \emph{tool surface}. Three properties of this arrangement drive the rest of the paper. The surface is decided by the user's configuration rather than by any single provider. Every tool on it is callable, because tool choice is made by the model from the advertised text. And the surface is not fixed: hosts commonly launch servers from an unpinned package specification, so the code behind a tool can change between sessions without any action by the user --- in the corpus collected in \S\ref{sec:prelim:limitation}, 91.3\% of stdio entries name no version (Table~\ref{tab:corpus}).

도구가 광고하는 것은 이름과 설명, 인자의 JSON 스키마, 그리고 선택적인 annotation이다. 이 가운데 무엇도 그 도구가 무엇에 닿는지를 말해 주지 않는다. 스키마는 인자의 모양만 정하고, 설명은 제공자가 자유롭게 쓴 산문이며, annotation에 대해서는 프로토콜 명세 자신이 신뢰된 서버에서 온 것이 아닌 한 믿지 말 것을 클라이언트에 요구한다. 본 논문은 도구가 닿는 대상을 네 가지 \emph{효과}로 나눈다.
% What a tool advertises is a name, a description, a JSON schema for its arguments and optional annotations. None of these states what the tool reaches: a schema fixes the shape of the arguments, a description is prose the provider writes freely, and for annotations the protocol specification itself requires clients to treat them as untrusted unless they come from a trusted server. This paper divides what a tool reaches into four \emph{effects}.

\begin{itemize}
    \item \textbf{SECRET}: 사용자의 비공개 데이터를 읽는다. 그림~\ref{fig:example}의 \texttt{get\_file\_contents}가 비공개 저장소를 읽는 것이 여기 해당한다.
    % \item \textbf{SECRET}: reads the user's private data, as \texttt{get\_file\_contents} reads a private repository in Figure~\ref{fig:example}.
    \item \textbf{UNTRUSTED}: 공격자가 쓸 수 있는 콘텐츠를 컨텍스트로 들여온다. 공개 이슈 본문을 읽어 오는 \texttt{list\_issues}가 그렇다.
    % \item \textbf{UNTRUSTED}: brings content an attacker can write into the context, as \texttt{list\_issues} brings in the body of a public issue.
    \item \textbf{SINK}: 공격자가 읽을 수 있는 곳에 쓴다. \texttt{add\_issue\_comment}가 공개 이슈에 코멘트를 남기는 것이 그렇다.
    % \item \textbf{SINK}: writes where an attacker can read, as \texttt{add\_issue\_comment} leaves a comment on a public issue.
    \item \textbf{HOSTEXEC}: 호스트에서 코드를 실행한다. 호스트가 닿을 수 있는 모든 것에 닿으므로 나머지 셋을 함의한다.
    % \item \textbf{HOSTEXEC}: executes code on the host. It implies the other three, since it reaches everything the host can reach.
\end{itemize}

우리는 에이전트가 자신이 읽은 콘텐츠 안의 지시를 따른다고 가정한다. 이는 lethal trifecta 프레이밍~\cite{willison2025lethal}과 toxic-flow 분석이 전제하는 가정이며, 이 층위에 대해 공개된 공격들이 실제로 악용하는 가정이다~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. 공격자는 임의의 웹 호스트와 콘텐츠를 통제하고, 여러 사람이 쓸 수 있거나 제3자가 제공하는 출처의 콘텐츠 --- 공개 이슈와 댓글, 저장소 내용, 커뮤니티 문서와 레지스트리, 검색 결과 --- 도 통제한다. 공격자는 사용자의 로컬 파일이나 사용자 계정에 담긴 데이터를 통제하지 못하며, 설치된 서버를 수정하지도 못한다. 공격자는 자신이 통제하는 호스트와 공개된 모든 것을 읽을 수 있다. 이 가정 아래에서, 어떤 배포의 surface가 한 세션 안에서 SECRET과 UNTRUSTED와 SINK에 모두 닿을 때 그 배포는 위험하다.
% We assume an agent that follows instructions found in the content it reads, the assumption under which the lethal-trifecta framing~\cite{willison2025lethal} and toxic-flow analysis are stated and which published attacks on this layer exploit~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. The attacker controls arbitrary web hosts and content, and content in multi-writer or third-party sources: public issues, comments and repository content, community documentation and registries, search results. The attacker does not control the user's local files or the data held in the user's own accounts, and does not modify the installed servers. The attacker can read hosts they control and anything published publicly. Under these assumptions a deployment is dangerous when its surface reaches SECRET, UNTRUSTED and SINK in the same session.

% To our knowledge one attempt supplies that knowledge for real servers. \texttt{mcp-sec-audit} extracts capability categories with a rulebook of keywords and regular expressions, and its authors report detecting 2 of 2 on Python servers against 0 of 7 on JavaScript ones~\cite{huang2026auditing}. Yet the servers people actually declare are mostly npm: in the corpus of Table~\ref{tab:corpus}, collected from public configurations, there are 22,010 npm entries against 3,156 PyPI ones. The tool does not work on the ecosystem where the problem actually lives.

\subsection{Goal}
\label{sec:prelim:goal}

이 논문의 목표는 실제 MCP 서버의 도구마다 무엇에 닿는지를, 제공자가 쓴 글이 아니라 배포된 코드에서, 독자가 한 줄까지 되짚을 수 있는 형태로 회수하는 것이다. 그렇게 얻은 효과 요약은 \S\ref{sec:prelim:limitation}의 시스템들이 사람 손으로 채우거나 가정으로 두던 자리를 대신할 수 있고, 설정 시점에 직접 쓰일 수도 있다. 효과를 코드에서 직접 회수하는 것이 남은 길인데, 여기에 두 가지 어려움이 있다. 첫째, 공개된 패키지를 전부 정적 분석으로 따라가는 것은 규모가 맞지 않는다. 서버는 TypeScript와 Python, Go, Rust 등으로 작성되고, 번들이나 minify된 형태로, 또는 바이너리를 내려받는 실행기로 배포되며, 얇은 wrapper가 실제 구현을 의존성에 두기도 한다. \texttt{mcp-sec-audit}이 JavaScript에서 멈춘 지점이 바로 여기다. 둘째, 언어 모델에 코드를 읽히면 규모 문제는 사라지지만 그 판정을 무엇으로 믿을지가 남는다. 모델은 읽지 않은 것을 그럴듯하게 서술할 수 있고, 판정 대상 자체가 공격자가 쓸 수 있는 텍스트를 포함한다.
% The goal of this paper is to recover, for each tool of a real MCP server, what that tool reaches --- from the code that is distributed rather than from prose the provider wrote, and in a form a reader can trace to a line. Such summaries can stand in for what the systems of \S\ref{sec:prelim:limitation} fill in by hand or leave as an assumption, and can also be used directly at configuration time. Recovering the effects from code is what remains, and two things make it hard. First, following every published package by static analysis does not scale: servers are written in TypeScript, Python, Go and Rust, are shipped bundled, minified or as launchers that download a binary, and thin wrappers leave the real implementation in a dependency --- which is exactly where \texttt{mcp-sec-audit} stops on JavaScript. Second, handing the code to a language model removes the scale problem but leaves the question of what makes its judgement trustworthy: a model can describe plausibly what it has not read, and the object being judged itself contains text an attacker can write.

회수한 라벨은 집행되어야 하는데, 도구 단위의 집행으로는 충분하지 않다. 도구 수준의 거부 목록은 작업에 필요 없는 도구를 끄는 것이므로, 주입된 호출이 작업 자체가 필요로 하는 도구를 쓰면 그것을 정당한 호출과 구별하지 못한다. 사용자가 이메일을 보내라고 지시했고 주입이 공격자에게도 보내라고 말하면 두 호출은 같은 도구를 쓴다. 표~\ref{tab:adrun}의 무방어 궤적을 다시 재생하면 성공한 공격 413건 가운데 38건이 작업이 필요로 하는 도구만으로 수행되며, 따라서 각 작업의 도구를 완벽히 안다 해도 도구 수준 거부 목록의 targeted ASR은 이 벤치마크에서 4.18\% 아래로 내려갈 수 없다. 이는 Progent가 실제로 도달한 값보다 높다. 그러므로 집행은 어느 도구를 허용할지에 더해, 호출마다 그 목적지 인자의 값이 어디에서 왔는지를 판정해야 하고, 라벨은 도구의 효과와 함께 어느 인자가 목적지인지를 담아야 한다.
% The recovered labels also have to be enforced, and enforcement at the granularity of a tool is not enough. A tool-level deny-list switches off the tools a task does not need, so when an injected call uses a tool the task itself needs, the list cannot separate it from the legitimate call: the user asks for an email to be sent and the injection says to send it to the attacker as well, and both calls use the same tool. Replaying the undefended trajectories of Table~\ref{tab:adrun}, 38 of the 413 successful attacks are carried out entirely with tools the task needs, so even with perfect knowledge of each task's tools a tool-level deny-list cannot bring targeted ASR below 4.18\% on this benchmark --- above what Progent actually reaches. Enforcement therefore has to decide, beyond which tools to admit, at every call where the value of its destination argument came from, and the labels have to carry, along with a tool's effect, which of its arguments is a destination.


\section{Our Approach}
\label{sec:approach}

\subsection{Overview}
\label{sec:approach:overview}

\textsc{Interlock}은 설정과 사용자의 작업을 입력으로 받는다. 설정은 호스트가 띄울 서버와 그 서버들이 유도하는 tool surface를 정하고, 작업은 그 surface 가운데 무엇이 쓰여도 되는지를 정한다. 절차는 세 단계다. \emph{Summarize}는 서버의 소스 코드에서 도구별 효과 요약을 도출하고, 모든 주장을 인용된 \texttt{file:line}에 대해 다시 검사한다. 나머지 두 단계는 그 라벨을 소비하는 집행 규칙이다. \emph{Narrow}는 에이전트의 첫 턴 이전에 작업만 보고 그 작업이 필요로 하는 WRITE 도구 --- 상태를 바꾸거나 데이터를 내보내는 도구 --- 의 허용 목록을 만들고, 목록 밖의 WRITE 호출을 거부한다. \emph{Guard}는 목적지 인자를 가진 모든 호출에서 각 값의 출처를 추적해, 공격자가 쓸 수 있는 텍스트에서만 나올 수 있는 값을 가진 호출을 거부한다. 두 규칙이 요약에서 읽는 것은 도구가 WRITE인지와 어느 인자가 목적지나 값인지, 결과의 어느 필드가 공격자가 쓸 수 있는 텍스트(UNTRUSTED)이고 어느 필드가 시스템이 등록한 식별자인지이며, 도구의 설명은 어느 규칙도 읽지 않는다. 세 단계는 모두 구현되어 있다. \emph{Summarize}는 실제 MCP 서버를 대상으로 평가하고(\S\ref{sec:rq1}), \emph{Narrow}와 \emph{Guard}는 선행 시스템들이 공유하는 AgentDojo 위에서 평가하는데, 거기서 두 규칙이 읽는 라벨은 모델이 도구 코드에서 분류하고 적대적으로 재검사한 것이다(\S\ref{sec:rq2}).
% \textsc{Interlock} takes a configuration and the user's task. The configuration fixes the servers the host will start and the tool surface they induce; the task fixes which of that surface may be used. It proceeds in three stages. \emph{Summarize} derives a per-tool effect summary from the server's source code and re-checks every claim against the \texttt{file:line} it cites. The other two stages are enforcement rules that consume those labels. \emph{Narrow} builds, before the agent's first turn and from the task alone, an allow-list of the WRITE tools --- the tools that change state or send data --- the task needs, and refuses a call to any WRITE outside it. \emph{Guard} traces, at every call that has a destination argument, where each value could have come from, and refuses a call whose value could only have come from text an attacker can write. What the two rules read from a summary is whether a tool is a WRITE and which of its arguments are destinations or values, which fields of its result are attacker-writable text (UNTRUSTED) and which hold identifiers the system registered; neither rule reads the tool's description. All three stages are implemented. \emph{Summarize} is evaluated on real MCP servers (\S\ref{sec:rq1}); \emph{Narrow} and \emph{Guard} are evaluated on AgentDojo, the benchmark the prior systems share, where the labels the two rules read were classified by a model from the tool code and adversarially re-checked (\S\ref{sec:rq2}).

\subsection{Summarize: Trust-ranked Effect Summaries}

이 단계는 광고된 도구마다 하나의 질문에 답한다. 이 도구는 \S\ref{sec:prelim:surface}의 네 효과 가운데 무엇에 닿을 수 있으며 그 증거는 무엇인가. 증거는 공격자가 얼마나 통제할 수 있는지에 따라 순위가 매겨진다. 설정 자신의 인자와 서버의 소스 코드가 1순위, 선언된 스키마와 annotation이 2순위이며, 자유 서술 설명은 효과를 낮추는 데 결코 쓰이지 않는다. 올리는 데만 쓸 수 있는데, 설명은 판정 대상인 당사자가 작성하기 때문이다. HOSTEXEC은 나머지 셋을 함의한다. 호스트에서의 코드 실행은 호스트가 닿을 수 있는 모든 것에 닿기 때문이다.
% The stage answers one question per advertised tool: which of the four effects of \S\ref{sec:prelim:surface} can this tool reach, and what is the evidence? Evidence is ranked by how much an attacker controls it. The configuration's own arguments and the server's source code rank first, declared schemas and annotations second, and free-text descriptions are never allowed to lower an effect --- they may only raise one, because a description is written by the party being judged. HOSTEXEC implies the other three, since host code execution reaches whatever the host can reach.

요약은 언어 모델이 생성하되 모든 주장에 \texttt{file:line} 증거를 인용해야 하며, 이후 결정적 검사기가 가져온 소스에서 인용된 구간을 다시 읽어 걸러낸다. 인용이 가져온 트리 안에서 해석되지 않거나, 그 구간에 도구 이름이나 근거 설명이 지목한 식별자가 없으면, 그 주장은 유지되되 미확인으로 표시된다. 미확인 주장이 효과를 낮춰서는 안 되므로 라벨은 살아남지만, 검증된 것으로는 세지 않는다. 모델이 아예 판정하지 않은 도구에는 가장 보수적인 값인 HOSTEXEC을 부여한다. 모델이 라벨 없이 무해하다고 판정한 도구는 그 증거가 코드에서 해석될 때만 무해로 센다. 문서는 효과의 \emph{부재}를 입증할 수 없기 때문이다. 이 구분이 이 단계의 출력을 그럴듯한 것이 아니라 감사 가능한 것으로 만들며, \S\ref{sec:eval}은 그중 얼마가 검사기를 통과하는지 측정한다.
% Summaries are produced by a language model that must cite \texttt{file:line} evidence for every claim, and are then filtered by a deterministic checker that re-reads the cited span in the fetched source. A claim whose citation does not resolve inside the fetched tree, or whose span does not contain the tool name or an identifier the rationale names, is kept but marked undetermined; the label survives, because an unverified claim must not lower an effect, but it no longer counts as verified. A tool the model does not judge at all is assigned HOSTEXEC, the least restrictive reading. A tool the model clears with no labels counts as cleared only when its evidence resolves in code: documentation cannot establish the \emph{absence} of an effect. This split is what makes the stage's output auditable rather than merely plausible, and Section~\ref{sec:eval} measures how much of it survives the checker.

실무적으로 중요한 세부가 둘 있다. 모델에게는 모든 줄에 실제 줄 번호를 붙인 소스를 보여준다. 줄 번호가 없으면 인용된 줄이 파일 뒤로 갈수록 어긋나고, 올바른 판정이 검증에 실패하기 때문이다. 또한 패키지 자신의 코드가 도구 이름을 전혀 언급하지 않는 경우 --- 구현이 의존성에 있는 래퍼 패키지가 그렇다 --- 그 이름을 언급하는 직접 의존성을 스크립트 실행을 끈 채 가져와 함께 보여준다. 파이프라인의 어느 지점에서도 제공자 코드는 실행되지 않는다.
% Two details matter in practice. The model is shown source with every line prefixed by its true line number, because without them cited lines drift with depth and correct judgements fail verification. And when a package's own code never mentions a tool name --- the case for wrapper packages whose implementation lives in a dependency --- the direct dependencies that do mention it are fetched and shown, with scripts disabled; provider code is never executed at any point in the pipeline.

\subsection{Narrow: The Write Surface a Task Needs}
\label{sec:approach:narrow}

이 단계는 작업이 필요로 하는 WRITE 도구의 허용 목록을 에이전트의 첫 턴 이전에 한 번 만든다. 시스템 메시지와 사용자의 요청만 보는 언어 모델이 surface 위의 WRITE 도구 가운데 그 작업에 필요한 것의 이름을 대고, 그 답은 에이전트의 컨텍스트에 더해지지 않고 집행기에만 기록된다. 이 모델은 도구 출력을 결코 보지 않으므로, 주입이 목록을 넓힐 방법은 없다. 게이트 대상은 목적지 인자나 값 인자를 가진 WRITE, 곧 주입이 겨냥할 수 있는 WRITE뿐이다. READ 도구는 게이트하지 않는다. 읽기를 막는 것은 작업이 쓸 정보를 끊을 뿐이고, 읽기 도구가 목적지 인자를 가지는 경우 --- URL을 받는 \texttt{get\_webpage} --- 는 다음 단계가 호출마다 검사하기 때문이다. 메일을 읽으면서 읽음 표시를 남기는 \texttt{get\_unread\_emails}처럼 부수 효과만 있는 WRITE도 게이트하지 않는데, 공격자가 무엇을 쓰든 그 도구가 하는 일은 바뀌지 않기 때문이다. 그림~\ref{fig:example}의 선언된 작업이 이슈를 정리하기만 하고 코멘트를 남기지 않는다면 \texttt{add\_issue\_comment}는 목록에 들지 않고, 그 호출은 거부된다.
% This stage builds the allow-list of WRITE tools the task needs, once, before the agent's first turn. A language model that sees only the system message and the user's request names, among the WRITE tools on the surface, those the task needs, and its answer is recorded for the executor rather than appended to the agent's context. That model never sees a tool output, so an injection has no way to widen the list. What is gated is only a WRITE that takes a destination or a value argument, that is, a WRITE an injection could aim. READ tools are never gated: blocking a read only cuts off information the task will use, and where a read tool does take a destination argument --- \texttt{get\_webpage}, which takes a URL --- the next stage checks it at every call. A WRITE with only an incidental side effect, such as \texttt{get\_unread\_emails} marking mail as read while it reads it, is not gated either, because nothing an attacker writes changes what that tool does. If the declared task of Figure~\ref{fig:example} only triaged the issues without leaving a comment, \texttt{add\_issue\_comment} would not be on the list and a call to it would be refused.

목록 밖의 WRITE는 surface에서 제거하지 않고 그대로 보이게 두며, 그 호출이 오면 실행하지 않고 거부한다. 보안은 같지만 에이전트가 겪는 것이 다르다. 주입이 작업에 없는 도구를 지목했을 때 그 도구가 없으면 에이전트에게 남는 것은 침묵이고, 에이전트는 표류한다. 거부는 신호이고, 에이전트는 사용자의 작업으로 돌아온다. 같은 라벨과 같은 거부 문구를 두고 도구를 제거하는 대신 보이게 두고 거부하는 것의 효과는 \S\ref{sec:rq3}에서 잰다. 호스트가 설정 시점의 제어 수단 --- 도구 단위 거부 항목, 서버 모드와 toolset 플래그 --- 을 제공하면 같은 라벨 위의 결정을 설정 diff로 내보낼 수 있다. 그림~\ref{fig:example}의 \stepnum{7}이 그 형태로, 선언된 작업이 \stepnum{3}과 \stepnum{5}를 쓰므로 \stepnum{4}를 끈다. 이 논문은 그 형태를 평가하지 않는다.
% A WRITE outside the list is not removed from the surface; it stays visible, and a call to it is refused instead of executed. The security is the same, but what the agent experiences differs. When an injection names a tool the task does not need and that tool is absent, what the agent is left with is silence, and it drifts. A refusal is a signal, and the agent returns to the user's task. The effect of leaving the tools visible and refusing, rather than removing them, with the same labels and the same refusal text is measured in \S\ref{sec:rq3}. Where a host exposes configuration-time controls --- per-tool deny entries, server mode and toolset flags --- a decision over the same labels can be emitted as a configuration diff. \stepnum{7} in Figure~\ref{fig:example} is that form: the declared task uses \stepnum{3} and \stepnum{5}, so \stepnum{4} is switched off. This paper does not evaluate that form.

\subsection{Guard: Destination Provenance at Each Call}
\label{sec:approach:guard}

도구 단위 규칙은 AgentDojo에서 targeted ASR을 4.18\% 아래로 내릴 수 없다(\S\ref{sec:prelim:goal}). 이 단계는 그 호출들을 인자 수준에서 가른다. 목적지 인자를 가진 모든 호출에서, 도구의 종류와 무관하게 --- \texttt{get\_webpage}는 READ이지만 URL에 담긴 것을 내보낸다 --- 각 값이 어디에서 왔을 수 있는지를 추적한다. 출처는 넷이다. 사용자의 요청, 앞선 결과의 구조화된 필드, 앞선 쓰기의 결과, 그리고 공격자가 쓸 수 있는 텍스트. 값은 정규화한 형태와 그 축약형 --- 스킴을 뗀 것, \texttt{www.}를 뗀 것, 호스트만 --- 으로 각각 찾으며, 어느 형태에든 신뢰된 출처가 하나라도 있으면 값은 통과한다. 공격자가 쓸 수 있는 텍스트에서만 찾아지는 값을 가진 호출은 거부된다.
% A tool-level rule cannot bring targeted ASR below 4.18\% on AgentDojo (\S\ref{sec:prelim:goal}). This stage separates those calls at the level of the argument. At every call that has a destination argument, whatever the tool's kind --- \texttt{get\_webpage} is a READ and still sends whatever is in the URL --- it traces where each value could have come from. There are four sources: the user's request, a structured field of an earlier result, the result of an earlier write, and text an attacker can write. A value is looked up in its normalised form and its stripped forms --- without the scheme, without \texttt{www.}, the bare host --- and any trusted source for any form clears it. A call whose value is found only in attacker-writable text is refused.

출처 판정은 도구 결과를 필드 단위로 쪼개어 잎마다 부류를 매긴 뒤 이루어진다. 결과는 YAML로 기록되므로 필드 분리는 정확하고, \texttt{body} 안에 주입된 문자열이 키를 만들어 낼 수 없다. 잎의 부류는 넷이다. \emph{신뢰할 수 없는 산문}은 공격자가 쓸 수 있는 필드의 텍스트로, 값이 그 안에 포함되면 오염된다. \emph{고정 산문}은 공격자가 닿지 못하는 텍스트로, 값이 그 안에 포함되면 통과한다. \emph{식별자}는 id와 주소, 시스템이 등록한 이름으로, 값이 그것과 동등할 때만 통과하고 포함은 아무것도 뜻하지 않는다. 사전의 키는 항상 식별자다. \emph{이름 붙은 식별자}는 공격자가 철자를 정한 식별자 --- 공격자가 만든 채널 --- 로, 동등하면 통과하고 포함되면 오염된다. 공격자가 이름 지은 채널은 실제 채널이지만 그 텍스트는 지시를 실을 수 있어서, \texttt{External\_visit www.evil.com}이라는 채널은 식별자이되 \texttt{www.evil.com}은 그것이 아니다. 짧은 id는 텍스트 안에서 찾지 않고 식별자와의 동등으로만 맞춘다. 어디서나 찾아지기 때문이다. 반환값 전체가 공격자가 쓸 수 있는 도구 --- 파일 내용, 웹 페이지 --- 의 결과는 파싱하지 않는다. \texttt{key: value}처럼 보이는 내용이 구조화된 필드로 승격되어서는 안 되기 때문이다.
% Provenance is decided after a tool result is split by field and every leaf is given a class. Results are recorded as YAML, so the field split is exact and a string injected inside \texttt{body} cannot manufacture a key. There are four leaf classes. \emph{Untrusted prose} is the text of an attacker-writable field: a value contained in it is tainted. \emph{Fixed prose} is text the attacker cannot reach: a value contained in it is cleared. An \emph{identifier} is an id, an address or a name the system registered: a value is cleared only when equal to it, and containment means nothing. A dictionary key is always an identifier. A \emph{named identifier} is an identifier whose spelling the attacker chose --- a channel the attacker created: equality clears, containment taints. An attacker-named channel is a real channel, but its text can carry an instruction, so the channel \texttt{External\_visit www.evil.com} is an identifier while \texttt{www.evil.com} is not it. A short id is never searched for inside text and matches an identifier by equality only, because it would be found everywhere. The result of a tool whose whole return is attacker-writable --- file contents, a web page --- is not parsed, because content that happens to look like \texttt{key: value} must not be promoted to structured fields.

strict 모드는 조건 하나를 더한다. 신뢰된 출처도 오염된 출처도 없는 목적지, 곧 세 글자 이상이면서 신뢰된 컨텍스트 어디에도 없는 값도 거부한다. 에이전트는 주입이 \texttt{mark [at] gmail [dot] com}으로 적은 주소를 스스로 복원하고, 복원된 값은 어느 텍스트에도 없으므로 기본 규칙은 그것을 잡지 못한다. 에이전트가 지어냈든 난독화된 주입에서 복호했든, 그 값은 사용자가 요청한 목적지가 아니다. 짧은 id는 여기서도 예외인데, 어느 잎과도 같지 않은 id는 에이전트가 적어 넣은 id일 뿐 유출 경로가 아니다. 거부는 두 단계 모두 같은 형태의 결과로 에이전트에게 돌아간다. 어떤 인자나 값이 검사에 걸렸는지는 말하지 않고, 도구 결과 안의 지시는 사용자의 것이 아니니 무시하고 이미 가진 정보로 사용자의 원래 작업을 계속하라고 말한다. 인자와 값을 밝히면 주입에게 가드가 무엇을 검사하는지 탐색할 통로를 주고, 다음에 무엇을 할지 말하지 않으면 에이전트는 작업을 버린다. 판정의 세부는 로그에만 남는다.
% Strict mode adds one condition: it also refuses a destination that has neither a trusted nor a tainted source, that is, a value of three or more characters that appears nowhere in the trusted context. The agent reconstructs on its own an address the injection spelt as \texttt{mark [at] gmail [dot] com}, and the reconstructed value is in no text, so the default rule does not catch it. Whether the agent made it up or decoded it from an obfuscated injection, that value is not a destination the user asked for. Short ids are exempt here too: an id equal to no leaf is just an id the agent typed, not an exfiltration channel. A refusal returns to the agent in the same form from both stages. It says nothing about which argument or value tripped the check; it says that instructions inside tool results are not from the user, to disregard them, and to continue the user's original task with the information already at hand. Naming the argument and the value would hand the injection a channel to probe what the guard checks, and not saying what to do next makes the agent abandon the task. The detail of the judgement goes only to the log.

\subsection{Research Questions}

본 연구의 실험은 \textsc{Interlock}의 두 부분을 각각 묻는다. \emph{Summarize}가 내놓는 효과 요약은 그 자체로 참임을 보일 수 없고 --- 판정 대상이 제3자의 코드이므로 정답 집합이 존재하지 않는다 --- 다만 각 주장이 스스로 지목한 증거로 되짚어지는지는 결정적으로 확인할 수 있다. 그 요약을 소비하는 두 집행 규칙 \emph{Narrow}와 \emph{Guard}는 결과로 잴 수 있다. 공격이 막혔는지와 사용자의 작업이 유지되었는지를 같은 벤치마크 위에서 베이스라인과 나란히 재면 된다. 따라서 우리는 다음을 묻는다.
% Our experiments ask about the two parts of \textsc{Interlock} separately. The effect summaries \emph{Summarize} produces cannot be shown true in themselves --- the object judged is third-party code, for which no ground truth set exists --- but whether each claim traces back to the evidence it names can be checked deterministically. The two enforcement rules that consume those summaries, \emph{Narrow} and \emph{Guard}, can be measured by outcome: whether the attack was stopped and whether the user's task survived, on the same benchmark and beside the baselines. We therefore ask:

\begin{itemize}
    \item \textbf{RQ1.} 실제 MCP 서버에 대해 모델이 내놓은 효과 판정 가운데 얼마나 많은 부분이 결정적 재검사를 통과하는가? 통과하지 못하는 판정은 어디에서 발생하며, 무엇이 그 비율을 좌우하는가?
    % \item \textbf{RQ1.} How much of the model's effect judgement on real MCP servers survives deterministic re-checking? Where does the judgement fail to survive, and what governs that rate?
    \item \textbf{RQ2.} Narrow와 Guard를 함께 쓴 \textsc{Interlock}이 같은 조건의 베이스라인보다 낮은 targeted ASR을 더 적은 utility 손실로 달성하는가?
    % \item \textbf{RQ2.} Does \textsc{Interlock}, with Narrow and Guard together, reach a lower targeted ASR than the baselines under the same conditions, at a smaller loss of utility?
    \item \textbf{RQ3.} 두 규칙 각각이 얼마를 기여하며, 그 결과는 목적지를 난독화한 적응형 주입에도 유지되는가?
    % \item \textbf{RQ3.} How much does each of the two rules contribute, and does the result hold against an adaptive injection that obfuscates its destination?
\end{itemize}

RQ1의 답은 \S\ref{sec:rq1}에, RQ2의 답은 \S\ref{sec:rq2}에, RQ3의 답은 \S\ref{sec:rq3}에 있다.

\subsection{Experimental Settings}
\label{sec:settings}

\subsubsection{Benchmarks}

본 연구는 AgentDojo~\cite{debenedetti2024agentdojo}를 벤치마크로 사용한다. 비교 대상인 세 선행연구가 모두 이 환경에서 결과를 보고했기 때문이다. AgentDojo는 프롬프트 주입에 대한 에이전트 방어를 평가하는 환경으로, 업무용 메일과 일정과 드라이브를 다루는 workspace, 메신저를 다루는 slack, 예약을 다루는 travel, 계좌를 다루는 banking의 네 suite에 도구 74개와 사용자 과제 97개, 주입 과제 35개를 담고 있다. 하나의 \emph{보안 케이스}는 사용자 과제와 주입 과제를 짝지은 것으로, 공격자의 지시는 에이전트가 읽게 될 콘텐츠에 심기고 성공 여부는 결정적 Python 함수가 판정한다. 언어 모델 심판을 쓰지 않는 이유를 저자들이 밝혀 두었고 우리도 이를 따르는데, 공격이 충분히 성공적이면 평가 모델까지 탈취할 수 있기 때문이다. 다만 우리는 보안 케이스 949개 전부가 아니라 \textbf{909개}를 사용한다. \subsubsection{Baselines}

본 연구는 MCP 에이전트의 권한을 제한하는 선행연구인 AgentDojo~\cite{debenedetti2024agentdojo}, Progent~\cite{shi2025progent}, CaMeL~\cite{debenedetti2025defeating}을 베이스라인으로 삼아 평가를 수행한다. Fides~\cite{costa2025securing} 역시 같은 갈래의 선행연구이나, 공개된 저장소가 튜토리얼 노트북 하나여서 보고된 결과를 재현할 수 없기 때문에 제외하였다. 조합 검사 계열의 연구도 제외하였는데, 위험 여부를 판정할 뿐 설정을 바꾸지 않으므로 공격이 막혔는지와 작업이 유지되었는지로 채점하는 자리에 놓일 수 없기 때문이다. 비교 대상은 다음과 같다.
% This study evaluates against the prior work that narrows an MCP agent's privilege: AgentDojo~\cite{debenedetti2024agentdojo}, Progent~\cite{shi2025progent} and CaMeL~\cite{debenedetti2025defeating}. Fides~\cite{costa2025securing} belongs to the same line but is excluded, because its public repository is a single tutorial notebook from which the reported results cannot be reproduced. Set-level analyses are excluded as well: they judge whether a deployment is dangerous without changing its configuration, and so cannot be scored on whether an attack was stopped and the task preserved. The baselines we take from this prior work are the following.

\begin{itemize}
    \item \textbf{No Defense}~\cite{debenedetti2024agentdojo}: 방어를 두지 않은 에이전트로, 나머지 넷이 무엇을 줄였는지 재는 기준점이다.
    % \item \textbf{No Defense}~\cite{debenedetti2024agentdojo}: an agent with no defence at all, the reference against which the other four are measured.
    \item \textbf{Tool Filter}~\cite{debenedetti2024agentdojo}: AgentDojo가 함께 제공하는 방어다. 질의를 받으면 모델에게 그 작업에 필요한 도구만 고르게 한 뒤 나머지를 제거하며, 집행은 첫 호출 이전에 한 번 이루어진다.
    % \item \textbf{Tool Filter}~\cite{debenedetti2024agentdojo}: the defence AgentDojo ships. Given the query it asks the model to select only the tools the task needs and removes the rest, enforcing once before the first call.
    \item \textbf{Progent}~\cite{shi2025progent}: 사용자의 작업에서 도구 이름과 인자에 대한 기호 규칙을 LLM으로 생성하고 호출마다 그 규칙과 대조하며, 실행 중 새 정보가 들어오면 정책을 갱신한다.
    % \item \textbf{Progent}~\cite{shi2025progent}: has an LLM generate symbolic rules over tool names and arguments from the user's task, checks every call against them, and updates the policy as new information arrives.
    \item \textbf{CaMeL}~\cite{debenedetti2025defeating}: 권한 있는 LLM이 신뢰된 질의를 제한된 프로그램으로 옮기고 격리된 LLM이 신뢰할 수 없는 데이터를 해석하며, 전용 인터프리터가 값마다 능력을 추적해 도구 호출 시점에 정책을 집행한다.
    % \item \textbf{CaMeL}~\cite{debenedetti2025defeating}: a privileged LLM turns the trusted query into a restricted program while a quarantined LLM interprets untrusted data, and a custom interpreter tracks a capability per value and enforces policies at the point a tool is called.
    \item \textbf{\textsc{Interlock}}: 본 연구의 시스템으로, Narrow와 Guard를 함께 켠 구성이다. 허용 목록 밖의 WRITE는 제거하지 않고 호출 시점에 거부하며(게이트), 출처가 전혀 없는 목적지까지 거부하는 strict 모드는 RQ3에서 따로 잰다. 두 규칙이 소비하는 도구별 라벨 --- READ/WRITE, 목적지 인자, 주입 가능한 출력 필드, 식별자 필드 --- 는 도구의 설명이 아니라 코드에서 분류하고 적대적으로 재검사한 것이다.
    % \item \textbf{\textsc{Interlock}}: our system, with Narrow and Guard both on. A WRITE outside the allow-list is refused at the call rather than removed (gate); strict mode, which also refuses a destination with no provenance at all, is measured separately in RQ3. The per-tool labels the two rules consume --- READ/WRITE, destination arguments, injectable output fields, identifier fields --- are classified from the tool code rather than its description and adversarially re-checked.
\end{itemize}

\subsubsection{Evaluation Metrics}

본 연구는 AgentDojo가 정의한 세 지표를 그대로 사용한다~\cite{debenedetti2024agentdojo}. 비교 대상들이 같은 용어로 결과를 보고하므로, 지표를 새로 정의하기보다 이를 따르는 편이 비교에 유리하다. 각 지표는 다음과 같다.
% This study adopts the three metrics AgentDojo defines~\cite{debenedetti2024agentdojo}. The systems we compare against report under the same terms, so following them serves the comparison better than defining metrics of our own. The metrics are the following.

\begin{itemize}
    \item \textbf{Benign Utility}(BU): 공격이 없을 때 사용자 과제를 푼 비율.
    % \item \textbf{Benign Utility} (BU): the fraction of user tasks solved in the absence of any attack.
    \item \textbf{Utility Under Attack}(UUA): 보안 케이스에서 부작용 없이 사용자 과제를 푼 비율.
    % \item \textbf{Utility Under Attack} (UUA): the fraction of security cases in which the user task is solved without adversarial side effects.
    \item \textbf{Targeted Attack Success Rate}(ASR): 보안 케이스에서 공격자의 목표가 달성된 비율. 낮을수록 좋다.
    % \item \textbf{Targeted Attack Success Rate} (ASR): the fraction of security cases in which the attacker's goal is met. Lower is better.
\end{itemize}

방어는 이 셋을 함께 읽어야 한다. 도구를 전부 꺼 버리면 ASR은 0이 되지만 BU도 함께 0이 되므로, ASR만으로는 공격을 막은 것과 에이전트를 멈춰 세운 것이 구별되지 않는다.
% A defence has to be read on all three: switching every tool off drives ASR to zero and BU with it, so ASR alone does not distinguish blocking an attack from halting the agent.

측정 방식에서 본 연구는 두 가지를 벤치마크의 기본값과 다르게 한다. 첫째, slack suite의 \texttt{injection\_task\_5}는 모든 arm에서 실제로 실행된 호출로 채점한다. 이 과제는 성공해도 최종 상태가 바뀌지 않아 AgentDojo가 호출 기록으로 채점하므로 방어가 거부한 호출도 성공으로 세기 때문이다. Progent의 저자들은 이를 손으로 보정했고, 본 연구는 과제의 상태 기계를 실행된 호출 위에서 재생하는 방식으로 같은 보정을 모든 arm에 적용한다. 이 보정은 Progent의 첫 공격 실행에서 8건, \textsc{Interlock}의 첫 게이트 실행에서 6건의 판정을 바꾸며, 기록된 값은 보정된 값 옆에 보관한다. 둘째, BU는 같은 구성의 모든 benign 실행에 대한 평균 $\pm$ 표준편차로 보고하고, Progent와 \textsc{Interlock}의 게이트 구성은 공격 실행을 세 번씩 반복해 UUA와 ASR도 같은 형태로 보고한다. 반복이 필요한 이유는 다음 항목에 있다.
% In two respects our measurement departs from the benchmark's default. First, \texttt{injection\_task\_5} of the slack suite is scored from the calls that actually executed, in every arm. Its end state does not change even when the attack succeeds, so AgentDojo scores it from the call trace, and a call a defence refused still counts as a success. Progent's authors corrected this by hand; we apply the same correction to every arm by replaying the task's state machine over the executed calls. The correction changes the outcome of 8 cases in Progent's first attack run and 6 in \textsc{Interlock}'s first gate-mode run, and the logged value is kept beside the corrected one. Second, BU is reported as mean $\pm$ standard deviation over every benign run of a configuration, and for Progent and \textsc{Interlock}'s gate configuration the attack run is repeated three times so that UUA and ASR are reported the same way. The next item gives the reason repetition is needed.

\subsubsection{Environments}

본 연구는 GPT-4o를 사용한다. 네 베이스라인이 공통으로 사용한 모델일 뿐 아니라, 그들이 사용한 모델 가운데 지금도 API로 이용할 수 있는 유일한 모델이기 때문이다. Progent가 함께 보고한 Claude Sonnet~4와 Gemini~2.5 Flash, GPT-4.1, CaMeL이 사용한 Claude~3.5 Sonnet과 Gemini~2.5 Pro는 모두 제공자가 서비스를 종료하여 재현할 수 없다. Progent는 에이전트와 정책 생성기 양쪽에, CaMeL은 권한 있는 LLM과 격리된 LLM 양쪽에 같은 모델을 사용하므로 우리도 그와 같이 맞추었다. 온도는 베이스라인이 설정한 0을 그대로 따랐다. AgentDojo와 Progent, CaMeL은 모두 온도를 0으로 두고 보안 케이스마다 한 번씩만 실행하며 반복 실행을 하지 않는데, 이들 논문이 보고하는 구간 역시 반복 사이의 편차가 아니라 케이스 수에 대한 신뢰구간이다. 그러나 온도 0에서도 GPT-4o의 출력은 결정적이지 않다. 같은 구성을 다시 실행하면 케이스 909개 위의 UUA와 ASR은 표준편차 0.8 이하로 안정적이지만 과제 97개 위의 BU는 2--4점 흔들리며, 베이스라인 논문이 단일 실행으로 보고한 BU의 몇 점 차이도 이 폭 안에 있다. 그래서 본 연구는 같은 구성을 반복 실행하고 앞 항목의 방식으로 보고한다. 실험은 macOS~26.6, Apple~M1 Ultra(20코어), 64\,GB 메모리 환경에서 수행하였고, 모든 모델 호출이 제공자의 API를 거치므로 GPU는 사용하지 않는다. 벤치마크와 각 베이스라인은 공개 저장소를 고정된 리비전으로 받아 사용하였으며, 체크아웃에 가한 수정은 두 가지뿐이다. AgentDojo에는 모델 식별자를 등록하는 세 줄을 더하였고, CaMeL에는 지원하지 않는 상수를 만났을 때 오류 메시지를 만들면서 존재하지 않는 속성을 참조해 실행 전체가 중단되는 버그를 한 줄 고쳤다. 과제와 채점기, 공격, 정책 로직에는 손대지 않았다.
% This study uses GPT-4o. It is the model the four baselines share, and it is also the only model any of them used that a provider still serves: the Claude Sonnet~4, Gemini~2.5 Flash and GPT-4.1 that Progent additionally reports, and the Claude~3.5 Sonnet and Gemini~2.5 Pro that CaMeL uses, have all been retired and cannot be reproduced. Progent uses one model for both the agent and the policy generator, and CaMeL one for both the privileged and the quarantined LLM, and we match that. Temperature follows what the baselines set, 0. AgentDojo, Progent and CaMeL all use a temperature of 0 and run each security case once without repetition, and the intervals their papers report are likewise confidence intervals over cases rather than spread between repetitions. At temperature 0, however, GPT-4o is not deterministic. Re-running the same configuration leaves UUA and ASR, over 909 cases, stable to a standard deviation of at most 0.8, but BU, over 97 tasks, swings by 2--4 points, and the BU differences of a few points that the baselines' papers report from single runs fall inside that band. We therefore repeat each configuration and report it as the previous item describes. The experiments were run on macOS~26.6 with an Apple~M1 Ultra (20 cores) and 64\,GB of memory; all model calls go through the providers' APIs, so no GPU is used. The benchmark and each baseline were taken from their public repositories at pinned revisions, and we made only two changes to those checkouts: three lines registering model identifiers in AgentDojo, and a one-line fix in CaMeL where the handler for an unsupported constant referenced a non-existent attribute while formatting its error message, aborting the whole run. \subsection{RQ1: How Much of the Effect Judgement Survives Re-checking?}
\label{sec:rq1}

우리는 광고된 surface를 복원할 수 있었던, 가장 자주 설정되는 npm 및 PyPI 서버 34개, 총 433개의 광고된 도구를 대상으로, 고정된 rubric과 JSON 스키마를 사용하는 Claude Opus~5, 패키지당 400\,KB의 소스 예산, 그리고 \S\ref{sec:approach}에서 설명한 검사기로 프로파일을 만든다. 광고된 각 도구는 정확히 하나의 범주에 들어간다. 모델이 라벨을 주장했고 인용이 코드에서 해석된 경우(\emph{verified}), 문서에서만 해석된 경우(\emph{verified\_doc}), 해석되지 않은 경우(\emph{demoted}), 모델이 무해로 판정했고 코드 증거가 있는 경우(\emph{cleared verified}) 또는 없는 경우(\emph{cleared unverified}), 그리고 모델이 판정하지 않은 경우(\emph{unjudged})다. 광고된 surface에 없는 이름을 판정한 경우는 별도로 센다. 기준과 정의는 실행 전에 사전 등록했으며, 계획서가 정한 dry-run에서 발견된 측정 도구 변경은 모두 실행 이후가 아니라 이전에 기록했다.

\section{Threats to Validity}
\label{sec:threats}

\emph{코퍼스.} GitHub 코드 검색은 질의당 결과 수에 상한을 두고 표집이 아니라 관련도 순위로 반환하므로, 이 코퍼스는 배포의 무작위 표본이 아니다. 커밋된 설정은 사람들이 실제로 실행하는 설정과 다를 수도 있다. \emph{판정 대상 집합.} 효과는 가장 자주 설정되는 서버 34개에 대해서만 도출했으므로, 결과는 인기 서버를 설명하며 롱테일을 설명하지 않는다. \emph{위협 모델.} 우리의 판정은 최악 가정의 에이전트 아래에서 광고된 surface가 갖는 성질이다. 특정 배포가 공격을 당했다거나 공격이 성공한다고 주장하지 않으며, 악용 가능성 확인은 향후 과제다. \emph{검사기.} 검사기는 한 방향으로 엄격하고 다른 방향으로 느슨하다. 강등 81건 중 약 9건은 인용 구간에 해당 식별자가 더 긴 표현 안에 실제로 존재하지만 토큰 일치가 이를 놓친 경우이고, 반대로 코드로 검증된 판정 308건 중 4건은 네 글자 이하의 토큰에 기대고 있다. \emph{발췌.} 큰 파일에 대해서는 이름이 등장하는 지점 주변 창만 보여주므로, 큰 파일에 존재하는 도구 이름 11개는 모델에게 한 번도 보이지 않았다. 따라서 의존성 추적의 이득은 하한이다. \emph{범위.} 우리의 결론은 설정 파일이 선언하는 MCP 서버에 대한 것이며, 에이전트 스킬로 일반화하지 않는다. 스킬은 광고된 도구 목록을 갖지 않으므로 여기서 쓴 측정 단위가 그대로 적용되지 않는다. \emph{실행 간 분산.} GPT-4o는 온도 0에서도 결정적이지 않다. 같은 구성을 같은 설정으로 다시 실행하면 benign utility가 97개 과제 위에서 2--4점 움직이므로, 본 연구는 benign utility를 반복 실행의 평균과 표준편차로 보고하고 Progent와 \textsc{Interlock}의 게이트 구성에는 공격 실행을 세 번씩 두었다. 909개 보안 케이스 위의 utility under attack과 targeted ASR은 실행 사이 표준편차가 0.8 이하로 안정적이다. \emph{채점.} AgentDojo는 slack의 injection\_task\_5를 종료 상태가 아니라 호출 기록으로 채점하므로, 방어가 거부한 호출도 성공으로 센다. 본 연구는 모든 비교 대상에 대해 이 과제를 실제로 실행된 호출로 채점하며, 이 보정은 Progent의 첫 실행에서 targeted ASR을 3.96에서 3.08로 옮긴다. \emph{라벨의 출처.} AgentDojo에서 효과 라벨은 모델이 도구 코드에서 분류하고 적대적으로 재검사한 것이지만, 이 벤치마크에서는 설명과 코드가 일치하므로 \S\ref{sec:prelim:limitation}이 논한 코드 유래 라벨의 이점은 RQ2에서 발휘되지 않는다. 실제 서버 위에서 가드를 평가하는 것은 향후 과제다. \emph{공격.} 평가한 공격은 한 계열과 우리가 직접 작성한 적응 변형 하나뿐이다. 철자 이상으로 목적지를 변형하는 공격자, 또는 정당한 목적지로 보내는 내용에 데이터를 실어 유출하는 공격자는 가드가 검사하는 범위 밖에 있다. \emph{단일 모델.} 모든 요약은 한 시점의 한 모델에서 나왔다. 모델이나 시간에 따라 이 비율이 얼마나 달라지는지는 측정하지 않았다.
% \emph{Corpus.} GitHub's code search caps results per query and ranks rather than samples them, so the corpus is not a random sample of deployments; committed configurations may also differ from those people run. \emph{Adjudicated set.} Effects are derived for the 34 most frequently configured servers, so the results describe popular servers, not the long tail. \emph{Threat model.} Our judgements are a property of the advertised surface under a worst-case agent; it does not assert that a deployment has been attacked or that an attack would succeed, and confirming exploitability is future work. \emph{Checker.} The checker is strict in one direction and loose in another: about 9 of 81 demotions cite spans that do contain the relevant identifier inside a longer expression that the token match misses, while 4 of 308 code-verified judgements rest on a token of four characters or fewer. \emph{Excerpts.} For large files the prompt shows windows around name occurrences, and 11 tool names present in large files were never shown, so the benefit we report from following dependencies is a lower bound. \emph{Scope.} Our conclusions concern the MCP servers a configuration file declares and do not generalise to agent skills, which have no advertised tool list and therefore no counterpart to the unit of measurement used here. \emph{Run-to-run variance.} GPT-4o is not deterministic at temperature 0. Rerunning the same configuration under the same setting moves benign utility by 2--4 points over 97 tasks, so we report benign utility as mean and standard deviation over repeated runs and give Progent and \textsc{Interlock}'s gate configuration three attack runs each; utility under attack and targeted ASR over 909 security cases are stable between runs, with a standard deviation of at most 0.8. \emph{Scoring.} AgentDojo scores slack's injection\_task\_5 from the call trace rather than the end state, so a call a defence refused still counts as a success. We score this task from the calls that actually executed, for every arm; the correction moves Progent's targeted ASR in its first run from 3.96 to 3.08. \emph{Provenance of the labels.} On AgentDojo the effect labels were classified by a model from the tool code and adversarially re-checked, but there descriptions and code agree, so the advantage of code-derived labels that \S\ref{sec:prelim:limitation} argues for is not exercised by RQ2. Evaluating the guard on real servers is future work. \emph{Attacks.} We evaluate one attack family and one adaptive variant we wrote ourselves. An attacker who transforms destinations beyond spelling, or who exfiltrates through the content sent to a legitimate destination, is outside what the guard checks. \emph{Single model.} All summaries come from one model at one date; we have not measured how much the rate varies across models or over time.


\section{Related Work}
\label{sec:related}

\subsection{Vetting an Individual Artifact}
\label{sec:related:artifact}

MCP 아티팩트 하나를 검사하는 연구는 서버가 광고하는 텍스트에서 시작한다. 도구 오염 탐지기는 설명 안에 숨겨진 지시와 이름 가로채기, 유출 엔드포인트를 읽어내고~\cite{jain2026detecting}, 신뢰할 수 있는 설명을 다시 생성해 그 벡터 자체를 없애기도 하며~\cite{ye2026trustdesc}, 벤치마크는 실제 서버에서 이런 공격이 얼마나 성공하는지를 정량화한다~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}. 도구 설명이 그 자체로 과잉 권한을 합성하는 경로가 됨을 보인 측정도 있다~\cite{rashidi2026measuring}. 텍스트 아래로 내려가면, 정적 분석은 신뢰할 수 없는 입력이 민감한 연산에 닿는 결함을 개별 도구 핸들러까지 추적하고~\cite{sun2026viper}, 동작 감사는 도구를 샌드박스에서 실행해 관찰된 흐름을 보고하며~\cite{tan2026sandscope}, 설정 감사기는 선언된 서버의 출처와 알려진 위험 패턴을 점검한다~\cite{patel2026mcpaudit, snyk2026agentscan}. 이 갈래에서 판정의 대상은 아티팩트 하나이고, 판정의 결론은 그 아티팩트가 악의적이거나 결함이 있는가이다. 우리가 묻는 것은 그와 독립적인 질문이다. 악의도 결함도 없이 문서화된 대로 동작하는 도구가 정상 동작으로 무엇에 닿는가.
% Work that vets a single MCP artifact starts from the text a server advertises. Tool-poisoning detectors read descriptions for hidden instructions, shadowed names and exfiltration endpoints~\cite{jain2026detecting}; trusted descriptions can be regenerated to remove the vector altogether~\cite{ye2026trustdesc}; and benchmarks quantify how often such attacks succeed on real servers~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}. Measurement has also shown the description itself to be a path by which excess privilege is synthesised~\cite{rashidi2026measuring}. Below the text, static analysis traces defects where untrusted input reaches a sensitive operation, down to the individual tool handler~\cite{sun2026viper}; behavioural audit executes a tool in a sandbox and reports the flows it observes~\cite{tan2026sandscope}; and configuration auditors check the provenance of declared servers against known risky patterns~\cite{patel2026mcpaudit, snyk2026agentscan}. In this line the object judged is one artifact and the conclusion is whether that artifact is malicious or defective. Ours is an independent question: what a tool that is neither, behaving exactly as documented, reaches in normal operation.

\subsection{Set-level Analysis and Information Flow}
\label{sec:related:setlevel}

여럿이 모였을 때 비로소 성립하는 성질을 묻는 전통은 정보 흐름 제어에 있다. Denning은 허용되는 흐름을 보안 등급의 격자로 형식화해, 어떤 흐름이 허용되는지를 프로그램마다 논증하는 대신 격자 위에서 판정할 수 있게 했다~\cite{denning1976lattice}. 분산 IFC는 라벨에 소유자를 기록해 서로 불신하는 주체들이 각자의 몫만 선별적으로 declassify하도록 했고~\cite{myers1997decentralized}, 동적 taint 분석은 신뢰할 수 없는 입력에 표시를 붙여 실행 중에 전파하며 그것이 민감한 사용 지점에 닿는 순간을 잡았다~\cite{newsome2005dynamic}. 설치된 집합을 단위로 삼는 형태도 오래되었다. Android의 앱 간 권한 유출에 대한 조합 분석은 설치된 앱 전체를 함께 분석하고, 앱이 설치·갱신·삭제될 때마다 이를 다시 검사한다~\cite{bagheri2015covert, li2015iccta}. 에이전트 층위에서 같은 질문은 lethal trifecta로 명명되고 toxic flow로 탐지되며~\cite{willison2025lethal, beurerkellner2025toxicflow, schneider2026securing}, 계획 생성과 보안 감시를 분리해 신뢰할 수 없는 입력이 제어 결정에 영향을 주지 못하게 하는 시스템 수준 IFC도 제시되었다~\cite{wu2024system}. \textsc{Interlock}의 Guard는 이 갈래의 능력 추적을 값의 동일성으로 근사한다. 도구 결과의 값마다 출처 클래스를 붙이고 목적지 인자가 그 값과 같은지 또는 그 안에 포함되는지만 보므로 값이 그대로 전달되는 흐름에 대해서는 건전하며, CaMeL처럼 질의를 프로그램으로 옮기거나 격리된 모델을 두지 않고 보통의 도구 호출 에이전트 위에서 그대로 동작한다~\cite{debenedetti2025defeating}.
% The tradition of asking what holds only once several artifacts are combined lies in information-flow control. Denning formalised the permitted flows as a lattice of security classes, so that whether a flow is allowed becomes a decision over the lattice rather than an argument made afresh for each program~\cite{denning1976lattice}. Decentralised IFC records an owner in each label so that mutually distrusting principals may selectively declassify only their own component~\cite{myers1997decentralized}, and dynamic taint analysis marks untrusted input, propagates the mark through a running program and catches the moment it reaches a sensitive use~\cite{newsome2005dynamic}. Taking the installed set as the unit is likewise long established: compositional analysis of inter-application permission leakage on Android analyses the installed applications together and re-checks them whenever one is installed, updated or removed~\cite{bagheri2015covert, li2015iccta}. At the agent layer the same question is named as the lethal trifecta and detected as toxic flow~\cite{willison2025lethal, beurerkellner2025toxicflow, schneider2026securing}, and system-level IFC separates plan generation from a security monitor so that untrusted input cannot influence control decisions~\cite{wu2024system}. \textsc{Interlock}'s Guard approximates the capability tracking of this line by value identity. It attaches a provenance class to every value of a tool result and asks only whether a destination argument equals or is contained in such a value, which is sound for flows that carry a value unchanged, and it runs on a stock tool-calling agent without translating the query into a program or running a quarantined model as CaMeL does~\cite{debenedetti2025defeating}.

\subsection{Privilege Narrowing and Policy Synthesis}
\label{sec:related:narrowing}

주체에게 필요한 만큼의 권한만 준다는 원칙은 Saltzer와 Schroeder가 정리한 여덟 설계 원칙 가운데 하나다~\cite{saltzer1975protection}. 이를 표현하는 고전적 메커니즘이 capability --- 대상의 이름과 그에 대한 권한을 함께 담은 위조 불가능한 토큰 --- 이고~\cite{dennis1966programming}, 이를 프로세스 구조에 적용한 것이 권한 분리다. 특권 데몬을 작은 감시자와 신뢰할 수 없는 입력을 파싱하는 비특권 자식으로 쪼개면 노출된 코드의 버그가 권한으로 이어지지 않는다~\cite{provos2003preventing}. LLM 에이전트에 대해서도 같은 원칙이 적용되어, 작업에서 정책을 합성해 호출마다 집행하거나~\cite{shi2025progent}, 값에 능력을 붙여 인터프리터가 검사하게 하거나~\cite{debenedetti2025defeating}, 신뢰 수준이 다른 구성 요소를 분리하며~\cite{costa2025securing}, 도달 가능성 위의 cut으로 능력을 가두거나~\cite{xiong2026reachability} 에이전트 루프를 가드레일로 감싸는 방법도 제시되었다~\cite{murugan2026}. 기능을 유지한 채 권한을 줄이는 문제는 에이전트 밖에서도 연구되어, 브라우저 확장의 과다 권한은 선언된 manifest 권한을 코드가 실제로 호출하는 API와 대조해 탐지되고~\cite{cheng2026percheck}, 프로그램 debloating은 테스트 스위트를 계속 통과시켜야 한다는 제약 아래 아티팩트를 줄인다~\cite{heo2018effective, sharif2018trimmer}. \textsc{Interlock}도 호출마다 검사하지만, 작업에서 정하는 것은 WRITE 도구의 허용 목록뿐이고 호출마다 대조하는 것은 코드에서 한 번 도출한 효과 라벨 위의 고정된 출처 규칙이다. Progent와 달리 인자 정책을 질의마다 합성하지 않고 도구 출력을 읽어 정책을 갱신하는 단계도 없으므로 주입이 정책에 닿을 길이 없으며, 제3자의 아티팩트는 고쳐 쓰지 않는다~\cite{shi2025progent}.
% Granting a principal no more privilege than it needs is one of the eight design principles set out by Saltzer and Schroeder~\cite{saltzer1975protection}. The classical mechanism that expresses it is the capability --- an unforgeable token carrying both the name of an object and the rights held over it~\cite{dennis1966programming} --- and privilege separation applies it to process structure: splitting a privileged daemon into a small monitor and an unprivileged child that parses all untrusted input means a bug in the exposed code yields no privilege~\cite{provos2003preventing}. The same principle has been applied to LLM agents, which synthesise a policy from the task and enforce it at every call~\cite{shi2025progent}, attach capabilities to values for an interpreter to check~\cite{debenedetti2025defeating}, separate components of differing trust~\cite{costa2025securing}, confine capabilities with a cut computed over reachability~\cite{xiong2026reachability}, or wrap the agent loop in guardrails~\cite{murugan2026}. Reducing privilege while preserving function has been studied outside agents as well: over-privilege in browser extensions is detected by contrasting declared manifest permissions with the API calls the code makes~\cite{cheng2026percheck}, and program debloating shrinks an artifact under the constraint that a test suite must keep passing~\cite{heo2018effective, sharif2018trimmer}. \textsc{Interlock} also checks every call, but the only thing decided from the task is an allow-list of WRITE tools, and what each call is checked against is a fixed provenance rule over effect labels derived once from code. Unlike Progent it synthesises no argument policy per query and has no step that reads tool outputs to update a policy, so an injection has no path to the policy, and the third party's artifact is never rewritten~\cite{shi2025progent}.

\subsection{Making a Model's Judgement Checkable}
\label{sec:related:verifiable}

코드를 읽고 판정하는 일을 언어 모델에 맡길 때 남는 문제는 그 판정을 무엇으로 믿느냐이며, 이에 대한 답은 크게 두 갈래다. 하나는 모델이 스스로 근거를 인용하게 하고 그 인용을 검증하는 쪽이다. ALCE는 인용 표식을 믿는 대신 인용된 구절이 그 문장을 실제로 함의하는지 검사해 citation recall과 precision을 매기고, 강한 시스템조차 상당한 비율의 문장이 자신이 인용한 근거로 뒷받침되지 않음을 보인다~\cite{gao2023enabling}. 배포된 생성 검색 엔진을 사람이 문장 단위로 대조한 감사에서는 완전히 뒷받침되는 문장이 절반 남짓에 그쳐, 유창하게 인용하는 답과 실제로 확인 가능한 답 사이의 간격이 수치로 남았다~\cite{liu2023evaluating}. 다른 하나는 모델의 출력을 결정적인 외부 검사기에 통과시키는 쪽이다. IRIS는 정적 분석이 스스로 추론할 수 없는 taint source와 sink만 모델에서 받고 실제 경로 계산은 CodeQL에 맡기며~\cite{li2025iris}, LLift는 의도적으로 제약을 푼 분석기가 남긴 후보를 모델이 좁히되 자기 검증을 거치게 한다~\cite{li2024llift}. Baldur는 증명 전체를 한 번에 생성하되 그것이 성립하는지는 증명 보조기가 판정하게 하여, 건전성이 전적으로 외부 검사기에서 나오고 모델은 틀려도 되게 만든다~\cite{first2023baldur}. \textsc{Interlock}의 재검사는 두 번째 갈래에 속하되 검사기가 판정하는 대상이 다르다. 우리는 모델의 결론이 참인지를 검사기에게 묻지 않고, 모델이 인용한 \texttt{file:line}이 그 결론을 실제로 증언하는지만 결정적으로 묻는다.
% When the reading and judging of code is handed to a language model, what remains is the question of what makes its judgement trustworthy, and the answers fall into two lines. One has the model cite its own evidence and then verifies the citation. ALCE declines to trust the citation marker and instead checks whether the cited passage entails the sentence it is attached to, scoring citation recall and precision, and finds that even strong systems leave a substantial fraction of sentences unsupported by what they cite~\cite{gao2023enabling}. An audit in which humans checked every sentence of deployed generative search engines against its sources found only about half fully supported, putting a number on the gap between an answer that cites fluently and one that can be checked~\cite{liu2023evaluating}. The other line passes the model's output through a deterministic external checker. IRIS takes from the model only the taint sources and sinks that static analysis cannot infer for itself and leaves the path computation to CodeQL~\cite{li2025iris}, while LLift has the model narrow the candidates left by a deliberately under-constrained analyser, subject to self-validation~\cite{li2024llift}. Baldur generates a whole proof in one shot and lets the proof assistant decide whether it holds, so that soundness comes entirely from the external checker and the model is free to be wrong~\cite{first2023baldur}. \textsc{Interlock}'s re-checking belongs to this second line, but what the checker decides is different: we do not ask it whether the model's conclusion is true, only --- deterministically --- whether the \texttt{file:line} the model cited actually witnesses that conclusion.

\subsection{Measuring the MCP and Skill Ecosystems}
\label{sec:related:measurement}

생태계를 대상으로 한 실증 연구는 이 층위의 위험이 어디에 얼마나 있는지를 보고한다. 공개된 MCP 서버를 대규모로 수집한 연구들은 취약점 유병률과 분류 체계를 제시하고~\cite{majeed2026empirical, gaire2026systematization}, 서버가 시간에 따라 어떻게 변해 가는지를 추적하며~\cite{liu2026mcpevol}, 공격 쪽에서는 MCP 고유의 공격면을 체계화하고 실제 배포에서 재현한 시연이 축적되었다~\cite{sun2025msa, zhao2026parasites, liu2026sharelock, milanta2025github}. 인접한 에이전트 스킬 생태계도 빠르게 측정되어 취약점 유병률과 자격증명 유출, 공급망 오염이 보고되었고~\cite{liu2026agent, holzbauer2026context, chen2026your, qu2026supply, liu2026not, acharya2026skill}, 페이로드를 여러 스킬에 분산해 아티팩트 단위 검사기를 회피하는 공격~\cite{zeng2026colluskill}과 건전한 능력 상한을 추상 해석으로 계산하려는 시도~\cite{bhardwaj2026formal}가 제시되었다. 다만 스킬에는 도구 목록을 협상하는 프로토콜도 광고된 schema도 없어, 우리가 쓰는 측정 단위 --- 설정이 선언한 서버와 그 서버가 광고한 도구 --- 에 대응하는 대상이 존재하지 않는다. 우리의 코퍼스도 이 갈래에 속하지만 모집단이 다르다. 이들이 표집하는 것은 공개된 서버나 스킬인 반면, 우리가 표집하는 것은 사용자가 실제로 작성해 커밋한 설정이다.
% Empirical work on the ecosystem reports where the risk at this layer lies and how much of it there is. Studies that collect public MCP servers at scale give prevalence figures and taxonomies for vulnerabilities~\cite{majeed2026empirical, gaire2026systematization} and track how servers change over time~\cite{liu2026mcpevol}, while on the offensive side MCP-specific attack surfaces have been systematised and demonstrated on real deployments~\cite{sun2025msa, zhao2026parasites, liu2026sharelock, milanta2025github}. The neighbouring agent-skill ecosystem has been measured just as quickly, with reports of vulnerability prevalence, credential leakage and supply-chain poisoning~\cite{liu2026agent, holzbauer2026context, chen2026your, qu2026supply, liu2026not, acharya2026skill}, an attack that disperses a payload across several skills to evade per-artifact scanners~\cite{zeng2026colluskill}, and an attempt to compute a sound capability bound by abstract interpretation~\cite{bhardwaj2026formal}. A skill, however, has neither a protocol that negotiates a tool list nor an advertised schema, so nothing in it corresponds to our unit of measurement: the servers a configuration declares and the tools those servers advertise. Our corpus belongs to this line too, but samples a different population --- not the published servers or skills, but the configurations users actually wrote and committed.

\section{Conclusion}
\label{sec:conclusion}

본 연구는 \textsc{Interlock}을 제시했다. 도구가 무엇에 닿는지를 제공자가 쓴 글이 아니라 서버의 소스 코드에서 회수하되 모든 주장에 \texttt{file:line} 증거를 요구하고 결정적 검사기로 그 구간을 다시 읽는 Summarize와, 그 라벨을 소비하는 두 집행 규칙 Narrow와 Guard다. 공개 설정에서 가장 자주 선언되는 서버 34개, 도구 433개에 대해 라벨 주장의 72.5\%가 코드로 검증되고, 구현 코드를 배포하는 서버 27개로 한정하면 90.7\%다. AgentDojo에서는 도구 단위 규칙이 아무리 정확해도 targeted ASR을 4.18\% 아래로 내리지 못하므로, Narrow는 사용자 요청만 보고 정한 WRITE 허용 목록 밖의 호출을 거부하고, Guard는 목적지 인자마다 값의 출처를 추적해 공격자가 쓸 수 있는 텍스트에서만 올 수 있는 값을 거부한다. 둘을 함께 두면 세 번의 실행에서 targeted ASR 1.06\%에 utility under attack 61.35\%로, 같은 조건의 Progent는 3.15\%와 58.71\%다. 남는 것은 실행당 공격 10건과 benign 과제 5건이며, 전자는 목적지가 정당하고 내용이나 선택만 악의적인 경우이고 후자는 사용자가 신뢰할 수 없는 페이지에서 목적지를 읽어 쓰라고 지시한 경우로, 값이 어디서 왔는지만 보는 규칙은 이 둘을 구별하지 못한다.
% We presented \textsc{Interlock}: Summarize, which recovers what a tool reaches from the server's source code rather than from prose the provider wrote, requiring \texttt{file:line} evidence for every claim and re-reading the cited span with a deterministic checker, and two enforcement rules, Narrow and Guard, that consume those labels. On the 34 servers and 433 tools most frequently declared in public configurations, 72.5\% of label claims are verified in code, and 90.7\% on the 27 servers that ship their implementation. On AgentDojo no tool-level rule, however exact, brings targeted ASR below 4.18\%, so Narrow refuses a call to any WRITE tool outside an allow-list decided from the user's request alone, and Guard traces the provenance of every destination argument and refuses a value that could only have come from attacker-writable text. Together they reach, over three runs, a targeted ASR of 1.06\% at a utility under attack of 61.35\%, where Progent under the same setting stands at 3.15\% and 58.71\%. What remains is ten attacks and five benign tasks per run: in the former the destination is legitimate and only the content or the choice is hostile, in the latter the user asks for the destination to be read out of an untrusted page, and a rule that looks only at where a value came from cannot tell the two apart.
