\section{Introduction}
\label{sec:intro}

에이전트가 외부 도구를 받아오는 표준은 MCP(Model Context Protocol)다~\cite{gaire2026systematization}. 사용자는 설정 파일에 서버를 적고, 서버마다 그것을 실행할 명령, 서버가 받을 자격증명, 그리고 (일부 서버는) 어떤 도구를 광고할지 정하는 플래그를 함께 적는다. 그러면 호스트가 서버를 띄우고 도구 목록을 받아, 각 도구의 이름과 설명, 스키마를 모델에게 보여준다. 이렇게 한 세션에 모인 도구 전부를 그 배포의 \emph{tool surface}, 곧 모델이 부를 수 있는 도구의 집합이라 부른다. 이 방식은 이미 굳어졌다. 실제 애플리케이션 1,723개 중 85.2\%가 서버 목록을 파일로 두는 반면, 도구 호출을 멈추고 사용자 승인을 받는 차단형 게이트를 두는 것은 37.2\%뿐이다~\cite{majeed2026mcpapps}. 서버 한 줄을 적으면, 대개 그 서버의 도구는 모델이 부르기만 하면 실행된다.
% An LLM agent obtains external tools mainly through the Model Context Protocol (MCP)~\cite{gaire2026systematization}. A user lists servers in a configuration file, giving for each the command that starts it, the credentials it receives and, for some servers, flags that decide which of its tools are advertised. The host then starts each server, retrieves its tool list, and shows the model each tool's name, description and schema. We call the tools assembled for one session the deployment's \emph{tool surface}, the set of tools the model may call. This arrangement is settled: of 1,723 real applications, 85.2\% keep their server list in a file, while only 37.2\% put a blocking approval gate in front of a tool call~\cite{majeed2026mcpapps}. Listing one server therefore usually means its tools run on the model's call alone.

그림~\ref{fig:example}이 우리가 다루는 상황을 보인다. 개발자가 코딩 에이전트에 GitHub MCP 서버 하나를 붙인다~(\stepnum{1}). 목적은 평범하다. 자기 저장소의 열린 이슈를 정리하는 것이다. 설정에는 서버 한 줄뿐이지만, 호스트가 받아 오는 도구는 우리가 계측한 버전 기준 26개이고 모두 모델이 부를 수 있다~(\stepnum{2}). 이 중 셋이 모이면 유출 경로가 된다. \texttt{list\_issues}는 누구나 쓸 수 있는 공개 이슈를 컨텍스트로 들여오고~(\stepnum{3}), \texttt{get\_file\_contents}는 같은 토큰으로 비공개 저장소를 읽으며~(\stepnum{4}), \texttt{create\_pull\_request}는 그 내용을 공격자가 볼 수 있는 곳에 쓴다~(\stepnum{5}). 공격자가 공개 이슈에 지시문을 심어 두면, 에이전트는 그 이슈를 읽다가 지시를 따른다. 이런 경로는 손대지 않은 GitHub MCP 서버 하나만 연결한 상태에서 실제로 시연되었다~\cite{milanta2025github}. 레지스트리 규모 조사도 한 서버가 외부 유입과 비공개 접근, 외부 전송을 동시에 가질 수 있어 서버 사이 협조 없이 공격이 완성된다고 보고한다~\cite{zhao2026parasites}. 그러나 이 세 도구는 어느 것도 그 자체로 잘못이 아니고, 사용자가 원한 이슈 정리에는 26개 중 몇 개면 충분하다.
% Figure~\ref{fig:example} shows the situation we address. A developer connects one GitHub MCP server to a coding agent~(\stepnum{1}) for an ordinary purpose: to triage the open issues of their own repository. The configuration holds a single server, but the host retrieves 26 tools in the version we measured, every one callable by the model~(\stepnum{2}). Three of them form a leak. \texttt{list\_issues} brings a publicly writable issue into the context~(\stepnum{3}), \texttt{get\_file\_contents} reads a private repository with the same token~(\stepnum{4}), and \texttt{create\_pull\_request} writes the result where the attacker can read it~(\stepnum{5}). If the attacker has planted instructions in a public issue, the agent follows them while reading it. A path of this shape has been demonstrated with a single unmodified GitHub MCP server~\cite{milanta2025github}, and a registry-scale census likewise reports that one server can hold external ingestion, private access and egress at once, completing an attack without cross-server coordination~\cite{zhao2026parasites}. Yet no one of these tools is wrong on its own, and the triage the user wanted needs only a few of the 26.

이 위험을 다루는 연구는 많고, 대부분 도구 단위로 판정한다. 광고된 설명에서 숨은 지시와 이름 가로채기, 유출 지점을 찾아내 신뢰할 수 있는 설명을 다시 만들고~\cite{jain2026detecting, ye2026trustdesc, wang2026mcptox}, 서버 구현 안에서 신뢰할 수 없는 입력이 민감한 연산에 닿는 결함을 정적으로 추적한다. 후자는 파일 단위로 나오던 taint 경고를 개별 도구 핸들러까지 해소하는 것 자체가 기여일 만큼 도구 단위 정밀도를 목표로 삼는다~\cite{sun2026viper}. 실행 중 도구 동작을 감사하는 연구도 있다~\cite{tan2026sandscope}. 그러나 이들이 답하는 질문은 ``이 도구가 악의적이거나 결함이 있는가''이다. 그림~\ref{fig:example}의 세 도구는 어느 쪽도 아니다. \stepnum{4}가 비공개 저장소를 읽는 것은 그 도구가 명세대로 동작하는 것이고, 시연을 보고한 저자들도 ``서버 코드의 결함이 아니다''라고 적었다~\cite{milanta2025github}. 악의나 결함을 찾는 검사로는 이 설정에서 무엇을 꺼야 하는지가 나오지 않는다.
% Much research addresses this risk, and most of it judges at the granularity of a tool. It finds hidden instructions, shadowed names and exfiltration endpoints in advertised descriptions and regenerates trusted ones~\cite{jain2026detecting, ye2026trustdesc, wang2026mcptox}, and it statically traces defects inside a server implementation where untrusted input reaches a sensitive operation --- work whose contribution is precisely to resolve file-level taint alerts down to the individual tool handler~\cite{sun2026viper}. Others audit tool behaviour as it runs~\cite{tan2026sandscope}. The question they answer, however, is whether a tool is malicious or defective. Neither holds of the three tools in Figure~\ref{fig:example}: \stepnum{4} reading a private repository is that tool working as specified, and the authors who reported the demonstration say as much, that it is ``not a flaw in the server code''~\cite{milanta2025github}. A check for malice or defects does not say what to switch off in this configuration.

무엇을 꺼야 하는지를 실제로 계산하는 연구는 최소 권한 쪽에 있다. Progent는 사용자의 작업에서 도구 이름과 인자에 대한 규칙을 LLM으로 자동 생성하고 호출마다 검사한다~\cite{shi2025progent}. CaMeL은 신뢰된 질의에서 제어 흐름과 데이터 흐름을 추출해 능력 기반으로 유출을 막고~\cite{debenedetti2025camel}, Fides는 기밀성과 무결성 라벨을 호출 단위로 추적해 집행한다~\cite{costa2025fides}. 셋 다 도구 단위로 권한을 좁히며, 그 점에서 우리가 하려는 일과 목표가 같다. 그런데 셋 다 같은 것을 전제한다. 각 도구가 무엇에 닿는지를 이미 누군가 말해 주었다는 것이다. Fides는 이를 가정으로 명시한다. 신뢰할 수 없는 모든 도구에 신뢰된 wrapper를 두어 ``모든 도구가 자기 출력에 올바로 라벨을 붙인다고 가정할 수 있게 한다''는 것이다. CaMeL의 능력 표시는 사용 사례마다 사람이 정하며, 저자들은 이를 한계로 적고 자동화를 향후 과제로 남긴다. Progent의 정책 생성기가 받는 것은 작업과 도구 집합, 곧 제공자가 쓴 이름과 설명과 스키마다. 그리고 그 세 연구의 평가 대상은 실제 MCP 서버가 아니라 벤치마크 안에 정의된 가상 도구 모음이어서, 설명과 구현을 같은 사람이 같은 파일에 쓴다. 전제가 구조적으로 참인 환경인 것이다.
% The work that does compute what to switch off is on the least-privilege side. Progent has an LLM generate rules over tool names and arguments from the user's task and checks every call against them~\cite{shi2025progent}; CaMeL extracts control and data flow from the trusted query and blocks exfiltration through a capability system~\cite{debenedetti2025camel}; and Fides tracks and enforces confidentiality and integrity labels per call~\cite{costa2025fides}. All three narrow privilege at the granularity of a tool, which is the goal we share. All three also presuppose the same thing: that someone has already stated what each tool reaches. Fides states it as an assumption, giving every untrusted tool a trusted wrapper so that it ``can assume that all tools label their outputs correctly''. CaMeL's capability annotations are chosen by hand per use case, and its authors record this as a limitation and leave automation to future work. What Progent's policy generator receives is the task and the tool set, that is, the names, descriptions and schemas the provider wrote. Moreover, these systems are evaluated on simulated tool suites defined inside a benchmark rather than on real MCP servers, where the description and the implementation are written by the same author in the same file, so the presupposition holds by construction.

그 전제를 채워 주는 것이 없다. 실제 서버의 도구마다 무엇에 닿는지를 기계가 읽을 수 있는 형태로 내놓으려는 시도는, 우리가 아는 한 하나뿐이다. \texttt{mcp-sec-audit}은 TOML 규칙집의 키워드와 정규식으로 \texttt{file\_read}, \texttt{network\_outbound}, \texttt{command\_exec} 같은 능력 범주를 서버에서 뽑는다~\cite{huang2026audit}. 저자들이 스스로 보고한 한계가 결정적이다. Python 서버에서는 2개 중 2개를 탐지하지만 JavaScript 서버에서는 7개 중 0개, 곧 0\%다. 그런데 사람들이 실제로 선언하는 서버는 대부분 npm이다. 우리 코퍼스에서 npm 항목이 22,010개, PyPI가 3,156개다. 출력 또한 위험 점수와 일반적인 강화 권고이며, 저자들의 표현으로 ``배포 가능한 설정을 생성하지 않는다''. 주장을 코드로 되짚는 장치도 없다. 남는 그림은 이렇다. 호스트는 도구를 하나씩 끌 수 있게 해 주고, 조사된 애플리케이션의 77.2\%가 서버 또는 도구를 켜고 끄는 명시적 제어를 둔다~\cite{majeed2026mcpapps}. 최소 권한 연구는 그 제어에 넣을 정책을 만들 줄 안다. 정작 양쪽이 모두 필요로 하는 도구별 효과 지식만 아무도 만들지 않는다. 그 결과 세밀한 제어는 있어도 쓰이지 않아서, 우리 코퍼스에서 GitHub 서버를 선언한 항목 189개 가운데 읽기 전용 모드를 켠 것은 3개, 더 좁은 toolset을 고른 것은 12개뿐이다(\S\ref{sec:measurement}).
% Nothing supplies that presupposition. To our knowledge only one line of work tries to state, in machine-readable form, what each tool of a real server reaches: \texttt{mcp-sec-audit} extracts capability categories such as \texttt{file\_read}, \texttt{network\_outbound} and \texttt{command\_exec} from a server using the keywords and regular expressions of a TOML rulebook~\cite{huang2026audit}. The limitation its authors report is decisive: it detects 2 of 2 on Python servers and 0 of 7, that is 0\%, on JavaScript ones. Yet the servers people actually declare are mostly npm --- 22,010 npm entries against 3,156 PyPI entries in our corpus. Its output is a risk score and generic hardening advice, and in its authors' words it ``does not generate deployment-ready configurations''; nor does it re-check its claims against code. The picture that remains is this. Hosts let a user switch off one tool at a time, and 77.2\% of surveyed applications keep an explicit enable/disable control over servers or tools~\cite{majeed2026mcpapps}. Least-privilege work knows how to produce a policy to put into that control. What nobody produces is the per-tool effect knowledge both sides need. The fine-grained controls accordingly go unused: of the 189 entries in our corpus that declare the GitHub server, 3 set its read-only mode and 12 select a narrower toolset (\S\ref{sec:measurement}).

이 논문에서 우리는 \textsc{Interlock}을 제시한다. 도구가 무엇에 닿는지를 제공자가 쓴 글이 아니라 서버의 소스 코드에서 회수하되 모든 주장을 기계적으로 재검사하고, 그렇게 얻은 효과 요약이 실제로 쓸 수 있는 정보임을 설정 변경을 계산해 보이는 접근이다. \emph{Summarize}는 신뢰도 순으로 정렬한 증거에서 도구마다 어떤 효과에 닿는지를 판정하고, 판정마다 그것을 뒷받침하는 코드 위치를 남긴다. 이 요약은 그 자체로 앞 문단의 빈자리를 채우는 산출물이며, 런타임 최소 권한 시스템이 사람 손으로 채우던 라벨을 대신할 수 있다. 우리는 이어서 그 요약이 설정 수준에서 실행 가능함을 보인다. \emph{Decide}는 설정이 지정한 값 수준 조건을 적용한 뒤 요약 위에서 흐름 정책을 평가해 금지된 흐름마다 그것을 만드는 도구를 짚고(그림의 \stepnum{3}--\stepnum{5}), \emph{Repair}는 호스트와 서버가 이미 가진 수단 --- 도구 거부 항목, 서버 모드와 toolset 플래그, 인자 축소, 마지막 수단인 서버 제거 --- 위에서 선언된 작업을 지키는 최소 비용 patch를 만들어 설정 diff로 내보낸다~(\stepnum{6}). 집행에 호스트를 고칠 필요는 없다.
% In this paper we present \textsc{Interlock}, an approach that recovers what a tool reaches from the server's source code rather than from prose the provider wrote, re-checks every claim mechanically, and then shows that the resulting effect summaries are usable information by computing a configuration change from them. \emph{Summarize} judges, from evidence ranked by trust, which effects each tool can reach, and records for every judgement the code location that supports it. These summaries are themselves the artifact the previous paragraph finds missing, and they can stand in for the labels that run-time least-privilege systems fill in by hand. We then show that they are actionable at the level of a configuration. \emph{Decide} applies the value-level conditions the configuration sets, evaluates a flow policy over the summaries and points to the tools that make each forbidden flow (\stepnum{3}--\stepnum{5} in the figure), and \emph{Repair} builds a minimum-cost patch over the controls hosts and servers already have --- per-tool deny entries, server mode and toolset flags, argument narrowing, and server removal as a last resort --- subject to preserving the declared tasks, and emits it as a configuration diff~(\stepnum{6}). Enforcement needs no change to the host.

핵심 난점은 그 정보가 선언되어 있지 않다는 것이다. 효과를 코드에서 읽어내야 하는데, 두 길 모두 쉽지 않다. 공개 패키지를 전부 정적 분석으로 따라가면 규모가 맞지 않고, 언어 모델에 읽히면 그 판정을 무엇으로 믿느냐가 남는다. 우리는 \emph{신뢰도 순위 요약과 결정적 재검사}를 묶어 이를 푼다. 모델이 서버의 소스를 읽고 도구별 효과를 판정하되 주장마다 \texttt{file:line} 증거를 달게 하고, 결정적 검사기가 가져온 소스에서 그 줄을 다시 읽어 확인되지 않는 주장을 걸러낸다. 확인되지 않은 주장은 버리지 않고 ``미확인''으로 표시해 라벨을 지키며, 모델이 판정하지 않은 도구에는 가장 보수적인 값을 준다. 문서만 근거로 한 ``무해'' 판정은 무해로 세지 않는다. 문서는 효과가 없다는 것을 증명하지 못하기 때문이다. 그래서 출력은 그럴듯한 요약이 아니라, 독자가 코드 한 줄까지 되짚을 수 있는 감사 가능한 기록이 된다.
% The central difficulty is that this information is not declared, so effects must be read out of code, and neither route is easy: following every published package by static analysis does not scale, and handing the code to a language model leaves open what makes its judgement trustworthy. We solve this by pairing \emph{trust-ranked summarisation with deterministic re-checking}. The model reads the server's source and judges each tool's effects, but must cite \texttt{file:line} evidence for every claim, and a deterministic checker re-reads the cited span in the fetched source and drops what it cannot confirm. \section{Background and Threat Model}
\label{sec:background}

\subsection{Tool surfaces and who decides them}

호스트 애플리케이션 --- IDE 어시스턴트, 데스크톱 에이전트, 코딩 에이전트 --- 은 설정 파일에 명시된 각 Model Context Protocol 서버를 실행하고 도구 목록을 요청한 뒤, 반환된 이름과 설명, JSON 스키마를 모델의 컨텍스트에 넣는다. 서버는 명령줄로 실행되는 로컬 프로세스일 수도, 컨테이너일 수도, 원격 엔드포인트일 수도 있으며, 스킬 번들이 서버를 추가로 기여하기도 한다. 한 세션에서 광고된 도구들의 합집합을 우리는 그 배포의 \emph{tool surface}라 부른다. 이 구조의 세 가지 성질이 이후 논의를 이끈다. surface는 개별 제공자가 아니라 사용자의 설정이 결정한다. surface 위의 모든 도구는 호출 가능하다. 도구 선택은 광고된 텍스트를 읽은 모델이 하기 때문이다. 그리고 surface는 고정되어 있지 않다. 호스트는 대개 버전을 고정하지 않은 패키지 지정으로 서버를 실행하므로, 도구 뒤의 코드는 사용자가 아무 행동을 하지 않아도 세션 사이에 바뀔 수 있다.
% A host application --- an IDE assistant, a desktop agent, a coding agent --- starts each Model Context Protocol server named in a configuration file, asks it for its tool list, and places the returned names, descriptions and JSON schemas into the model's context. A server may be a local process started by a command line, a container, or a remote endpoint; a skill bundle may contribute further servers. The union of the advertised tools, for the session, is what we call the deployment's \emph{tool surface}. Three properties of this arrangement drive the rest of the paper. The surface is decided by the user's configuration rather than by any single provider. Every tool on it is callable, because tool choice is made by the model from the advertised text. And the surface is not fixed: hosts commonly launch servers from an unpinned package specification, so the code behind a tool can change between sessions without any action by the user.

\subsection{Threat model}

우리는 에이전트가 자신이 읽은 콘텐츠 안의 지시를 따른다고 가정한다. 이는 lethal trifecta 프레이밍~\cite{willison2025trifecta}과 toxic-flow 분석~\cite{beurerkellner2025toxicflow}이 전제하는 가정이며, 이 층위에 대해 공개된 공격들이 실제로 악용하는 가정이다~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. 공격자는 임의의 웹 호스트와 콘텐츠를 통제하고, 여러 사람이 쓸 수 있거나 제3자가 제공하는 출처의 콘텐츠 --- 공개 이슈와 댓글, 저장소 내용, 커뮤니티 문서와 레지스트리, 검색 결과 --- 도 통제한다. 공격자는 사용자의 로컬 파일이나 사용자 계정에 담긴 데이터를 통제하지 못하며, 설치된 서버를 수정하지도 못한다. 공격자는 자신이 통제하는 호스트와 공개된 모든 것을 읽을 수 있다. 이 가정 아래에서, 어떤 배포의 surface가 한 세션 안에서 비공개 데이터 출처, 공격자가 통제하는 콘텐츠 출처, 공격자가 읽을 수 있는 목적지에 모두 닿을 때 그 배포는 위험하다. 우리는 그런 surface를 \emph{trifecta-complete}라 부르고, 자기 도구만으로 충분한 제공자를 \emph{capability-bundling}이라 부른다.
% We assume an agent that follows instructions found in the content it reads, which is the assumption under which the lethal-trifecta framing~\cite{willison2025trifecta} and toxic-flow analysis~\cite{beurerkellner2025toxicflow} are stated, and which published attacks on this layer exploit~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. The attacker controls arbitrary web hosts and content, and content in multi-writer or third-party sources: public issues, comments and repository content, community documentation and registries, search results. The attacker does not control the user's local files or the data held in the user's own accounts, and does not modify the installed servers. The attacker can read hosts they control and anything published publicly. Under these assumptions a deployment is dangerous when its surface reaches, in the same session, a source of private data, a source of attacker-controlled content, and a destination the attacker can read; we call such a surface \emph{trifecta-complete}, and a provider whose own tools suffice \emph{capability-bundling}.

\section{How Dangerous Are Real Configurations?}
\label{sec:measurement}

\subsection{Study design}

이 절의 코퍼스가 하는 첫 번째 일은 피험자 선정이다. 어떤 서버를 읽을 가치가 있는지를 저자의 판단이 아니라 공개 설정에 등장하는 빈도로 정한다. 그 위에서 우리는 앞 절에서 정의한 두 성질도 측정하지만, 그 비율은 이차적 증거이며 \S\ref{sec:threats}가 적는 표집 한계 안에서 읽어야 한다. 우리는 위에서 정의한 두 성질을, 사람들이 실제로 작성한 설정에서 측정한다. 현재 호스트들이 읽는 설정 형식 다섯 가지(\texttt{.mcp.json}, \texttt{.cursor/mcp.json}, \texttt{.vscode/mcp.json}, \texttt{claude\_desktop\_config.json}, 그리고 \texttt{.codex/config.toml}의 \texttt{[mcp\_servers]} 테이블)를 공개 GitHub에서 검색하고, 각 파일을 메모리에서 파싱해 서버의 식별자와 실행 형태만 보관한다. 자격증명은 저장하지 않는다. 검색은 85,065개의 파일을 보고했고, API의 질의당 상한 아래에서 22,552개를 받을 수 있었으며, 21,015개가 파싱되고, 포크와 저장소 내 중복 서버 집합을 제거한 뒤 19,777개가 남았다. 표~\ref{tab:corpus}가 코퍼스를 요약한다.

\subsection{Results}

\emph{분석 가능한 설정의 대부분이 trifecta-complete이다.} 판정 대상 서버 17개로만 구성된 설정 880개 --- 우리가 수집한 다중 서버 설정의 10분의 1 --- 가운데 \textbf{84.1\%}(740개)가 trifecta-complete이다. 코드로 확정하지 못한 효과를 양극단으로 밀어도 값은 84.0\%에서 85.6\% 사이로만 움직인다. 사용자 자신의 데이터베이스와 워크스페이스 안의 레코드도 공격자가 쓸 수 있다고 보는 두 번째 위협 모델 변형에서도 값은 84.1\%로 변하지 않는데, 해당 서버들이 이미 다른 경로로 세 효과 모두에 닿기 때문이다.
% \emph{Most analysable configurations are trifecta-complete.} Of the 880 configurations composed entirely of the 17 adjudicated servers --- one in ten of the multi-server configurations we collected --- \textbf{84.1\%} (740) are trifecta-complete. Pushing every effect we could not settle from code to either extreme moves the figure only between 84.0\% and 85.6\%. A second variant of the threat model, in which records inside the user's own databases and workspaces are also treated as attacker-writable, leaves the figure unchanged at 84.1\%, because those servers already reach all three effects by other means.

\emph{존재하는 제어 수단은 쓰이지 않고, 주요 원인 서버에는 아예 없다.} 코드 호스팅 서버는 읽기 전용 모드를 제공하지만 항목 189개 중 3개만 이를 설정하고 12개가 더 좁은 toolset을 선택한다. 데이터베이스 서버는 읽기 전용 모드를 제공하며 항목 116개 중 32개가 이를 설정한다. 코딩 에이전트 서버는 이름이 지정된 대부분의 context에서 셸 도구를 비활성화하는데, 항목 111개 중 84개가 그런 context를 선택한다. 채택률이 높은 유일한 사례다. 브라우저 자동화 서버에는 자기 프로세스 안에서 코드를 실행하는 도구를 제거하는 플래그가 없으며, archived 코드 호스팅 서버와 컴포넌트 레지스트리 서버, fetch 서버는 제한을 거는 플래그를 전혀 제공하지 않는다.
% \emph{The controls that exist are unused, and for the main drivers they do not exist.} The code-hosting server offers a read-only mode; 3 of 189 entries set it, and 12 select a narrower toolset. The database server offers a read-only mode; 32 of 116 entries set it. The coding-agent server disables its shell tool in most of its named contexts, and 84 of 111 entries select such a context --- the one case where adoption is high. % \emph{The surface is not static.} Across 64 consecutive releases of one widely configured server, 45 changed the advertised surface and only 2 changed descriptions alone; a published benchmark reports that 54.6\% of initial tools were modified or deprecated across 9,273 versions of 515 servers~\cite{liu2026mcpevol}. Meanwhile 91.3\% of stdio entries name no version, so the code behind a tool changes without the user acting. Hash-based pinning reacts to all of this: replaying our corpus against recovered version histories produces about 23 change alerts per configuration over an 18-month window.

\emph{레지스트리 규모 조사와의 대조.} 서버 1,360개의 도구 12,230개를 대상으로 한 조사는 한 서버가 세 능력을 동시에 가질 수 있고 그 경우 서버 사이 협조 없이 공격을 완성할 수 있다고 보고하면서, 그런 서버를 2개로 센다~\cite{zhao2026parasites}. 우리의 비율이 훨씬 높은 이유는 두 가지다. 그 조사는 레지스트리에서 서버를 균등하게 표집하지만 우리는 사람들이 실제로 설치하는 빈도로 가중치를 준다. 또한 우리는 도구 메타데이터가 아니라 소스 코드에서 효과를 도출하므로, 광고된 도구에서 도달 가능한 호스트 코드 실행이나 브라우저·fetch 도구가 로컬 URL로 얻는 파일 내용처럼 메타데이터 수준 분류기가 보지 못하는 효과를 센다. 두 결과는 방향에서 일치하고 비율에서 갈리며, 어느 쪽이든 단일 서버가 충분하다는 결론은 같다.
% \emph{Comparison with a registry-scale census.} A census of 12,230 tools across 1,360 servers reports that a server can hold all three capabilities at once and then complete an attack without cross-server coordination, but counts two such servers~\cite{zhao2026parasites}. Our rate is far higher for two reasons. That census samples servers uniformly from registries, whereas we weight them by how often people install them; and we derive effects from source code rather than tool metadata, so we count effects a metadata-level classifier does not see, such as host code execution reachable from an advertised tool, or file content a browser or fetch tool obtains through a local URL. The two results agree in direction and differ in rate, and either way a single server suffices.

\subsection{What this rules out}

이 수치들은 설계 공간을 세 가지 방식으로 제약한다. 이 기저율에서 경고는 정보를 주지 못한다. 집합 단위 trifecta 검사는 이 설정들의 84\%에 경고를 띄우고, 사용자가 할 수 있는 일은 무시하는 것뿐이다. 실제로 어떤 벤더 검사기는 바로 이 점을, 즉 대부분의 에이전트가 세 특성을 모두 가지므로 각 구성요소를 개별적으로 분석한다고 밝힌다~\cite{snyk2026agentscan}. 서버 제거는 지나치게 거칠다. 판정을 좌우하는 서버들이 사용자가 의도적으로 설치한 것들이기 때문이다. 그리고 조합 지향 방어가 함의하는 해법인 제공자 사이 흐름 차단은 740개 설정 전부를 여전히 trifecta-complete로 남긴다. 남는 길은 사용자가 유지하는 제공자 \emph{내부에서} surface를 좁히는 것이며, 그것이 \textsc{Interlock}이 하는 일이다.
% These numbers constrain the design space in three ways. Alerting is uninformative at this base rate: a set-level trifecta check flags 84\% of these configurations, which is a warning a user can only dismiss --- a vendor scanner states exactly this, that most agents possess all three characteristics and that it therefore analyses each component separately~\cite{snyk2026agentscan}. Removing servers is too coarse, since the servers that drive the verdict are the ones users installed on purpose. And severing cross-provider flows, the remedy implied by composition-oriented defences, would leave every one of the 740 configurations trifecta-complete. What remains is to narrow the surface \emph{inside} the providers a user keeps, which is what \textsc{Interlock} does.

\section{Approach}
\label{sec:approach}

\subsection{Overview}

\textsc{Interlock}은 설정, 흐름 정책, 배포가 선언한 작업을 입력으로 받아, 호스트와 서버가 이미 제공하는 제어 수단 위의 patch를 반환한다. 절차는 세 단계다. \emph{Summarize}는 신뢰도 순으로 정렬한 증거에서 도구별 효과 요약을 도출한다. \emph{Decide}는 설정이 유도한 surface에 대해 정책을 평가하고 각 금지 흐름을 증언하는 도구를 반환한다. \emph{Repair}는 최소 비용 patch --- 도구 단위 거부 항목, 서버 모드와 toolset 플래그, 인자 축소, 그리고 가장 비싼 선택지인 서버 제거 --- 를 탐색해 금지된 흐름을 제거하면서 선언된 작업이 계속 동작하도록 한다. 이 논문은 \emph{Summarize}를 구현·평가하며, \emph{Decide}와 \emph{Repair}는 여기서 명세하고 진행 중인 작업으로 남겨 두되, 두 단계에 관한 모든 진술은 그에 맞게 표시한다.
% \textsc{Interlock} takes a configuration, a flow policy and the deployment's declared tasks, and returns a patch over the controls that hosts and servers already expose. It proceeds in three stages. \emph{Summarize} derives a per-tool effect summary from evidence ranked by trust. \emph{Decide} evaluates the policy over the surface the configuration induces and returns the tools that witness each forbidden flow. \emph{Repair} searches for a minimum-cost patch --- per-tool deny entries, server mode and toolset flags, argument narrowing, and, as the most expensive option, server removal --- that removes the forbidden flows while keeping the declared tasks working. This paper implements and evaluates \emph{Summarize}; \emph{Decide} and \emph{Repair} are specified here and are the subject of ongoing work, and we mark every claim about them accordingly.

\subsection{Summarize: trust-ranked effect summaries}

이 단계는 광고된 도구마다 하나의 질문에 답한다. 이 도구는 SECRET, UNTRUSTED, SINK, HOSTEXEC 가운데 무엇에 닿을 수 있으며 그 증거는 무엇인가. 증거는 공격자가 얼마나 통제할 수 있는지에 따라 순위가 매겨진다. 설정 자신의 인자와 서버의 소스 코드가 1순위, 선언된 스키마와 annotation이 2순위이며, 자유 서술 설명은 효과를 낮추는 데 결코 쓰이지 않는다. 올리는 데만 쓸 수 있는데, 설명은 판정 대상인 당사자가 작성하기 때문이다. HOSTEXEC은 나머지 셋을 함의한다. 호스트에서의 코드 실행은 호스트가 닿을 수 있는 모든 것에 닿기 때문이다.
% The stage answers one question per advertised tool: which of SECRET, UNTRUSTED, SINK and HOSTEXEC can this tool reach, and what is the evidence? Evidence is ranked by how much an attacker controls it. The configuration's own arguments and the server's source code rank first, declared schemas and annotations second, and free-text descriptions are never allowed to lower an effect --- they may only raise one, because a description is written by the party being judged. HOSTEXEC implies the other three, since host code execution reaches whatever the host can reach.

요약은 언어 모델이 생성하되 모든 주장에 \texttt{file:line} 증거를 인용해야 하며, 이후 결정적 검사기가 가져온 소스에서 인용된 구간을 다시 읽어 걸러낸다. 인용이 가져온 트리 안에서 해석되지 않거나, 그 구간에 도구 이름이나 근거 설명이 지목한 식별자가 없으면, 그 주장은 유지되되 미확인으로 표시된다. 미확인 주장이 효과를 낮춰서는 안 되므로 라벨은 살아남지만, 검증된 것으로는 세지 않는다. 모델이 아예 판정하지 않은 도구에는 가장 보수적인 값인 HOSTEXEC을 부여한다. 모델이 라벨 없이 무해하다고 판정한 도구는 그 증거가 코드에서 해석될 때만 무해로 센다. 문서는 효과의 \emph{부재}를 입증할 수 없기 때문이다. 이 구분이 이 단계의 출력을 그럴듯한 것이 아니라 감사 가능한 것으로 만들며, 5절은 그중 얼마가 검사기를 통과하는지 측정한다.
% Summaries are produced by a language model that must cite \texttt{file:line} evidence for every claim, and are then filtered by a deterministic checker that re-reads the cited span in the fetched source. A claim whose citation does not resolve inside the fetched tree, or whose span does not contain the tool name or an identifier the rationale names, is kept but marked undetermined; the label survives, because an unverified claim must not lower an effect, but it no longer counts as verified. A tool the model does not judge at all is assigned HOSTEXEC, the least restrictive reading. A tool the model clears with no labels counts as cleared only when its evidence resolves in code: documentation cannot establish the \emph{absence} of an effect. This split is what makes the stage's output auditable rather than merely plausible, and Section~\ref{sec:eval} measures how much of it survives the checker.

실무적으로 중요한 세부가 둘 있다. 모델에게는 모든 줄에 실제 줄 번호를 붙인 소스를 보여준다. 줄 번호가 없으면 인용된 줄이 파일 뒤로 갈수록 어긋나고, 올바른 판정이 검증에 실패하기 때문이다. 또한 패키지 자신의 코드가 도구 이름을 전혀 언급하지 않는 경우 --- 구현이 의존성에 있는 래퍼 패키지가 그렇다 --- 그 이름을 언급하는 직접 의존성을 스크립트 실행을 끈 채 가져와 함께 보여준다. 파이프라인의 어느 지점에서도 제공자 코드는 실행되지 않는다.
% Two details matter in practice. The model is shown source with every line prefixed by its true line number, because without them cited lines drift with depth and correct judgements fail verification. And when a package's own code never mentions a tool name --- the case for wrapper packages whose implementation lives in a dependency --- the direct dependencies that do mention it are fetched and shown, with scripts disabled; provider code is never executed at any point in the pipeline.

\subsection{Decide and Repair (planned)}

\emph{Decide}는 설정이 지정한 값 수준 조건 --- 읽기 전용 모드, toolset 선택, 경로 root, origin 허용 목록 --- 을 적용한 뒤 설정이 유도한 surface에 대해 배포자의 정책을 평가하고, 금지된 흐름마다 그것을 증언하는 도구를 반환할 것이다. \emph{Repair}는 선언된 작업의 보존을 조건으로 사용 가능한 제어 수단 위에서 최소 비용 patch를 탐색하고, 후보 patch마다 다시 판정해 결과가 가정이 아니라 검증된 것이 되게 하며, patch를 설정 diff로 내보낼 것이다. 우리는 두 단계를 서버 통째 제거, 서버 모드만 사용하는 방식, 이름 기반 휴리스틱 거부 목록, 동일 정책 하의 실행 시점 집행과 비교해, patch 전후의 benign utility, 공격 하 utility, 표적 공격 성공률을 측정할 계획이다.
% \emph{Decide} will evaluate the deployer's policy over the surface induced by a configuration, after applying the value-level conditions that configuration sets --- read-only modes, toolset selections, path roots, origin allow-lists --- and return, for each forbidden flow, the tools that witness it. \emph{Repair} will search for a minimum-cost patch over the available controls subject to preserving the declared tasks, re-deciding after each candidate patch so that the result is verified rather than assumed, and will emit the patch as a configuration diff. We plan to evaluate both against whole-server removal, server modes alone, a name-based heuristic deny list, and run-time enforcement under the same policy, measuring benign utility, utility under attack and targeted attack success rate before and after the patch.

\section{Evaluation of the Summarize Stage}
\label{sec:eval}

\subsection{Research question and setup}

여기서는 하나의 질문을 던진다. \textbf{RQ1.} 모델의 효과 판정 가운데 얼마가 제공자의 소스에 대한 결정적 재검사를 통과하며, 어떤 제공자에서 이 절차가 실패하는가? 우리는 광고된 surface를 복원할 수 있었던, 가장 자주 설정되는 npm 및 PyPI 서버 34개, 총 433개의 광고된 도구를 대상으로, 고정된 rubric과 JSON 스키마를 사용하는 Claude Opus~5, 패키지당 400\,KB의 소스 예산, 그리고 4절에서 설명한 검사기로 프로파일을 만든다. 광고된 각 도구는 정확히 하나의 범주에 들어간다. 모델이 라벨을 주장했고 인용이 코드에서 해석된 경우(\emph{verified}), 문서에서만 해석된 경우(\emph{verified\_doc}), 해석되지 않은 경우(\emph{demoted}), 모델이 무해로 판정했고 코드 증거가 있는 경우(\emph{cleared verified}) 또는 없는 경우(\emph{cleared unverified}), 그리고 모델이 판정하지 않은 경우(\emph{unjudged})다. 광고된 surface에 없는 이름을 판정한 경우는 별도로 센다. 기준과 정의는 실행 전에 사전 등록했으며, 계획서가 정한 dry-run에서 발견된 측정 도구 변경은 모두 실행 이후가 아니라 이전에 기록했다.
% We ask one question here: \textbf{RQ1.} How much of a model's effect judgement survives deterministic re-checking against the provider's source, and for which providers does the procedure fail? We profile the 34 most frequently configured npm and PyPI servers whose advertised surface we could recover, 433 advertised tools in total, using Claude Opus~5 with a fixed rubric and a JSON schema, a 400\,KB per-package source budget, and the checker described in Section~\ref{sec:approach}. Each advertised tool falls into exactly one bucket: the model claimed labels for it and the citation resolved in code (\emph{verified}), resolved only in documentation (\emph{verified\_doc}), or did not resolve (\emph{demoted}); or the model cleared it, with (\emph{cleared verified}) or without (\emph{cleared unverified}) code evidence; or the model did not judge it (\emph{unjudged}). Judged names absent from the advertised surface are counted separately. Thresholds and definitions were registered before the run, and every change to the instrument found by the prescribed dry-runs was recorded before the run rather than afterwards.

\subsection{Threats to validity}
\label{sec:threats}

\emph{코퍼스.} GitHub 코드 검색은 질의당 결과 수에 상한을 두고 표집이 아니라 관련도 순위로 반환하므로, 이 코퍼스는 배포의 무작위 표본이 아니다. 커밋된 설정은 사람들이 실제로 실행하는 설정과 다를 수도 있다. \emph{판정 대상 집합.} 효과는 가장 자주 설정되는 서버 17개(측정)와 34개(평가)에 대해서만 도출했으므로, 유병률 수치는 인기 서버로 구성된 설정을 설명하며 롱테일을 설명하지 않는다. \emph{위협 모델.} 유병률 수치는 최악 가정의 에이전트 아래에서 광고된 surface가 갖는 성질이다. 특정 배포가 공격을 당했다거나 공격이 성공한다고 주장하지 않으며, 악용 가능성 확인은 향후 과제다. \emph{검사기.} 검사기는 한 방향으로 엄격하고 다른 방향으로 느슨하다. 강등 81건 중 약 9건은 인용 구간에 해당 식별자가 더 긴 표현 안에 실제로 존재하지만 토큰 일치가 이를 놓친 경우이고, 반대로 코드로 검증된 판정 308건 중 4건은 네 글자 이하의 토큰에 기대고 있다. \emph{발췌.} 큰 파일에 대해서는 이름이 등장하는 지점 주변 창만 보여주므로, 큰 파일에 존재하는 도구 이름 11개는 모델에게 한 번도 보이지 않았다. 따라서 의존성 추적의 이득은 하한이다. \emph{범위.} 우리의 결론은 설정 파일이 선언하는 MCP 서버에 대한 것이며, 에이전트 스킬로 일반화하지 않는다. 스킬은 광고된 도구 목록을 갖지 않으므로 여기서 쓴 측정 단위가 그대로 적용되지 않는다. \emph{단일 모델.} 모든 요약은 한 시점의 한 모델에서 나왔다. 모델이나 시간에 따라 이 비율이 얼마나 달라지는지는 측정하지 않았다.
% \emph{Corpus.} GitHub's code search caps results per query and ranks rather than samples them, so the corpus is not a random sample of deployments; committed configurations may also differ from those people run. \emph{Adjudicated set.} Effects are derived for the 17 (measurement) and 34 (evaluation) most frequently configured servers, so the prevalence figures describe configurations built from popular servers, not the long tail. \emph{Threat model.} The prevalence figure is a property of the advertised surface under a worst-case agent; it does not assert that a deployment has been attacked or that an attack would succeed, and confirming exploitability is future work. \emph{Checker.} The checker is strict in one direction and loose in another: about 9 of 81 demotions cite spans that do contain the relevant identifier inside a longer expression that the token match misses, while 4 of 308 code-verified judgements rest on a token of four characters or fewer. \emph{Excerpts.} For large files the prompt shows windows around name occurrences, and 11 tool names present in large files were never shown, so the benefit we report from following dependencies is a lower bound. \emph{Scope.} Our conclusions concern the MCP servers a configuration file declares and do not generalise to agent skills, which have no advertised tool list and therefore no counterpart to the unit of measurement used here. \emph{Single model.} All summaries come from one model at one date; we have not measured how much the rate varies across models or over time.

\section{Related Work}
\label{sec:related}

\emph{아티팩트 하나를 검사하는 연구.} 도구 오염 탐지기는 광고된 설명에서 숨겨진 지시, 이름 가로채기, 유출 엔드포인트를 읽어낸다~\cite{jain2026detecting}. 신뢰할 수 있는 설명을 재생성해 이 벡터를 제거할 수 있고~\cite{ye2026trustdesc}, 벤치마크는 실제 서버에서 그런 공격의 성공률을 정량화하며~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}, 정적 분석은 서버 내부의 taint 계열 결함을 찾고~\cite{sun2026viper}, 동작 감사는 실행 중 도구를 관찰하며~\cite{tan2026sandscope}, 이들은 아티팩트를 그 자신의 manifest나 코드에 비추어 판단한다. 우리의 입력은 여러 아티팩트를 조합한 설정이고, 출력은 그 설정에 대한 변경이다.
% \emph{Vetting one artifact.} Tool-poisoning detectors read advertised descriptions for hidden instructions, shadowed names and exfiltration endpoints~\cite{jain2026detecting}; trusted descriptions can be regenerated to remove the vector~\cite{ye2026trustdesc}; benchmarks quantify how often such attacks succeed on real servers~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}; static analysis finds taint-style bugs inside a server~\cite{sun2026viper}; behavioural audit watches tools as they run~\cite{tan2026sandscope}; These judge an artifact against its own manifest or code. Our input is a configuration that composes several artifacts, and our output is a change to that configuration.

\emph{집합을 판단하는 연구.} lethal trifecta 프레이밍은 위험한 조합을 명명하고~\cite{willison2025trifecta}, toxic-flow 분석은 정책을 위반할 도구 순서를 구성해 점수화하며~\cite{beurerkellner2025toxicflow}, 조합 정책은 누적된 노출로 다음 호출이 위반이 되면 세션을 취소하고~\cite{schneider2026compositional}, 레지스트리 규모 조사는 일부 서버가 세 능력을 동시에 가진다고 보고한다~\cite{zhao2026parasites}. 우리는 판단하는 성질을 공유하되 모집단과 출력에서 다르다. 레지스트리 아티팩트가 아니라 사람들이 작성한 설정을 대상으로 측정하고, 판정이나 세션 범위의 제한이 아니라 patch를 반환한다.
% \emph{Judging a set.} The lethal-trifecta framing names the dangerous combination~\cite{willison2025trifecta}; toxic-flow analysis instantiates and scores tool sequences that would violate a policy~\cite{beurerkellner2025toxicflow}; compositional policies revoke a session once accumulated exposure would make the next call a violation~\cite{schneider2026compositional}; and a registry-scale census reports that some servers hold all three capabilities at once~\cite{zhao2026parasites}. We share the property being judged and differ in population and output: we measure it over configurations people wrote rather than over registry artifacts, and we return a patch rather than a verdict or a session-scoped restriction.

\emph{인접 생태계: 에이전트 스킬.} 에이전트 스킬은 MCP와 다른 메커니즘이다. 스킬은 지시문 파일과 선택적 스크립트의 묶음이며, 도구 목록을 협상하는 프로토콜이 없고 광고된 schema도 없다. 그럼에도 공급망 관점의 위험은 닮아 있어서, 스킬에 대해서도 건전한 능력 상한이 추상 해석으로 계산되고~\cite{bhardwaj2026formal}, 스킬 집합이 유도한 전이 시스템 위의 reachability가 능력 제한 cut과 짝지어지며~\cite{xiong2026reachability}, 페이로드를 여러 스킬에 분산해 아티팩트 단위 검사기를 회피하는 공격이 제시되었고~\cite{zeng2026colluskill}, 대규모 측정으로 취약점 유병률과 자격증명 유출, 공급망 오염이 보고되었다~\cite{liu2026agent, holzbauer2026context, chen2026your, qu2026supply, liu2026not}. 우리 결과는 이 생태계로 그대로 옮겨지지 않는다. 우리의 측정 단위는 설정 파일이 선언한 MCP 서버와 그 서버가 광고한 도구이며, 스킬에는 대응하는 광고된 surface가 없기 때문이다.
% \emph{A neighbouring ecosystem: agent skills.} Agent skills are a different mechanism from MCP: a skill is a bundle of instruction files and optional scripts, with no protocol that negotiates a tool list and no advertised schema. The supply-chain risks nevertheless rhyme, and for skills a sound capability bound is computed by abstract interpretation~\cite{bhardwaj2026formal}, reachability over a skill-induced transition system is paired with a capability-restricting cut~\cite{xiong2026reachability}, payloads are dispersed across skills to evade per-artifact scanners~\cite{zeng2026colluskill}, and large-scale measurement reports vulnerability prevalence, credential leakage and supply-chain poisoning~\cite{liu2026agent, holzbauer2026context, chen2026your, qu2026supply, liu2026not}. Our results do not transfer to that ecosystem unchanged: our unit of measurement is the MCP servers a configuration file declares and the tools those servers advertise, and a skill has no corresponding advertised surface.

\emph{실행 시점에 에이전트를 제약하는 연구.} 신뢰된 질의에서 제어 흐름과 데이터 흐름을 추출해 신뢰할 수 없는 데이터가 프로그램 흐름에 영향을 주지 못하게 하거나~\cite{debenedetti2025camel}, 기밀성과 무결성 라벨을 호출 단위로 추적·집행하거나~\cite{costa2025fides}, 호출 단위 권한 정책으로 최소 권한을 강제하거나~\cite{shi2025progent}, 질의 사이에 계획을 검사하거나~\cite{girrens2026spa}, 가드레일로 에이전트 루프를 감쌀 수 있다~\cite{murugan2026}. 이들은 질의나 호출 단위로 판단하고, 호스트를 교체하거나 계측해야 하며, 설치된 surface는 그대로 둔다. \textsc{Interlock}은 이들과 상호보완적이다. 질의가 실행되기 전에 기성 호스트가 광고하는 것을 좁히며, 한 배포가 둘을 함께 쓸 수 있다.
% \emph{Constraining the agent at run time.} Control and data flow can be extracted from the trusted query so that untrusted data cannot affect program flow~\cite{debenedetti2025camel}; confidentiality and integrity labels can be tracked and enforced per call~\cite{costa2025fides}; per-call privilege policies enforce least privilege~\cite{shi2025progent}; plans can be checked across queries~\cite{girrens2026spa}; and guardrails can wrap the agent loop~\cite{murugan2026}. These decide per query or per call, require the host to be replaced or instrumented, and leave the installed surface untouched. \textsc{Interlock} is complementary: it narrows what a stock host advertises before any query runs, and a deployment can do both.

\emph{기능 제약 아래 권한을 줄이는 연구.} 브라우저 확장의 과다 권한은 선언된 manifest 권한을 코드가 실제로 호출하는 API와 비교해 탐지되고~\cite{cheng2026percheck}, 프로그램 debloating은 테스트 스위트를 계속 통과시키면서 아티팩트를 줄인다~\cite{heo2018effective, sharif2018trimmer}. Android의 앱 간 권한 유출에 대한 조합 분석은 설치된 집합을 분석하고 앱이 설치·갱신·삭제될 때 이를 다시 검사한다~\cite{bagheri2015covert, li2015iccta}. 우리 상황은 무엇을 바꿀 수 있는가에서 다르다. 아티팩트는 제3자의 것이라 우리가 고쳐 쓸 수 없으므로 축소는 배포의 설정에서 일어나며, 보존해야 할 성질은 아티팩트가 아니라 배포에 속한다.
% \emph{Reducing privilege under a functional constraint.} Over-privilege in browser extensions is detected by comparing declared manifest permissions against the API calls the code makes~\cite{cheng2026percheck}, and program debloating reduces an artifact while a test suite must keep passing~\cite{heo2018effective, sharif2018trimmer}. Compositional analysis of inter-application permission leakage on Android analyses the installed set and re-checks it when applications are installed, updated or removed~\cite{bagheri2015covert, li2015iccta}. Our setting differs in what may be changed: the artifact belongs to a third party and is not ours to rewrite, so the reduction happens in the deployment's configuration, and the property to preserve belongs to the deployment rather than to the artifact.

\section{Conclusion}
\label{sec:conclusion}

에이전트 도구 보안 연구는 아티팩트 단위로 성숙해 왔고 집합 단위 질문도 명명되고 탐지되었지만, 사용자가 실제로 바꿀 수 있는 대상인 설정에는 고유한 분석이 없었다. 우리는 그 설정 모집단을 측정해, 분석 가능한 설정의 84.1\%가 한 세션 안에서 비공개 데이터와 공격자가 통제하는 콘텐츠, 공격자가 읽을 수 있는 목적지에 닿으며, 그 전부에서 단일 서버로 충분하고, 존재하는 축소 수단은 대체로 쓰이지 않으며 주요 원인 서버에는 아예 없음을 확인했다. 우리는 설정에 대한 최소 권한 tool surface를 계산하는 \textsc{Interlock}을 제시하고 그 첫 단계를 구현했다. 모든 주장이 인용된 소스에 대해 재검사되는 효과 요약으로, 전체의 72.5\%가, 패키지가 실제로 실행하는 코드를 함께 배포하는 경우에는 90.7\%가 검사를 통과한다. 실무적 함의는 두 가지다. 이 층위의 해법은 설정에 속하며, 사용자가 설치한 것의 대부분은 이미 내려받은 코드만으로 판정할 수 있다.
% Research on agent tool security has matured artifact by artifact, and the set-level question has been named and detected, yet the object a user can actually change --- the configuration --- has had no analysis of its own. We measured that configuration population and found that 84.1\% of the analysable configurations reach private data, attacker-controlled content and an attacker-readable destination in a single session, that a single server suffices in every such case, and that the narrowing controls which exist are largely unused and for the main offenders absent. We presented \textsc{Interlock}, which computes a least-privilege tool surface for a configuration, and implemented its first stage: effect summaries whose every claim is re-checked against the cited source, of which 72.5\% survive overall and 90.7\% survive where a package actually ships the code it runs. The practical reading is that the remedy for this layer belongs in the configuration, and that most of what a user installs can be judged from the code they already downloaded.
