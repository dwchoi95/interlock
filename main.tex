\title{\textsc{Interlock}}

\begin{abstract}
LLM 에이전트의 권한은 설정 파일이 결정한다. 사용자가 설치한 Model Context Protocol 서버 집합이 곧 모델이 보고 호출할 수 있는 도구를 정한다. 이 층위의 방어는 아티팩트를 하나씩 검사하거나, 설치된 조합이 위험한지 판단하거나, 실행 중인 에이전트를 제한한다. 그러나 사용자가 실제로 취할 수 있는 행동, 즉 설치한 surface 가운데 무엇을 끄면 설치 목적을 잃지 않고 위험을 줄일 수 있는지는 어느 것도 계산하지 않는다. 우리는 공개된 에이전트 설정 19,777개를 수집하고, 각 서버의 소스 코드에서 효과마다 파일과 줄 번호를 인용해 그 서버가 광고한 도구가 무엇에 닿는지 도출한다. 가장 자주 설정되는 서버 17개로만 구성된 설정 880개 가운데 84.1\%가 한 세션 안에서 비공개 데이터, 공격자가 통제하는 콘텐츠, 공격자가 읽을 수 있는 목적지에 모두 닿을 수 있다. 그 전부에서 서버 하나만으로 이미 충분하므로 제공자 사이의 조합은 결정적 요인이 아니며, surface를 좁힐 수 있는 제어 수단은 존재하는 곳에서는 거의 쓰이지 않고 주요 원인 서버들에는 아예 없다. 우리는 \textsc{Interlock}을 제시한다. 이 도구는 설정에 대해 최소 권한 tool surface를 세 단계로 계산한다. 신뢰도 순위를 매긴 효과 요약, 유도된 surface에 대한 정책 판정, 그리고 호스트와 서버가 이미 제공하는 제어 수단 위에서 배포의 선언된 작업을 보존하는 최소 비용 patch 합성이다. 이 논문은 첫 단계를 구현하고 평가한다. 서버 34개와 광고된 도구 433개에 대해 모델이 제시한 효과 주장의 72.5\%가 인용된 소스에 대한 결정적 재검사를 통과하며, 구현 코드가 실제로 배포되는 서버만 보면 90.7\%이고, 판정되지 않은 도구는 없었으며, 전체 비용은 8.53달러였다. 또한 공개된 패키지를 읽는 것만으로는 효과를 확정할 수 없는 세 가지 구조적 한계를 식별하고, 도구와 설정 코퍼스, 판정된 요약을 공개한다.
% An LLM agent's authority is decided by a configuration file: the set of Model Context Protocol servers a user installs fixes which tools the model can see and call. Defences for this layer vet one artifact at a time, judge whether an installed combination is dangerous, or restrict the agent while it runs. None computes what the user is able to act on, namely which part of the surface they installed can be switched off without losing the work they installed it for. We mine 19,777 public agent configurations and derive, from each server's own source code with a file-and-line citation for every effect, what its advertised tools can reach. Of the 880 configurations built entirely from the 17 most frequently configured servers, 84.1\% can reach private data, attacker-controlled content and an attacker-readable destination in one session; in every one of them a single server already suffices, so cross-provider composition is never the operative factor, and the controls that would narrow the surface are unused where they exist and absent for the main offenders. We present \textsc{Interlock}, which computes a least-privilege tool surface for a configuration in three stages: trust-ranked effect summarisation, policy decision over the induced surface, and synthesis of a minimum-cost patch over the controls hosts and servers already expose, subject to the deployment's declared tasks. This paper implements and evaluates the first stage: over 34 servers and 433 advertised tools, 72.5\% of the model's effect claims survive deterministic re-checking against the cited source, 90.7\% among the servers whose implementation code is actually distributed, with no tool left unjudged, at a cost of USD 8.53. We identify the three structural limits where reading a published package cannot establish an effect, and we release the tool, the configuration corpus and the adjudicated summaries.
\end{abstract}

\section{Introduction}
\label{sec:intro}

LLM 에이전트는 사용자가 설치한 제공자로부터 도구를 받는다. 설정 파일은 Model Context Protocol(MCP) 서버 집합과 각 서버를 실행하는 명령 또는 엔드포인트, 서버가 받는 자격증명, 그리고 일부 서버의 경우 어떤 도구를 광고할지 결정하는 플래그를 지정한다. 스킬 번들은 자체적으로 서버를 추가 등록하기도 한다~\cite{gaire2026systematization, liu2026agent}. 따라서 설정이 배포의 단위이며, 설정이 에이전트의 \emph{tool surface}, 즉 모델이 한 세션에서 보고 호출할 수 있는 도구 집합을 결정한다. 이 구조에서 보안상 중요한 성질이 두 가지 있다. surface 위의 모든 것은 도달 가능하다. 에이전트는 광고된 이름과 설명, 스키마를 읽고 도구를 선택하므로, 에이전트가 읽는 콘텐츠를 통제하는 공격자는 그 선택을 유도할 수 있다~\cite{zhao2026parasites}. 사용자가 쓸 생각이 없던 도구도 의존하는 도구와 똑같이 호출 가능하다. 또한 surface는 제공자가 아니라 사용자가 고른다. 즉 이를 좁힐 수 있는 주체는 사용자인데, 호스트가 분명하게 제시하는 유일한 축소 행동은 서버를 통째로 제거하는 것뿐이다.
% An LLM agent obtains its tools from providers that a user installs. A configuration file names a set of Model Context Protocol (MCP) servers, the command or endpoint that starts each one, the credentials it receives and, for some servers, flags that decide which of its tools are advertised; skill bundles may register further servers of their own~\cite{gaire2026systematization, liu2026agent}. The configuration is therefore the unit of deployment, and it decides the agent's \emph{tool surface}: the set of tools the model can see and call in a session. Two properties of that arrangement matter for security. Everything on the surface is reachable, because the agent selects tools by reading advertised names, descriptions and schemas, and an attacker who controls any content the agent reads can steer that selection~\cite{zhao2026parasites}; a tool the user never intends to use is as callable as one they rely on. And the surface is chosen by the user rather than the provider, so the user is the party who can narrow it --- yet the only narrowing action hosts make obvious is removing a server altogether.

이 층위를 보호하는 연구는 네 갈래다. 첫째는 개별 도구를 검사한다. 광고된 설명에서 숨겨진 지시, 이름 가로채기, 유출 엔드포인트를 탐지하고~\cite{jain2026detecting}, 신뢰할 수 있는 설명을 재생성해 도구 오염을 막으며~\cite{ye2026trustdesc}, 실제 서버에 대한 벤치마크로 이런 공격의 성공률을 정량화한다~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}. 둘째는 개별 제공자를 검사한다. 정적 분석으로 MCP 서버 내부의 taint 계열 취약점을 찾고~\cite{sun2026viper}, 실행 중 도구 동작을 감사하며~\cite{tan2026sandscope}, 추상 해석으로 에이전트 스킬의 자원 격자 위에서 건전한 능력 상한을 계산한다~\cite{bhardwaj2026formal}. 셋째는 제공자 \emph{집합}을 판단한다. lethal trifecta 프레이밍은 비공개 데이터, 신뢰할 수 없는 콘텐츠, 외부 통신을 위험한 조합으로 지목하고~\cite{willison2025trifecta}, toxic-flow 분석은 실행 시 정책을 위반할 도구 순서를 구성해 점수화하며~\cite{beurerkellner2025toxicflow}, 조합 정책은 누적된 노출로 다음 호출이 위반이 될 때 세션을 취소하고~\cite{schneider2026compositional}, 스킬이 유도한 전이 시스템 위의 reachability를 능력 제한 cut과 짝짓는다~\cite{xiong2026reachability}. 공격 연구도 같은 대상으로 옮겨 가, 아티팩트 단위 검사기를 회피하려고 페이로드를 여러 스킬에 분산하거나~\cite{zeng2026colluskill, liu2026sharelock}, 합법적인 도구들을 조율된 워크플로로 조립한다~\cite{zhao2026parasites}. 넷째는 실행 시점에 에이전트를 제약한다. 신뢰된 질의에서 제어 흐름과 데이터 흐름을 추출해 신뢰할 수 없는 데이터가 프로그램 흐름에 영향을 주지 못하게 하고~\cite{debenedetti2025camel}, 기밀성과 무결성 라벨을 추적해 호출마다 집행하며~\cite{costa2025fides}, 호출 단위 권한 정책으로 최소 권한을 강제하고~\cite{shi2025progent}, 질의 사이에 계획을 검사하며~\cite{girrens2026spa}, 제로 트러스트 가드레일로 에이전트 루프를 감싼다~\cite{murugan2026}. 대규모 측정이 이 그림을 완성한다. 마켓플레이스 아티팩트의 취약점 유병률~\cite{liu2026agent, holzbauer2026context}, 스킬에 의한 자격증명 유출~\cite{chen2026your}, 스킬 생태계의 공급망 오염~\cite{qu2026supply, liu2026not}이 보고되었다.
% Four strands of research protect this layer. The first inspects a single tool: hidden instructions, shadowed names and exfiltration endpoints are detected in advertised descriptions~\cite{jain2026detecting}, trusted descriptions are regenerated to prevent poisoning~\cite{ye2026trustdesc}, and benchmarks over real-world servers quantify how often such attacks succeed~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}. The second inspects a single provider: taint-style vulnerabilities inside MCP servers are found by static analysis~\cite{sun2026viper}, tool behaviour is audited at run time~\cite{tan2026sandscope}, and a sound capability bound over a resource lattice is computed by abstract interpretation for agent skills~\cite{bhardwaj2026formal}. The third judges a \emph{set} of providers: the lethal-trifecta framing names private data, untrusted content and external communication as the dangerous combination~\cite{willison2025trifecta}, toxic-flow analysis instantiates and scores tool sequences that would violate a policy at run time~\cite{beurerkellner2025toxicflow}, compositional policies revoke a session when accumulated exposure would make the next call a violation~\cite{schneider2026compositional}, and reachability over a skill-induced transition system is paired with a capability-restricting cut~\cite{xiong2026reachability}; attack work has moved to the same object, dispersing payloads across skills to evade per-artifact scanners~\cite{zeng2026colluskill, liu2026sharelock} and assembling legitimate tools into coordinated workflows~\cite{zhao2026parasites}. The fourth constrains the agent at run time: control and data flow are extracted from the trusted query so that untrusted data cannot affect program flow~\cite{debenedetti2025camel}, confidentiality and integrity labels are tracked and enforced at each call~\cite{costa2025fides}, per-call privilege policies enforce least privilege~\cite{shi2025progent}, plans are checked across queries~\cite{girrens2026spa}, and zero-trust guardrails wrap the agent loop~\cite{murugan2026}. Large-scale measurement completes the picture, reporting vulnerability prevalence across marketplace artifacts~\cite{liu2026agent, holzbauer2026context}, credential leakage by skills~\cite{chen2026your}, and supply-chain poisoning of skill ecosystems~\cite{qu2026supply, liu2026not}.

이 성과들은 하나의 작동 지점을 공유한다. 모두 \emph{제공자가 출하한 그대로의} tool surface를 판단하거나 제약한다. 도구 단위와 제공자 단위 분석은 아티팩트가 악성인지 취약한지 묻는다. 집합 단위 분석은 설치된 조합이 위험한지 묻고, 경고로 답하거나 실행 시점에 세션 동안 유지되는 제한으로 답한다. 실행 시점 집행은 현재 호출이 허용되는지 묻는다. 그러나 어느 것도 사용자가 실제로 행동할 수 있는 질문, 즉 \emph{설치한 surface 가운데 무엇을 설정 자체에서 끌 수 있으며 그러면서도 설치 목적을 잃지 않는가}를 계산하지 않는다. 이 질문은 앞의 것들을 다시 포장한 것이 아니다. 입력이 아티팩트가 아니라 구체적인 설정이고, 출력이 판정이 아니라 설정이며, 제약이 사용자 자신의 작업이고, 집행에 호스트 변경이 필요 없다. 호스트는 이미 도구 단위 허용·거부 목록을 받아들이고 서버는 이미 모드 플래그를 받아들이기 때문이다.
% These advances share an operating point: they judge or constrain the tool surface \emph{as the provider ships it}. Per-tool and per-provider analyses ask whether an artifact is malicious or vulnerable. Set-level analyses ask whether the installed combination is dangerous, and answer with an alert or, at run time, with a restriction that lasts for a session. Run-time enforcement asks whether the current call is permitted. What none of them computes is the question the user is actually able to act on: \emph{which part of the surface they installed can be switched off, in the configuration itself, without losing the work they installed it for}. This question is not a repackaging of the others. Its input is a concrete configuration rather than an artifact, its output is a configuration rather than a verdict, its constraint is the user's own tasks, and its enforcement needs no change to the host, because hosts already accept per-tool allow and deny lists and servers already accept mode flags.

우리는 이 질문을 측정 가능하게 만들고 실제로 측정한다. lethal trifecta 프레이밍~\cite{willison2025trifecta}을 따라, 광고된 도구로 도달 가능한 효과에 비공개 데이터 출처, 공격자가 통제하는 콘텐츠 출처, 공격자가 읽을 수 있는 sink가 모두 포함될 때 그 tool surface를 \emph{trifecta-complete}라 부르고, 자기 도구만으로 trifecta-complete가 되는 제공자를 \emph{capability-bundling}이라 부른다. 둘 다 설정이 광고하는 surface의 정적 성질이며, 주입된 콘텐츠가 선택을 유도하므로 어떤 도구의 출력이든 다른 도구의 입력으로 전달될 수 있는 에이전트를 가정해 평가한다. 어느 쪽도 특정 배포가 공격을 당했다거나 공격이 성공한다고 주장하지 않는다. 우리의 사전 연구는 GitHub에서 중복을 제거한 공개 설정 파일 19,777개를 수집하고, 가장 자주 설정되는 서버 17개의 모든 도구에 대해 서버 자신의 소스 코드에서 효과를 도출하되 효과마다 파일과 줄 번호를 기록하고 각 설정이 실제로 지정한 모드 플래그와 인자를 적용한다. 그 서버들로만 구성된 설정 880개 가운데 --- 우리가 수집한 다중 서버 설정의 10분의 1이며, 이는 코드를 읽은 서버만 요약했기 때문이다 --- \textbf{84.1\%}(740개)가 trifecta-complete이고, 코드로 확정하지 못한 효과를 양극단으로 밀어도 이 값은 2\%포인트 미만으로 움직인다. 그 740개 \emph{전부}에서 서버 하나가 이미 capability-bundling이므로 제공자 사이의 조합은 결정적 요인이 아니다. 브라우저와 fetch 서버가 로컬 및 인트라넷 URL에 닿아 얻는 비공개 데이터 효과를 제외하면, 조합이 있어야 trifecta-complete가 되는 설정의 비율은 3.3\% 이하에 머문다. 원인은 특별한 서버가 아니라 흔하고 인기 있는 서버들이다. 기본 surface에 문서화된 원격 코드 실행 도구를 포함하는 브라우저 자동화 서버, 비공개 저장소를 읽고 제3자의 이슈 텍스트를 읽으며 공개 댓글을 쓰는 코드 호스팅 서버, 에이전트가 고른 URL을 가져오고 로컬 파일을 읽는 컴포넌트 레지스트리 서버가 그렇다. 완화 수단은 존재하더라도 쓰이지 않거나 아예 없다. 코드 호스팅 서버의 읽기 전용 모드는 항목 189개 중 3개에만 나타나고, 브라우저 서버의 실행 도구를 끄는 플래그는 존재하지 않는다. surface 또한 고정되어 있지 않다. stdio 항목의 91.3\%가 버전을 고정하지 않고 실행되며 공개된 서버는 도구 목록을 자주 바꾸기 때문에~\cite{liu2026mcpevol}, 어떤 축소든 일회성이 아니라 재검사 가능해야 한다.
% We make the question measurable, and we measure it. Following the lethal-trifecta framing~\cite{willison2025trifecta}, we call a tool surface \emph{trifecta-complete} when the effects reachable through its advertised tools include a private-data source, an attacker-controlled content source and an attacker-readable sink, and we call a provider \emph{capability-bundling} when its own tools alone are trifecta-complete. Both are static properties of the surface a configuration advertises, evaluated under an agent that may pass any tool's output into any tool's input because injected content steers its choices; neither property asserts that a deployment has been attacked or that an attack would succeed. Our preliminary study collects 19,777 deduplicated public configuration files from GitHub and derives the effect of every tool of the 17 most frequently configured servers from the servers' own source code, recording a file-and-line citation for each effect and applying the mode flags and arguments each configuration actually sets. Of the 880 configurations that consist entirely of those servers --- one in ten of the multi-server configurations we collected, the restriction being that we summarise only servers whose code we read --- \textbf{84.1\%} (740) are trifecta-complete, and that figure moves by less than two points when the effects we could not settle from code are pushed to either extreme. In \emph{every} one of the 740, a single server is already capability-bundling, so cross-provider composition is never the operative factor; the share of configurations that need composition to become trifecta-complete stays at or below 3.3\% when we withdraw the private-data effect that browser and fetch servers derive from reaching local and intranet URLs. The drivers are ordinary, popular servers: a browser-automation server whose default surface includes a documented remote-code-execution tool, a code-hosting server that reads private repositories, reads third-party issue text and writes public comments, and a component-registry server that fetches agent-chosen URLs and reads local files. Mitigations exist but are unused or absent: read-only mode appears in 3 of 189 entries for the code-hosting server, and no flag disables the browser server's execution tool. The surface is also not static --- 91.3\% of stdio entries launch without a version pin, and published servers change their tool lists frequently~\cite{liu2026mcpevol} --- so any narrowing must be re-checkable rather than one-off.

이 성질도, 단일 제공자 사례도 우리가 처음 주장하는 것이 아니며, 선행 수치 하나는 직접 대조할 필요가 있다. 서버 1,360개의 도구 12,230개를 대상으로 한 레지스트리 규모 조사는 한 서버가 세 능력을 동시에 가질 수 있고 그 경우 서버 사이 협조 없이 공격을 완성할 수 있다고 보고하지만, 그런 서버를 단 2개로 센다~\cite{zhao2026parasites}. 출시된 설정 검사기는 단일 서버 사례와 서버 간 사례를 이미 별도의 발견 항목으로 구분하지만 각각이 얼마나 자주 발생하는지는 공개하지 않는다~\cite{patel2026mcpaudit}. 또 어떤 벤더 검사기는 대부분의 에이전트가 세 특성을 모두 가지므로 각 구성요소를 개별적으로 분석한다고 밝힌다~\cite{snyk2026agentscan}. 우리의 측정은 모집단과 효과의 정의에서 그 조사와 다르다. 조사는 레지스트리에서 서버를 균등하게 표집하며 그 대부분은 사용 빈도가 낮은 서버인 반면, 설정 코퍼스는 사람들이 실제로 설치하는 빈도로 서버에 가중치를 준다. 가장 자주 설정되는 서버 17개 중 9개가 capability-bundling이며, 여기에는 수천 개 설정에 등장하는 브라우저, 코드 호스팅, 데이터베이스, 컴포넌트 레지스트리 서버가 포함된다. 또한 우리는 도구 메타데이터가 아니라 서버 소스 코드에서 효과를 도출하므로, 메타데이터 수준 분류기가 보지 못하는 효과를 센다. 광고된 도구에서 도달 가능한 호스트 코드 실행, 그리고 브라우저나 fetch 도구가 로컬 및 인트라넷 URL을 받아들여 도달하는 페이지와 파일 내용이 그 예다. 따라서 두 결과는 방향에서는 일치하고 --- 서버 하나로 충분할 수 있다 --- 비율에서는 한 자릿수 배 이상 차이가 나는데, 인기도와 코드 수준 효과가 둘 다 비율을 끌어올리기 때문이다. 어느 쪽이든 방어에 주는 함의는 같다. 제공자 사이의 흐름만 끊으면 이 설정들의 84.1\%는 여전히 trifecta-complete로 남으므로, 해법은 제공자가 광고하는 surface 내부에서 작동해야 한다.
% Neither the property nor the single-provider case is ours to claim first, and one prior number deserves a direct comparison. % The natural remedies fail for reasons the same measurement makes concrete. % We present \textsc{Interlock}, which computes a least-privilege tool surface for a given agent configuration in three stages. \emph{Summarize} derives a per-tool effect summary from evidence ranked by trust: the server's source code and the configuration's own arguments first, declared schemas and annotations next, and free-text descriptions never used to lower an effect, only to raise it, because descriptions are attacker-controlled. \emph{Decide} evaluates the deployer's flow policy over the surface induced by the configuration and returns the witnessing tools for each forbidden flow, distinguishing the flows a single provider completes from those that need several. \emph{Repair} synthesises a minimum-cost patch over the controls that hosts and servers actually expose --- per-tool deny entries, server mode and toolset flags, argument narrowing, and, as the most expensive option, server removal --- subject to preserving the tasks the deployment declares, and emits it as a configuration diff the user can apply. \section{Background and Threat Model}
\label{sec:background}

\subsection{Tool surfaces and who decides them}

호스트 애플리케이션 --- IDE 어시스턴트, 데스크톱 에이전트, 코딩 에이전트 --- 은 설정 파일에 명시된 각 Model Context Protocol 서버를 실행하고 도구 목록을 요청한 뒤, 반환된 이름과 설명, JSON 스키마를 모델의 컨텍스트에 넣는다. 서버는 명령줄로 실행되는 로컬 프로세스일 수도, 컨테이너일 수도, 원격 엔드포인트일 수도 있으며, 스킬 번들이 서버를 추가로 기여하기도 한다. 한 세션에서 광고된 도구들의 합집합을 우리는 그 배포의 \emph{tool surface}라 부른다. 이 구조의 세 가지 성질이 이후 논의를 이끈다. surface는 개별 제공자가 아니라 사용자의 설정이 결정한다. surface 위의 모든 도구는 호출 가능하다. 도구 선택은 광고된 텍스트를 읽은 모델이 하기 때문이다. 그리고 surface는 고정되어 있지 않다. 호스트는 대개 버전을 고정하지 않은 패키지 지정으로 서버를 실행하므로, 도구 뒤의 코드는 사용자가 아무 행동을 하지 않아도 세션 사이에 바뀔 수 있다.
% A host application --- an IDE assistant, a desktop agent, a coding agent --- starts each Model Context Protocol server named in a configuration file, asks it for its tool list, and places the returned names, descriptions and JSON schemas into the model's context. A server may be a local process started by a command line, a container, or a remote endpoint; a skill bundle may contribute further servers. The union of the advertised tools, for the session, is what we call the deployment's \emph{tool surface}. Three properties of this arrangement drive the rest of the paper. The surface is decided by the user's configuration rather than by any single provider. Every tool on it is callable, because tool choice is made by the model from the advertised text. And the surface is not fixed: hosts commonly launch servers from an unpinned package specification, so the code behind a tool can change between sessions without any action by the user.

\subsection{Threat model}

우리는 에이전트가 자신이 읽은 콘텐츠 안의 지시를 따른다고 가정한다. 이는 lethal trifecta 프레이밍~\cite{willison2025trifecta}과 toxic-flow 분석~\cite{beurerkellner2025toxicflow}이 전제하는 가정이며, 이 층위에 대해 공개된 공격들이 실제로 악용하는 가정이다~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. 공격자는 임의의 웹 호스트와 콘텐츠를 통제하고, 여러 사람이 쓸 수 있거나 제3자가 제공하는 출처의 콘텐츠 --- 공개 이슈와 댓글, 저장소 내용, 커뮤니티 문서와 레지스트리, 검색 결과 --- 도 통제한다. 공격자는 사용자의 로컬 파일이나 사용자 계정에 담긴 데이터를 통제하지 못하며, 설치된 서버를 수정하지도 못한다. 공격자는 자신이 통제하는 호스트와 공개된 모든 것을 읽을 수 있다. 이 가정 아래에서, 어떤 배포의 surface가 한 세션 안에서 비공개 데이터 출처, 공격자가 통제하는 콘텐츠 출처, 공격자가 읽을 수 있는 목적지에 모두 닿을 때 그 배포는 위험하다. 우리는 그런 surface를 \emph{trifecta-complete}라 부르고, 자기 도구만으로 충분한 제공자를 \emph{capability-bundling}이라 부른다.
% We assume an agent that follows instructions found in the content it reads, which is the assumption under which the lethal-trifecta framing~\cite{willison2025trifecta} and toxic-flow analysis~\cite{beurerkellner2025toxicflow} are stated, and which published attacks on this layer exploit~\cite{zhao2026parasites, zeng2026colluskill, liu2026sharelock}. The attacker controls arbitrary web hosts and content, and content in multi-writer or third-party sources: public issues, comments and repository content, community documentation and registries, search results. The attacker does not control the user's local files or the data held in the user's own accounts, and does not modify the installed servers. The attacker can read hosts they control and anything published publicly. Under these assumptions a deployment is dangerous when its surface reaches, in the same session, a source of private data, a source of attacker-controlled content, and a destination the attacker can read; we call such a surface \emph{trifecta-complete}, and a provider whose own tools suffice \emph{capability-bundling}.

\subsection{Results}

\emph{분석 가능한 설정의 대부분이 trifecta-complete이다.} 판정 대상 서버 17개로만 구성된 설정 880개 --- 우리가 수집한 다중 서버 설정의 10분의 1 --- 가운데 \textbf{84.1\%}(740개)가 trifecta-complete이다. 코드로 확정하지 못한 효과를 양극단으로 밀어도 값은 84.0\%에서 85.6\% 사이로만 움직인다. 사용자 자신의 데이터베이스와 워크스페이스 안의 레코드도 공격자가 쓸 수 있다고 보는 두 번째 위협 모델 변형에서도 값은 84.1\%로 변하지 않는데, 해당 서버들이 이미 다른 경로로 세 효과 모두에 닿기 때문이다.
% \emph{Most analysable configurations are trifecta-complete.} Of the 880 configurations composed entirely of the 17 adjudicated servers --- one in ten of the multi-server configurations we collected --- \textbf{84.1\%} (740) are trifecta-complete. Pushing every effect we could not settle from code to either extreme moves the figure only between 84.0\% and 85.6\%. A second variant of the threat model, in which records inside the user's own databases and workspaces are also treated as attacker-writable, leaves the figure unchanged at 84.1\%, because those servers already reach all three effects by other means.

\emph{그것들을 위험하게 만드는 것은 조합이 아니다.} trifecta-complete인 740개 설정 전부에서 단일 서버가 이미 capability-bundling이다. trifecta-complete가 되기 위해 서버 두 개 이상이 필요한 설정의 수는 0이다. 브라우저와 fetch 서버가 \texttt{file://}, localhost, 인트라넷 URL에 닿아 얻는 비공개 데이터 효과를 제외해도 그 비율은 3.3\% 이하에 머물고, 여기에 더해 문서화된 원격 코드 실행 도구와 모든 로컬 URL 효과까지 무시해야 19.1\%에 이르는데, 그 시점에는 남은 사례 대부분이 한 문서 서버의 자격증명 의존 효과에 기대고 있다. 17개 서버 중 9개가 단독으로 capability-bundling이며, 그중에는 수천 개 설정에 등장하는 브라우저 자동화, 코드 호스팅, 데이터베이스, 컴포넌트 레지스트리 서버가 있다(표~\ref{tab:drivers}).
% \emph{Composition is not what makes them dangerous.} In every one of the 740 trifecta-complete configurations, a single server is already capability-bundling. The number of configurations that require two or more servers to become trifecta-complete is zero. The share stays at or below 3.3\% when we withdraw the private-data effect that browser and fetch servers derive from reaching \texttt{file://}, localhost and intranet URLs, and reaches 19.1\% only when we additionally ignore a documented remote-code-execution tool and every local-URL effect, at which point most of the remaining cases rest on a credential-gated effect of one documentation server. \emph{존재하는 제어 수단은 쓰이지 않고, 주요 원인 서버에는 아예 없다.} 코드 호스팅 서버는 읽기 전용 모드를 제공하지만 항목 189개 중 3개만 이를 설정하고 12개가 더 좁은 toolset을 선택한다. 데이터베이스 서버는 읽기 전용 모드를 제공하며 항목 116개 중 32개가 이를 설정한다. 코딩 에이전트 서버는 이름이 지정된 대부분의 context에서 셸 도구를 비활성화하는데, 항목 111개 중 84개가 그런 context를 선택한다. 채택률이 높은 유일한 사례다. 브라우저 자동화 서버에는 자기 프로세스 안에서 코드를 실행하는 도구를 제거하는 플래그가 없으며, archived 코드 호스팅 서버와 컴포넌트 레지스트리 서버, fetch 서버는 제한을 거는 플래그를 전혀 제공하지 않는다.
% \emph{The controls that exist are unused, and for the main drivers they do not exist.} The code-hosting server offers a read-only mode; 3 of 189 entries set it, and 12 select a narrower toolset. The database server offers a read-only mode; 32 of 116 entries set it. The coding-agent server disables its shell tool in most of its named contexts, and 84 of 111 entries select such a context --- the one case where adoption is high. For the browser-automation server no flag removes the tool that executes code in its own process, and the archived code-hosting server, the component-registry server and the fetch server expose no restricting flag at all.

\emph{surface는 고정되어 있지 않다.} 널리 설정되는 한 서버의 연속된 릴리스 64개 가운데 45개가 광고된 surface를 바꿨고 설명만 바뀐 것은 2개뿐이었다. 공개된 벤치마크는 서버 515개의 버전 9,273개에 걸쳐 초기 도구의 54.6\%가 수정되거나 폐기되었다고 보고한다~\cite{liu2026mcpevol}. 한편 stdio 항목의 91.3\%는 버전을 명시하지 않으므로 도구 뒤의 코드는 사용자가 아무 행동을 하지 않아도 바뀐다. 해시 기반 pinning은 이 모든 변화에 반응한다. 우리 코퍼스를 복원한 버전 이력에 대해 재생하면 18개월 창에서 설정당 약 23건의 변경 경고가 발생한다.
% \emph{The surface is not static.} Across 64 consecutive releases of one widely configured server, 45 changed the advertised surface and only 2 changed descriptions alone; a published benchmark reports that 54.6\% of initial tools were modified or deprecated across 9,273 versions of 515 servers~\cite{liu2026mcpevol}. Meanwhile 91.3\% of stdio entries name no version, so the code behind a tool changes without the user acting. Hash-based pinning reacts to all of this: replaying our corpus against recovered version histories produces about 23 change alerts per configuration over an 18-month window.

\subsection{What this rules out}

이 수치들은 설계 공간을 세 가지 방식으로 제약한다. 이 기저율에서 경고는 정보를 주지 못한다. 집합 단위 trifecta 검사는 이 설정들의 84\%에 경고를 띄우고, 사용자가 할 수 있는 일은 무시하는 것뿐이다. 실제로 어떤 벤더 검사기는 바로 이 점을, 즉 대부분의 에이전트가 세 특성을 모두 가지므로 각 구성요소를 개별적으로 분석한다고 밝힌다~\cite{snyk2026agentscan}. 서버 제거는 지나치게 거칠다. 판정을 좌우하는 서버들이 사용자가 의도적으로 설치한 것들이기 때문이다. 그리고 조합 지향 방어가 함의하는 해법인 제공자 사이 흐름 차단은 740개 설정 전부를 여전히 trifecta-complete로 남긴다. 남는 길은 사용자가 유지하는 제공자 \emph{내부에서} surface를 좁히는 것이며, 그것이 \textsc{Interlock}이 하는 일이다.
% These numbers constrain the design space in three ways. Alerting is uninformative at this base rate: a set-level trifecta check flags 84\% of these configurations, which is a warning a user can only dismiss --- a vendor scanner states exactly this, that most agents possess all three characteristics and that it therefore analyses each component separately~\cite{snyk2026agentscan}. Removing servers is too coarse, since the servers that drive the verdict are the ones users installed on purpose. And severing cross-provider flows, the remedy implied by composition-oriented defences, would leave every one of the 740 configurations trifecta-complete. What remains is to narrow the surface \emph{inside} the providers a user keeps, which is what \textsc{Interlock} does.

\section{Approach}
\label{sec:approach}

\subsection{Overview}

\textsc{Interlock}은 설정, 흐름 정책, 배포가 선언한 작업을 입력으로 받아, 호스트와 서버가 이미 제공하는 제어 수단 위의 patch를 반환한다. 절차는 세 단계다. \emph{Summarize}는 신뢰도 순으로 정렬한 증거에서 도구별 효과 요약을 도출한다. \emph{Decide}는 설정이 유도한 surface에 대해 정책을 평가하고 각 금지 흐름을 증언하는 도구를 반환한다. \emph{Repair}는 최소 비용 patch --- 도구 단위 거부 항목, 서버 모드와 toolset 플래그, 인자 축소, 그리고 가장 비싼 선택지인 서버 제거 --- 를 탐색해 금지된 흐름을 제거하면서 선언된 작업이 계속 동작하도록 한다. 이 논문은 \emph{Summarize}를 구현·평가하며, \emph{Decide}와 \emph{Repair}는 여기서 명세하고 진행 중인 작업으로 남겨 두되, 두 단계에 관한 모든 진술은 그에 맞게 표시한다.
% \textsc{Interlock} takes a configuration, a flow policy and the deployment's declared tasks, and returns a patch over the controls that hosts and servers already expose. It proceeds in three stages. \emph{Summarize} derives a per-tool effect summary from evidence ranked by trust. \emph{Decide} evaluates the policy over the surface the configuration induces and returns the tools that witness each forbidden flow. \emph{Repair} searches for a minimum-cost patch --- per-tool deny entries, server mode and toolset flags, argument narrowing, and, as the most expensive option, server removal --- that removes the forbidden flows while keeping the declared tasks working. This paper implements and evaluates \emph{Summarize}; \emph{Decide} and \emph{Repair} are specified here and are the subject of ongoing work, and we mark every claim about them accordingly.

\subsection{Summarize: trust-ranked effect summaries}

이 단계는 광고된 도구마다 하나의 질문에 답한다. 이 도구는 SECRET, UNTRUSTED, SINK, HOSTEXEC 가운데 무엇에 닿을 수 있으며 그 증거는 무엇인가. 증거는 공격자가 얼마나 통제할 수 있는지에 따라 순위가 매겨진다. 설정 자신의 인자와 서버의 소스 코드가 1순위, 선언된 스키마와 annotation이 2순위이며, 자유 서술 설명은 효과를 낮추는 데 결코 쓰이지 않는다. 올리는 데만 쓸 수 있는데, 설명은 판정 대상인 당사자가 작성하기 때문이다. HOSTEXEC은 나머지 셋을 함의한다. 호스트에서의 코드 실행은 호스트가 닿을 수 있는 모든 것에 닿기 때문이다.
% The stage answers one question per advertised tool: which of SECRET, UNTRUSTED, SINK and HOSTEXEC can this tool reach, and what is the evidence? Evidence is ranked by how much an attacker controls it. The configuration's own arguments and the server's source code rank first, declared schemas and annotations second, and free-text descriptions are never allowed to lower an effect --- they may only raise one, because a description is written by the party being judged. HOSTEXEC implies the other three, since host code execution reaches whatever the host can reach.

요약은 언어 모델이 생성하되 모든 주장에 \texttt{file:line} 증거를 인용해야 하며, 이후 결정적 검사기가 가져온 소스에서 인용된 구간을 다시 읽어 걸러낸다. 인용이 가져온 트리 안에서 해석되지 않거나, 그 구간에 도구 이름이나 근거 설명이 지목한 식별자가 없으면, 그 주장은 유지되되 미확인으로 표시된다. 미확인 주장이 효과를 낮춰서는 안 되므로 라벨은 살아남지만, 검증된 것으로는 세지 않는다. 모델이 아예 판정하지 않은 도구에는 가장 보수적인 값인 HOSTEXEC을 부여한다. 모델이 라벨 없이 무해하다고 판정한 도구는 그 증거가 코드에서 해석될 때만 무해로 센다. 문서는 효과의 \emph{부재}를 입증할 수 없기 때문이다. 이 구분이 이 단계의 출력을 그럴듯한 것이 아니라 감사 가능한 것으로 만들며, 5절은 그중 얼마가 검사기를 통과하는지 측정한다.
% Summaries are produced by a language model that must cite \texttt{file:line} evidence for every claim, and are then filtered by a deterministic checker that re-reads the cited span in the fetched source. A claim whose citation does not resolve inside the fetched tree, or whose span does not contain the tool name or an identifier the rationale names, is kept but marked undetermined; the label survives, because an unverified claim must not lower an effect, but it no longer counts as verified. A tool the model does not judge at all is assigned HOSTEXEC, the least restrictive reading. A tool the model clears with no labels counts as cleared only when its evidence resolves in code: documentation cannot establish the \emph{absence} of an effect. This split is what makes the stage's output auditable rather than merely plausible, and Section~\ref{sec:eval} measures how much of it survives the checker.

실무적으로 중요한 세부가 둘 있다. 모델에게는 모든 줄에 실제 줄 번호를 붙인 소스를 보여준다. 줄 번호가 없으면 인용된 줄이 파일 뒤로 갈수록 어긋나고, 올바른 판정이 검증에 실패하기 때문이다. 또한 패키지 자신의 코드가 도구 이름을 전혀 언급하지 않는 경우 --- 구현이 의존성에 있는 래퍼 패키지가 그렇다 --- 그 이름을 언급하는 직접 의존성을 스크립트 실행을 끈 채 가져와 함께 보여준다. 파이프라인의 어느 지점에서도 제공자 코드는 실행되지 않는다.
% Two details matter in practice. The model is shown source with every line prefixed by its true line number, because without them cited lines drift with depth and correct judgements fail verification. And when a package's own code never mentions a tool name --- the case for wrapper packages whose implementation lives in a dependency --- the direct dependencies that do mention it are fetched and shown, with scripts disabled; provider code is never executed at any point in the pipeline.

\subsection{Decide and Repair (planned)}

\emph{Decide}는 설정이 지정한 값 수준 조건 --- 읽기 전용 모드, toolset 선택, 경로 root, origin 허용 목록 --- 을 적용한 뒤 설정이 유도한 surface에 대해 배포자의 정책을 평가하고, 금지된 흐름마다 그것을 증언하는 도구를 반환할 것이다. \emph{Repair}는 선언된 작업의 보존을 조건으로 사용 가능한 제어 수단 위에서 최소 비용 patch를 탐색하고, 후보 patch마다 다시 판정해 결과가 가정이 아니라 검증된 것이 되게 하며, patch를 설정 diff로 내보낼 것이다. 우리는 두 단계를 서버 통째 제거, 서버 모드만 사용하는 방식, 이름 기반 휴리스틱 거부 목록, 동일 정책 하의 실행 시점 집행과 비교해, patch 전후의 benign utility, 공격 하 utility, 표적 공격 성공률을 측정할 계획이다.
% \emph{Decide} will evaluate the deployer's policy over the surface induced by a configuration, after applying the value-level conditions that configuration sets --- read-only modes, toolset selections, path roots, origin allow-lists --- and return, for each forbidden flow, the tools that witness it. \emph{Repair} will search for a minimum-cost patch over the available controls subject to preserving the declared tasks, re-deciding after each candidate patch so that the result is verified rather than assumed, and will emit the patch as a configuration diff. We plan to evaluate both against whole-server removal, server modes alone, a name-based heuristic deny list, and run-time enforcement under the same policy, measuring benign utility, utility under attack and targeted attack success rate before and after the patch.

\section{Evaluation of the Summarize Stage}
\label{sec:eval}

\subsection{Research question and setup}

여기서는 하나의 질문을 던진다. \textbf{RQ1.} 모델의 효과 판정 가운데 얼마가 제공자의 소스에 대한 결정적 재검사를 통과하며, 어떤 제공자에서 이 절차가 실패하는가? 우리는 광고된 surface를 복원할 수 있었던, 가장 자주 설정되는 npm 및 PyPI 서버 34개, 총 433개의 광고된 도구를 대상으로, 고정된 rubric과 JSON 스키마를 사용하는 Claude Opus~5, 패키지당 400\,KB의 소스 예산, 그리고 4절에서 설명한 검사기로 프로파일을 만든다. 광고된 각 도구는 정확히 하나의 범주에 들어간다. 모델이 라벨을 주장했고 인용이 코드에서 해석된 경우(\emph{verified}), 문서에서만 해석된 경우(\emph{verified\_doc}), 해석되지 않은 경우(\emph{demoted}), 모델이 무해로 판정했고 코드 증거가 있는 경우(\emph{cleared verified}) 또는 없는 경우(\emph{cleared unverified}), 그리고 모델이 판정하지 않은 경우(\emph{unjudged})다. 광고된 surface에 없는 이름을 판정한 경우는 별도로 센다. 기준과 정의는 실행 전에 사전 등록했으며, 계획서가 정한 dry-run에서 발견된 측정 도구 변경은 모두 실행 이후가 아니라 이전에 기록했다.
% We ask one question here: \textbf{RQ1.} How much of a model's effect judgement survives deterministic re-checking against the provider's source, and for which providers does the procedure fail? We profile the 34 most frequently configured npm and PyPI servers whose advertised surface we could recover, 433 advertised tools in total, using Claude Opus~5 with a fixed rubric and a JSON schema, a 400\,KB per-package source budget, and the checker described in Section~\ref{sec:approach}. Each advertised tool falls into exactly one bucket: the model claimed labels for it and the citation resolved in code (\emph{verified}), resolved only in documentation (\emph{verified\_doc}), or did not resolve (\emph{demoted}); or the model cleared it, with (\emph{cleared verified}) or without (\emph{cleared unverified}) code evidence; or the model did not judge it (\emph{unjudged}). Judged names absent from the advertised surface are counted separately. Thresholds and definitions were registered before the run, and every change to the instrument found by the prescribed dry-runs was recorded before the run rather than afterwards.

\subsection{Threats to validity}

\emph{코퍼스.} GitHub 코드 검색은 질의당 결과 수에 상한을 두고 표집이 아니라 관련도 순위로 반환하므로, 이 코퍼스는 배포의 무작위 표본이 아니다. 커밋된 설정은 사람들이 실제로 실행하는 설정과 다를 수도 있다. \emph{판정 대상 집합.} 효과는 가장 자주 설정되는 서버 17개(측정)와 34개(평가)에 대해서만 도출했으므로, 유병률 수치는 인기 서버로 구성된 설정을 설명하며 롱테일을 설명하지 않는다. \emph{위협 모델.} 유병률 수치는 최악 가정의 에이전트 아래에서 광고된 surface가 갖는 성질이다. 특정 배포가 공격을 당했다거나 공격이 성공한다고 주장하지 않으며, 악용 가능성 확인은 향후 과제다. \emph{검사기.} 검사기는 한 방향으로 엄격하고 다른 방향으로 느슨하다. 강등 81건 중 약 9건은 인용 구간에 해당 식별자가 더 긴 표현 안에 실제로 존재하지만 토큰 일치가 이를 놓친 경우이고, 반대로 코드로 검증된 판정 308건 중 4건은 네 글자 이하의 토큰에 기대고 있다. \emph{발췌.} 큰 파일에 대해서는 이름이 등장하는 지점 주변 창만 보여주므로, 큰 파일에 존재하는 도구 이름 11개는 모델에게 한 번도 보이지 않았다. 따라서 의존성 추적의 이득은 하한이다. \emph{단일 모델.} 모든 요약은 한 시점의 한 모델에서 나왔다. 모델이나 시간에 따라 이 비율이 얼마나 달라지는지는 측정하지 않았다.
% \emph{Corpus.} GitHub's code search caps results per query and ranks rather than samples them, so the corpus is not a random sample of deployments; committed configurations may also differ from those people run. \emph{Adjudicated set.} Effects are derived for the 17 (measurement) and 34 (evaluation) most frequently configured servers, so the prevalence figures describe configurations built from popular servers, not the long tail. \emph{Threat model.} The prevalence figure is a property of the advertised surface under a worst-case agent; it does not assert that a deployment has been attacked or that an attack would succeed, and confirming exploitability is future work. \emph{Checker.} The checker is strict in one direction and loose in another: about 9 of 81 demotions cite spans that do contain the relevant identifier inside a longer expression that the token match misses, while 4 of 308 code-verified judgements rest on a token of four characters or fewer. \emph{Excerpts.} For large files the prompt shows windows around name occurrences, and 11 tool names present in large files were never shown, so the benefit we report from following dependencies is a lower bound. \emph{Single model.} All summaries come from one model at one date; we have not measured how much the rate varies across models or over time.

\section{Related Work}
\label{sec:related}

\emph{아티팩트 하나를 검사하는 연구.} 도구 오염 탐지기는 광고된 설명에서 숨겨진 지시, 이름 가로채기, 유출 엔드포인트를 읽어낸다~\cite{jain2026detecting}. 신뢰할 수 있는 설명을 재생성해 이 벡터를 제거할 수 있고~\cite{ye2026trustdesc}, 벤치마크는 실제 서버에서 그런 공격의 성공률을 정량화하며~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}, 정적 분석은 서버 내부의 taint 계열 결함을 찾고~\cite{sun2026viper}, 동작 감사는 실행 중 도구를 관찰하며~\cite{tan2026sandscope}, 추상 해석은 스킬의 건전한 능력 상한을 계산한다~\cite{bhardwaj2026formal}. 이들은 아티팩트를 그 자신의 manifest나 코드에 비추어 판단한다. 우리의 입력은 여러 아티팩트를 조합한 설정이고, 출력은 그 설정에 대한 변경이다.
% \emph{Vetting one artifact.} Tool-poisoning detectors read advertised descriptions for hidden instructions, shadowed names and exfiltration endpoints~\cite{jain2026detecting}; trusted descriptions can be regenerated to remove the vector~\cite{ye2026trustdesc}; benchmarks quantify how often such attacks succeed on real servers~\cite{wang2026mcptox, yang2025mcpsecbench, liu2026manual}; static analysis finds taint-style bugs inside a server~\cite{sun2026viper}; behavioural audit watches tools as they run~\cite{tan2026sandscope}; and abstract interpretation computes a sound capability bound for a skill~\cite{bhardwaj2026formal}. These judge an artifact against its own manifest or code. Our input is a configuration that composes several artifacts, and our output is a change to that configuration.

\emph{집합을 판단하는 연구.} lethal trifecta 프레이밍은 위험한 조합을 명명하고~\cite{willison2025trifecta}, toxic-flow 분석은 정책을 위반할 도구 순서를 구성해 점수화하며~\cite{beurerkellner2025toxicflow}, 조합 정책은 누적된 노출로 다음 호출이 위반이 되면 세션을 취소하고~\cite{schneider2026compositional}, 스킬이 유도한 전이 시스템 위의 reachability를 능력 제한 cut과 짝지으며~\cite{xiong2026reachability}, 레지스트리 규모 조사는 일부 서버가 세 능력을 동시에 가진다고 보고한다~\cite{zhao2026parasites}. 우리는 판단하는 성질을 공유하되 모집단과 출력에서 다르다. 레지스트리 아티팩트가 아니라 사람들이 작성한 설정을 대상으로 측정하고, 판정이나 세션 범위의 제한이 아니라 patch를 반환한다.
% \emph{Judging a set.} The lethal-trifecta framing names the dangerous combination~\cite{willison2025trifecta}; toxic-flow analysis instantiates and scores tool sequences that would violate a policy~\cite{beurerkellner2025toxicflow}; compositional policies revoke a session once accumulated exposure would make the next call a violation~\cite{schneider2026compositional}; reachability over a skill-induced transition system is paired with a capability-restricting cut~\cite{xiong2026reachability}; and a registry-scale census reports that some servers hold all three capabilities at once~\cite{zhao2026parasites}. We share the property being judged and differ in population and output: we measure it over configurations people wrote rather than over registry artifacts, and we return a patch rather than a verdict or a session-scoped restriction.

\emph{실행 시점에 에이전트를 제약하는 연구.} 신뢰된 질의에서 제어 흐름과 데이터 흐름을 추출해 신뢰할 수 없는 데이터가 프로그램 흐름에 영향을 주지 못하게 하거나~\cite{debenedetti2025camel}, 기밀성과 무결성 라벨을 호출 단위로 추적·집행하거나~\cite{costa2025fides}, 호출 단위 권한 정책으로 최소 권한을 강제하거나~\cite{shi2025progent}, 질의 사이에 계획을 검사하거나~\cite{girrens2026spa}, 가드레일로 에이전트 루프를 감쌀 수 있다~\cite{murugan2026}. 이들은 질의나 호출 단위로 판단하고, 호스트를 교체하거나 계측해야 하며, 설치된 surface는 그대로 둔다. \textsc{Interlock}은 이들과 상호보완적이다. 질의가 실행되기 전에 기성 호스트가 광고하는 것을 좁히며, 한 배포가 둘을 함께 쓸 수 있다.
% \emph{Constraining the agent at run time.} Control and data flow can be extracted from the trusted query so that untrusted data cannot affect program flow~\cite{debenedetti2025camel}; confidentiality and integrity labels can be tracked and enforced per call~\cite{costa2025fides}; per-call privilege policies enforce least privilege~\cite{shi2025progent}; plans can be checked across queries~\cite{girrens2026spa}; and guardrails can wrap the agent loop~\cite{murugan2026}. These decide per query or per call, require the host to be replaced or instrumented, and leave the installed surface untouched. \textsc{Interlock} is complementary: it narrows what a stock host advertises before any query runs, and a deployment can do both.

\emph{기능 제약 아래 권한을 줄이는 연구.} 브라우저 확장의 과다 권한은 선언된 manifest 권한을 코드가 실제로 호출하는 API와 비교해 탐지되고~\cite{cheng2026percheck}, 프로그램 debloating은 테스트 스위트를 계속 통과시키면서 아티팩트를 줄인다~\cite{heo2018effective, sharif2018trimmer}. Android의 앱 간 권한 유출에 대한 조합 분석은 설치된 집합을 분석하고 앱이 설치·갱신·삭제될 때 이를 다시 검사한다~\cite{bagheri2015covert, li2015iccta}. 우리 상황은 무엇을 바꿀 수 있는가에서 다르다. 아티팩트는 제3자의 것이라 우리가 고쳐 쓸 수 없으므로 축소는 배포의 설정에서 일어나며, 보존해야 할 성질은 아티팩트가 아니라 배포에 속한다.
% \emph{Reducing privilege under a functional constraint.} Over-privilege in browser extensions is detected by comparing declared manifest permissions against the API calls the code makes~\cite{cheng2026percheck}, and program debloating reduces an artifact while a test suite must keep passing~\cite{heo2018effective, sharif2018trimmer}. Compositional analysis of inter-application permission leakage on Android analyses the installed set and re-checks it when applications are installed, updated or removed~\cite{bagheri2015covert, li2015iccta}. Our setting differs in what may be changed: the artifact belongs to a third party and is not ours to rewrite, so the reduction happens in the deployment's configuration, and the property to preserve belongs to the deployment rather than to the artifact.

\section{Conclusion}
\label{sec:conclusion}

에이전트 도구 보안 연구는 아티팩트 단위로 성숙해 왔고 집합 단위 질문도 명명되고 탐지되었지만, 사용자가 실제로 바꿀 수 있는 대상인 설정에는 고유한 분석이 없었다. 우리는 그 설정 모집단을 측정해, 분석 가능한 설정의 84.1\%가 한 세션 안에서 비공개 데이터와 공격자가 통제하는 콘텐츠, 공격자가 읽을 수 있는 목적지에 닿으며, 그 전부에서 단일 서버로 충분하고, 존재하는 축소 수단은 대체로 쓰이지 않으며 주요 원인 서버에는 아예 없음을 확인했다. 우리는 설정에 대한 최소 권한 tool surface를 계산하는 \textsc{Interlock}을 제시하고 그 첫 단계를 구현했다. 모든 주장이 인용된 소스에 대해 재검사되는 효과 요약으로, 전체의 72.5\%가, 패키지가 실제로 실행하는 코드를 함께 배포하는 경우에는 90.7\%가 검사를 통과한다. 실무적 함의는 두 가지다. 이 층위의 해법은 설정에 속하며, 사용자가 설치한 것의 대부분은 이미 내려받은 코드만으로 판정할 수 있다.
% Research on agent tool security has matured artifact by artifact, and the set-level question has been named and detected, yet the object a user can actually change --- the configuration --- has had no analysis of its own. We measured that configuration population and found that 84.1\% of the analysable configurations reach private data, attacker-controlled content and an attacker-readable destination in a single session, that a single server suffices in every such case, and that the narrowing controls which exist are largely unused and for the main offenders absent. We presented \textsc{Interlock}, which computes a least-privilege tool surface for a configuration, and implemented its first stage: effect summaries whose every claim is re-checked against the cited source, of which 72.5\% survive overall and 90.7\% survive where a package actually ships the code it runs. The practical reading is that the remedy for this layer belongs in the configuration, and that most of what a user installs can be judged from the code they already downloaded.
