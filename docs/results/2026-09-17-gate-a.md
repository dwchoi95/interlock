## Why the unusable packages fail (explanatory analysis after the gate; not used to change it)

The three packages with low verification each hit a different limit of reading effects from a published package's source, not a mislabelling by the model:

- **Binary distribution.** `@azure/mcp` ships a launcher (`index.js`) and a post-install script that downloads a .NET binary; the implementation is not in the package. All 68 citations point at README.md, and 52 fail because the cited documentation lines do not name the tool.
- **Tool surfaces generated at run time.** `@notionhq/notion-mcp-server` builds its tool names (for example `API-create-a-comment`) from an OpenAPI description when it starts. The names occur nowhere in the source, so no source file was selected, dependency following found nothing, and every judgement cited the advertised tool list instead of a file.
- **Minified bundles.** `@supabase/mcp-server-supabase` implements its tools in a bundled `dist/chunk-*.js`; 13 of 35 citations point at line 1 of that bundle while the cited identifiers sit on other lines.

The four zero-claim packages are not failures of the method; their tools were cleared, and in three of the four cases every clear was verified from code.

## Sensitivity and threats found by the final review (reported, not used to change the branch)

- **Packages whose model request contained no implementation code.** For `@notionhq/notion-mcp-server` no source file was selected, and for `@azure/mcp` only README.md was. Together they hold 67 of the 335 claims, none code-verified. Excluding them gives a verified-claim rate of **243 / 268 = 0.907**. The pre-registration pools over all listed packages, so 0.725 is the registered figure; 0.907 describes the method where code was actually available. Stats rows now record `code_files_shown` and `doc_files_shown` so this split is computed rather than inferred in later phases.
- **Where the zero-claim rule comes from.** Treating a package with no labelled claims as not usable comes from the plan's gate script, written before measurement; the pre-registration text itself is silent on it. Hence the separately reported sensitivity reading (30 / 34).
- **Checker strictness and looseness.** About 9 of 81 demotions cite spans that do contain the relevant identifier but inside a longer expression the backticked token does not match verbatim (6 of `chrome-devtools-mcp`'s 7). In the other direction, 4 of 308 code-verified judgements rest on a backticked token of four characters or fewer. Neither moves the branch.
- **Excerpts can omit a tool.** Large-file excerpts sample occurrence positions, not tools; 11 tool names present in large files were never shown to the model (`@playwright/mcp` 5, `firecrawl-mcp` 4, `chrome-devtools-mcp` 2). Some documentation-only claims and one unverified clear in `@playwright/mcp` follow from this, so D4's reported effect is a lower bound.
- **Scope of the no-write guarantee.** The pipeline writes only inside its own cache, but `npm` and `pip` maintain their own user-level download caches (`~/.npm`, pip's cache). No provider code is executed.
- **Failure log.** `batch-failures.jsonl` keeps the lines for the four packages that failed in the batch and were then profiled synchronously; the gate reads profiles and stats, where all 34 packages are present.

## Consequences for the plan (A2, as pre-registered)

1. Phases B through E proceed on the **27 usable packages** only. The restriction is reported as a threat to validity, together with the three structural limits above, which are themselves a finding about where code-derived effect summaries cannot reach.
2. Before Phase B starts, recompute how many real configurations in the corpus consist only of usable packages; that count bounds the Phase C and D evaluation set. If it falls below the size Phase B needs, record it and decide at Gate B's pre-registration whether to extend the method to one of the three limits first.
3. Candidate extensions, none adopted now: read a package's linked source repository when the package is a binary launcher; read the OpenAPI description a server loads its tools from; map bundled lines through source maps when a bundle ships one.
4. Phase B's gate is pre-registered at its start, as the spec requires.
